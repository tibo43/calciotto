# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Calciotto is a small full-stack app for organizing amateur football ("calciotto") matches: creating matches, assigning players to color-named teams, and tracking goals per player. Backend is Go (Gin + GORM + PostgreSQL), frontend is Vue 3 (Vue CLI).

## Commands

### Dev environment (all services)
```bash
cd devops
docker compose --env-file env/develop.env up
```
This starts Postgres (with healthcheck), the Go backend (via `air` for live reload, port 8080), the Vue frontend (`npm install && npm run serve`, port 4000), and a one-shot `seed` service that runs `go run ./cmd/seed` as soon as `db` is healthy. The `--env-file` flag is required — without it, `${POSTGRES_PORT}`/`${POSTGRES_PASSWORD}` and the bare `DB_NAME`/`DB_USER`/`DB_PASSWORD` refs in `docker-compose.yaml` resolve to empty strings (Compose only auto-loads a file literally named `.env` next to the compose file, which this repo intentionally doesn't ship since `.env` is gitignored). The backend and frontend containers bind-mount `../app` and `../frontend`, so local edits are picked up without rebuilding the image.

`seed` is idempotent (`cmd/seed` skips itself once players already exist), so it's safe to run on every `up` — after the first successful run it just logs "skipping" and exits. Force a fresh reseed with `docker compose exec backend go run ./cmd/seed -reset`.

### Backend (`app/`)
```bash
go build ./...                 # build
go run .                       # run directly (needs Postgres reachable — set DB_HOST/DB_PORT/DB_USER/DB_PASSWORD/DB_NAME, see Gotchas)
go run ./cmd/seed              # populate the DB with demo players/teams/matches (skips if players already exist)
go run ./cmd/seed -reset       # wipe players/teams/matches/match_players first, then reseed
go run ./cmd/seed -matches 10  # control how many past matches get generated (default 6)
```
There is no separate lint command configured for the Go module, and no test suite currently exists.

### Frontend (`frontend/`)
```bash
npm run serve       # dev server on port 4000
npm run build       # production build
npm run lint        # eslint (plugin:vue/vue3-essential + eslint:recommended)
npm run test:unit   # Jest unit tests (added via `vue add unit-jest`), see tests/unit/
npm run test:visual        # Playwright visual regression tests, in Docker (see below)
npm run test:visual:update # same, accepting the current rendering as the new baselines
```
`tests/unit/` covers, under `services/`: `activeGroup.js` (the localStorage-backed active-group wrappers and the `resolveActiveGroup`/`resolveActiveGroupId` stale-id-fallback/no-groups/promise-cache logic, with `@/services/api`'s `getMyGroups` mocked), `datetime.js` (local-offset RFC3339 round-tripping, including the DST-boundary and half-hour-zone cases), `matchRegistration.js` (the five registration states and the team-filling split, both pure functions), `motmVoting.js` (the 24h voting-window anchor for both the scheduled and unscheduled cases, and the open/closed predicate around the deadline), `whatsappShare.js` (the shared message text and the URL-encoding of the wa.me link), `shortLink.js` (round-tripping a UUID through base62, including the all-zero and all-F edge cases and the fixed-width padding they exercise; and rejecting a truncated, over-long, invalid-character, or out-of-range code) and `api.js` (that the sign-up calls hit the right paths and send no `group_id`, and the same for the three Man of the Match vote calls plus `getMotmStandings`); under `router/`: `index.js` (`canEditMatch` and the shared `findGroupForMatch` helper it's built on, the pure-ish guard/search functions behind `/matches/:id/edit`'s `beforeEnter` and the `/m/:code` deep link's group resolution — see "Frontend" below — since there's no existing precedent in this codebase for mounting the router itself in a test); and under `components/`: `TeamColourPicker.vue` (native colour-input value/emit round-tripping, background reflecting `modelValue` vs falling back to the rainbow placeholder when empty, and `disabled` actually suppressing emits) plus `MatchesPanel.vue` (the scheduling half of the create modal, what a scheduled match's card renders, season preselection, the inline sign-up panel's Participate/Withdraw/count, the confirmed/waiting sign-up lists with names, the "Edit Match" link's admin-only visibility, the Man of the Match star/vote-count/window-disabled flow now living here, the gold `.is-leader` marker's independence from the caller's own vote, the "Selected Match Details" preview's collapse-to-teams-only toggle once a scheduled match's roster is composed, the card badge's switch from the sign-up state to Upcoming/Completed once composed, and an unscheduled match's card gaining an "Upcoming" badge only when composed-but-not-yet-played, never a new "Completed" one on an already-played match) and `MatchDetails.vue` (the sign-up panel's visibility, the four window states, admin close/reopen, the confirmed/waiting split, "Fill teams from sign-ups" gating *and* behaviour, the match-status badge, the compose-choice modal, and the Add Player list's sign-up tiering and the Share on WhatsApp link's gating/content — the Man of the Match voting tests moved out of this file entirely along with the feature itself, see "Frontend" below). `MatchesAndStandings.vue` has its own first slice too, scoped to the season-preselection fix, plus a second slice covering the `?match=<code>` deep link's tab/group/season/prop wiring. `MotmStandingsTable.vue` joins `PointsStandingsTable.vue`/`ScorersTable.vue` as untested pure presentation, for the same reason those two are: no state machine of its own, just rows handed down by the page. It is not a mandate for full coverage — the rule of thumb the existing specs follow is that pure logic gets tested directly and components only where a state machine drives what's rendered. Jest config is `jest.config.js` (the `@vue/cli-plugin-unit-jest` preset) plus the `jest` env override the plugin added to `package.json`'s `eslintConfig` for files under `tests/unit/**/*.spec.js`.

**Visual regression tests** live in `tests/visual/` (Playwright, `playwright.config.js`) and are a separate suite from `test:unit` — Jest runs in jsdom and renders no pixels at all, so a CSS or layout regression is invisible to it. Twelve baselines cover the home page's three sub-tabs (light, dark, narrow viewport, and as a plain member) and the match detail page (played match as admin vs. member, and a scheduled match with sign-ups open / open in dark mode / closed as the composing admin / not open yet), i.e. the states where the app's UI actually branches. `tests/visual/__screenshots__/` **is committed** — the baselines are the assertion.

Three things make those screenshots reproducible, and all three are load-bearing:
- **They only ever run in one environment.** `npm run test:visual` shells out to `tests/visual/run-in-docker.sh`, which runs the suite inside `mcr.microsoft.com/playwright:v1.62.1-noble`; the `visual` job in CI uses the *same image* as its `container:`. Font rasterisation and antialiasing differ between macOS and Linux, so a baseline generated on a Mac fails against CI on every single screenshot — and "fixing" that with a loose pixel threshold would mean the suite no longer catches anything. There is deliberately **no script that runs Playwright on the host**. The image tag is pinned to the `@playwright/test` version in `package.json` (the image ships the browser build its own version expects) and to the tag in `.github/workflows/ci.yml`: bump all three together. `snapshotPathTemplate` carries `{projectName}` but no `{platform}` — two viewports are a real dimension, two platforms are not, since only one ever produces baselines.
- **The backend is stubbed, not run.** `tests/visual/fixtures/app.js` intercepts `http://127.0.0.1:8080/**` (the `VUE_APP_API_BASE_URL` fallback the tested bundle is built with) and serves the frozen fixtures in `fixtures/data.js`. Running the real stack instead would make every screenshot a fresh diff, since `cmd/seed` builds its matches on "the last N Sundays" with random goals; stubbing also turns awkward states (a closed sign-up list, a player who left the group, a member who isn't an admin) into a different fixture rather than a setup script. A **catch-all route registered first** (Playwright checks handlers newest-first) records any call that reached no stub and answers 500, and each test asserts that list is empty — otherwise a forgotten stub would quietly photograph an error state and pass forever.
- **The clock is frozen** at `FIXED_NOW` (2026-09-04, two days before the fixtures' kick-off) via `page.clock.setFixedTime` before `goto`. The sign-up panel derives its whole state from `Date.now()`, so without this the calendar decides what the screenshots contain. A fixed *time* rather than fake timers, so transitions and timeouts keep working and the page finishes rendering.

The app is served from `dist/` by `tests/visual/serve-dist.js`, a ~40-line static server that reproduces `vercel.json`'s SPA rewrite (the tests deep-link into `/matches/:id/edit`, and the router is `createWebHistory`, so without the fallback every screenshot would capture a 404). It 404s a *missing asset* rather than falling back for it, so a broken build fails visibly instead of looking like a styling bug.

When a visual diff is intentional (a deliberate design change), regenerate with `npm run test:visual:update` and commit the new PNGs **in the same commit as the CSS change** — a baseline update sitting in its own commit is indistinguishable from a rubber-stamped regression.

## Continuous Integration

`.github/workflows/ci.yml` runs on every push and pull request, with three independent build/test jobs (no deployment step in any of them — see "Production deployment" below for those). Both triggers stay on: `push` is what `deploy-backend`/`deploy-frontend` gate on (they refuse to run on a `pull_request` event even against master, since a fork's PR has no access to that environment's secrets — see below), and `pull_request` is what gives a PR its own check run and comment thread. A push to a branch with an open PR fires both for the same commit, which would run every job — including the two Docker/Vercel builds — twice for nothing; a `concurrency` group (`${{ github.workflow }}-${{ github.head_ref || github.ref_name }}`) collapses the two into one key per branch (`head_ref` is only set on the `pull_request` event, `ref_name` is the *short* name `push` carries, and for the same branch they resolve to the same string) so the newer run cancels the older. `cancel-in-progress` is false specifically on `master`, since that's the branch a cancelled run could leave a Docker push or a Vercel deploy half-done on — a feature branch has no deploy job, so cancelling there is free.
- **Backend**: `actions/setup-go` pinned via `go-version-file: app/go.mod` (not a hardcoded Go version), a `postgres:17` service container with a `pg_isready` health check backing the network connection integration tests need (see `app/internal/testutil`), then from `app/`: `go build ./...`, `go vet ./...`, `go test ./... -count=1` (every package's tests share that one database and run concurrently — safe only because schema application takes an advisory lock, see Gotchas) with `DB_HOST=localhost`/`DB_PORT`/`DB_USER`/`DB_PASSWORD`/`DB_NAME` matching the service container's own credentials, plus a placeholder `JWT_SECRET` (required by `main.go`'s fail-fast check, though no test currently reads it from the environment — they hardcode their own test secrets instead).
- **Frontend**: `actions/setup-node` at `node-version: 24` (matching `devops/docker-compose.yaml`'s `node:24-alpine`), then from `frontend/`: `npm ci` (not `npm install` — installs strictly from the committed lockfile), `npm run lint`, `npm run test:unit`, `npm run build` — unit tests run before the build so a broken test fails fast instead of waiting on a full webpack build.

- **Frontend visual regression**: a third job, `visual`, running *inside* `mcr.microsoft.com/playwright:v1.62.1-noble` as its `container:` — no `actions/setup-node` and no `playwright install`, because the point is that the rendering environment is byte-identical to the one that produced the committed baselines (see "Visual regression tests" above). It runs `npm ci` → `npm run build` → `npx playwright test` against the production build, and uploads `playwright-report/` as an artifact on **every** run, not just a failing one (`if: always()`) — the HTML reporter writes it either way. `trace`/`video` in `playwright.config.js`'s `use` block are both `'on'` rather than the more common `'retain-on-failure'`, specifically so a *passing* run's report is inspectable too: `toHaveScreenshot` itself only attaches its expected/actual/diff triptych when the comparison fails, so without this a green run's report would be a bare list of step titles with nothing to look at. With it, every test — pass or fail — carries a video (a literal recording of that run) and a trace (open in the report's own Trace Viewer for a DOM snapshot, the console and the network at every action), which is what actually answers "what did this test do" rather than only "did it match". Costs ~5.6 MB across all 12 tests — worth revisiting to `'retain-on-failure'` if the suite grows enough for that to matter. `deploy-frontend` gates on `[backend, frontend, visual]`, so a visual diff blocks a deploy from master too — `deploy-backend` deliberately stays at `[backend, frontend]` only, since a screenshot diff has nothing to do with the safety of a backend rollout.

The CI Postgres credentials are chosen independently of `devops/env/develop.env` (a separate, local-only dev credential set) — they only need to be internally consistent between the service container and the job's own env vars.

## Production deployment

Frontend on **Vercel**, backend on **Koyeb**, database on **Neon** (project `calciotto`, `aws-eu-central-1`, branch `production` — the Koyeb region `fra` is Frankfurt too, deliberately, so app-to-database latency stays local). Everything is driven from GitHub Actions: the `deploy-backend` and `deploy-frontend` jobs live in `.github/workflows/ci.yml` rather than in workflows of their own, so that `needs: [...]` is a genuine gate — a failing Go test, Jest test, or (for `deploy-frontend` only, which additionally needs `visual`) a visual regression makes deployment impossible. A separate workflow triggered by `workflow_run` could not promise that, since it fires on *completion* and would need an explicit `conclusion == 'success'` check to avoid deploying a broken build. Both jobs are `if: github.ref == 'refs/heads/master' && github.event_name == 'push'` and target the `production` GitHub environment; a pull request never deploys, and a fork's PR has no access to that environment's secrets anyway.

### Backend (Koyeb)
`devops/Dockerfile.prod.backend` is the deployable image — `devops/dockerfile.dev` runs `air` against a bind-mounted tree and is not. It builds from the **repository root** (it needs `app/`), so `.dockerignore` at the root is what keeps `frontend/node_modules` out of the build context. Two details are load-bearing:
- The runtime stage installs **`ca-certificates`**, which the base `alpine` image does not ship. Both outbound TLS clients need it — Neon refuses plaintext connections, and Brevo's API is HTTPS — and without it the app starts fine and then fails every query and every email with `x509: certificate signed by unknown authority`.
- The build stage is pinned to `golang:1.25-alpine`, matching `app/go.mod`'s `go 1.25.0`. An older base fails outright at `go build`.

The image is tagged with both `${{ github.sha }}` and `latest`, and the **SHA tag is what gets deployed**: `:latest` alone gives no rollback target and does not reliably tell Koyeb that anything changed.

`main.go` gained three deployment affordances:
- `PORT` (default `8080`) instead of a hardcoded `r.Run(":8080")` — the host assigns it.
- `allowedOrigins()` reads `CORS_ALLOWED_ORIGINS` (comma-separated) and falls back to the local dev origins when unset *or* entirely blank. The fallback rather than an empty slice is deliberate: gin-contrib/cors with no allowed origin and `AllowAllOrigins` false rejects every cross-origin request, which would be a silent outage instead of a startup failure.
- `GET /health`, wired as Koyeb's healthcheck (`--checks 8080:http:/health`). It deliberately does **not** touch the database: the platform restarts an instance whose healthcheck fails, so reporting unhealthy on a transient database hiccup (Neon waking from scale-to-zero, a pooler blip) would turn a few slow seconds into a restart loop. `InitDB` already fails fast at startup if the database is unreachable, which is the check that matters.

The route is `/:8080`, **not** `/api:8080`: Koyeb passes the route path through unchanged, so an `/api` prefix would reach Gin as `/api/auth/login` and match none of its routes. The frontend lives on its own domain, so there is no path space to share.

Secrets are synced GitHub → Koyeb by the workflow before each deploy (`koyeb secrets update … --value-from-stdin || koyeb secrets create …` — the CLI has no upsert, and stdin keeps values out of the process argument list), then referenced in the service definition as `--env NAME=@NAME`. GitHub is the source of truth, but Koyeb needs its own copy because these are read at *every container start*, not only at deploy time. `BREVO_API_KEY` is the one optional secret: without it the app keeps logging reset links instead of emailing them (see `internal/services/mailer.go`), a degraded but working state, so the job warns rather than failing.

### Frontend (Vercel)
Deployed by the CLI from Actions, not by Vercel's Git integration — `frontend/vercel.json` sets `"git": {"deploymentEnabled": false}` so a push can't trigger a second, ungated deployment in parallel. The job runs `vercel pull` → `vercel build --prod` → `vercel deploy --prebuilt --prod`, authenticating with `VERCEL_TOKEN` plus `VERCEL_ORG_ID`/`VERCEL_PROJECT_ID` in the environment (which is what replaces an interactive `vercel link`). The Vercel project's **Root Directory must be set to `frontend`**; that is what makes `frontend/vercel.json` the config Vercel reads.

`vercel.json` also carries the SPA rewrite (`/(.*)` → `/index.html`). The router is `createWebHistory`, so without it a refresh on `/profile` or a visit to an emailed `/reset-password?token=…` link returns a Vercel 404. It is expressed as a `rewrite` rather than a `route` precisely because rewrites apply only after the filesystem check, leaving static assets alone.

**The `VUE_APP_` prefix is not cosmetic.** Vue CLI inlines only `VUE_APP_*` (plus `NODE_ENV`/`BASE_URL`) into the client bundle, replacing `process.env` wholesale — see `resolveClientEnv.js` in `@vue/cli-service`. The variable used to be named `VUE_API_BASE_URL`, which meant `process.env.VUE_API_BASE_URL` evaluated to `undefined` and the `http://127.0.0.1:8080` fallback was *always* what shipped. That was invisible locally (the fallback is correct there) and would have shipped a production bundle telling every visitor's browser to call their own machine. It is `VUE_APP_API_BASE_URL` everywhere now: `api.js`, `devops/env/develop.env`, `devops/docker-compose.yaml`.

Because `vercel build` runs the framework build with the environment from `.vercel/.env.production.local` (what `vercel pull` writes) rather than with the job's arbitrary env vars, the workflow **appends** the value to that file after pulling. That keeps GitHub the single source of truth instead of duplicating the setting in the Vercel dashboard.

### Configuration inventory
Set on the `production` GitHub environment. Secrets: `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`, `KOYEB_API_TOKEN`, `DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `JWT_SECRET` (must be generated fresh for production — never the one in `devops/env/develop.env`), `BREVO_API_KEY` (optional), `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`. Variables: `DOCKERHUB_IMAGE`, `CORS_ALLOWED_ORIGINS`, `FRONTEND_BASE_URL`, `VUE_APP_API_BASE_URL`, `BREVO_SENDER_EMAIL`, `BREVO_SENDER_NAME`. The last five are URLs and addresses, not secrets — storing them as variables keeps them readable in build logs, which is what you want when diagnosing a CORS rejection.

The database role in `DATABASE_URL`/`DATABASE_URL_UNPOOLED` must **own** the tables (or be a member of the role that does). `AutoMigrate` issues DDL at *every* boot, so a role with only read/write grants starts fine, reports `Successfully connected to the database!`, and then dies on the first `ALTER TABLE` with `must be owner of table … (SQLSTATE 42501)` — ownership is not a privilege that `GRANT ... ON TABLE` confers. Neon projects come with two roles (here `calciotto_owner` and `calciotto`); the secrets use the owner. The alternative, if you want the app on a non-owner role, is `GRANT calciotto_owner TO calciotto;` — Postgres accepts an ownership check from any *member* of the owning role.

There is **no seeding step in production**: `cmd/seed` is a development tool, and the schema is created by `AutoMigrate` on first boot (through `DATABASE_URL_UNPOOLED`, off the pooler).

## Architecture

### Backend layering
Strict `handlers/` → `services/` → `models/` layering:
- `internal/handlers/*.go` — Gin controllers only: bind JSON, call the service, map errors to HTTP status/JSON. No business logic here.
- `internal/services/*.go` — one service struct per entity (`PlayerService`, `TeamService`, `MatchService`, `MatchPlayerService`, `MatchRegistrationService`, `StandingsService`), each wrapping a `*gorm.DB`.
- `internal/models/database.go` — GORM models (`Player`, `Team`, `Match`, `MatchPlayer`, `MatchRegistration`), all embedding `BaseModel` which generates a `uuid.UUID` ID (`github.com/google/uuid`) in a `BeforeCreate` hook. All FK-style fields (`MatchPlayer.MatchID/TeamID/PlayerID`) are `uuid.UUID`, not `string` — comparisons against "no value" use `uuid.Nil`, not `""`.
- `internal/models/date.go` — `Date` is a `time.Time`-backed type used everywhere a calendar day is stored (`Match.Date`, DTO date fields). It marshals/unmarshals as `"YYYY-MM-DD"` over JSON (matching the original string-based API contract exactly) and scans/values as a SQL `date` column — this is why `Match.Date` could switch from `string` to a typed date without changing the wire format or requiring frontend changes. `DateOf(time.Time) Date` truncates a timestamp to its calendar day **in the timestamp's own location**, which is how `CreateMatch` derives a scheduled match's `Date` from its kick-off: normalizing to UTC first would move a kick-off near midnight onto the adjacent day.
- `internal/models/customModels.go` — DTOs used only for the "match with nested teams/players" API shape (`MatchWithDetails`, `TeamWithPlayers`, `PlayerCustom`) plus a flat row struct (`RowsMatchDetails`) used to scan the raw SQL join in `matches.go`, plus `MatchRegistrationEntry` (one line of a scheduled match's sign-up list, `Position`/`IsWaiting` derived rather than stored). IDs are `uuid.UUID`, dates are `Date`.

`MatchPlayerHandler` exists and is fully implemented in `internal/handlers/` and `internal/services/` but is **not registered as any route** — there is no HTTP path to create or edit a standalone `MatchPlayer` row directly (`MatchService.UpdateMatch`'s diff is the only way `match_players` rows get written). `TeamHandler` is partially wired: `GET /groups/:id/teams` (any member) and `PATCH /groups/:id/teams/:teamId` (admin-only, renames/recolours) exist, but there is still no route to create a standalone `Team` — the only way a `Team` row is created is as one of the two teams `GroupService.CreateGroup` makes alongside a new group.

Every handler that reads an ID from the URL (`c.Param("id")`, etc.) parses it with `uuid.Parse` and returns 400 on failure before calling the service — service methods take `uuid.UUID`, never a raw path string.

### Auth (email/password, JWT) and password reset
`AuthService` (`internal/services/auth.go`) covers the whole credential lifecycle. `POST /auth/signup` is the public "create your account" flow, handled by `AuthHandler.Signup` calling `AuthService.SignupNewPlayer(name, email, password, inviteCode string) (uuid.UUID, error)`: it creates a brand-new `Player` from the submitted name and attaches email/password credentials to it in one step, returning `{"id": ...}` on success. It deliberately never checks `Player.Name` for uniqueness — a display name can legitimately collide with another unrelated player's, and since a player only ever has one account name shared across every group they belong to, per-group uniqueness wouldn't make sense either. This is why `Player.Name` no longer carries a DB-level `uniqueIndex` (see `pkg/database/connect.go`, which explicitly drops the old `idx_players_name` index left over from before this change, since `AutoMigrate` only ever adds schema and never removes an index that's no longer declared). `PlayerService.CreatePlayer` no longer has any duplicate-name check of its own — that global, app-level rejection (`ErrPlayerAlreadyExists`) was removed as a follow-up to this signup feature, since it was inconsistent with `Player.Name` no longer being unique. The admin-created "ghost player" flow now enforces a soft, per-group duplicate guard one layer up instead — see "Input validation" below.

`inviteCode` is the optional fourth parameter that lets signup and "join a group" happen in one step, instead of requiring a separate `POST /groups/join` right after — the `{"invite_code": "..."}` field on the signup request body (`AuthHandler.Signup`'s request struct) is entirely optional and defaults to `""`, preserving the old account-only behavior for anyone who leaves it blank. What makes this safe is that the whole thing — creating the `Player` row and, if a code was supplied, looking up its group and calling `GroupMembershipService.AddPlayerToGroupWithRole(group.ID, player.ID, models.RoleMember)` — runs inside one `s.DB.Transaction`: an unknown or stale code (`ErrInviteCodeNotFound`, mapped to 400 in the handler alongside the pre-existing sentinels) rolls back the `Player` creation too, so a typo'd code can never leave behind an orphaned account with no group, and a valid code can never partially apply. This deliberately does not call `GroupService.JoinByInviteCode` — that method's `IsMember` check is meaningless for a player who was, by construction, just created a moment earlier in the same transaction, and it runs against the service's own `s.DB` rather than the caller's `tx`, which would defeat the atomicity guarantee entirely. Instead the group lookup and `AddPlayerToGroupWithRole` call are inlined directly in `SignupNewPlayer`, both scoped to the transaction's `tx`; the code itself is normalized with the same private `normalizeInviteCode` `JoinByInviteCode` uses, so it's matched the same case-insensitively-trimmed way regardless of which route joins the group. On the frontend, `Signup.vue` gained an optional "Invite code" field (styled like `JoinGroupModal.vue`'s own code input) so a new player can join their group right from the signup form rather than having to separately find "join a group" on their Profile page afterward.

`AuthService.Signup(playerID, email, password) error` is the older "claim by name" flow: it attaches email/password credentials to an *existing* `Player` (it never creates one) and is not wired to any HTTP route today. It's kept for an upcoming "claim an existing ghost player" feature that will reuse it. `Login` returns a 7-day HS256 JWT carrying `player_id`, `ParseToken` is what `AuthMiddleware` calls. All four public entry points (`/auth/signup`, `/auth/login`, `/auth/forgot-password`, `/auth/reset-password`) are wired without `authRequired` — a caller who is signing up or has lost their password has no token to present.

The reset flow is deliberately non-committal about what exists:
- `ForgotPassword(email)` normalizes the email, and returns `nil` for an unknown one — same reasoning as `Login`'s single `ErrInvalidCredentials` for both of its failure modes: the endpoint must not become an email-enumeration oracle. The unknown-email branch still generates (and discards) a token so both branches cost roughly the same time — a best effort at flattening the timing, not a constant-time guarantee. `POST /auth/forgot-password` therefore always answers 200 with one fixed message (`passwordResetRequestedMessage` in `internal/handlers/auth.go`); only a real server-side failure yields 500.
- `ResetPassword(token, newPassword)` collapses *every* token failure — unknown, expired, already used, player since deleted — into the single `ErrInvalidResetToken` → 400. Empty password is `ErrPasswordRequired` (the sentinel `Signup` already uses) → 400.
- A successful reset updates `Player.PasswordHash` **and** marks every unused `PasswordResetToken` of that player as used, in one transaction: requesting a second reset email must not leave the first link live.

`models.PasswordResetToken` stores only the **SHA-256 hex digest** of the raw token, never the token itself. That's a deliberately different choice from `Player.PasswordHash` (bcrypt): a reset token is 32 random bytes, so there is nothing to brute-force and bcrypt's cost buys nothing; a human-chosen password is the opposite case. Raw tokens are `base64.RawURLEncoding` so they drop straight into a query string, and live one hour (`passwordResetTTL`).

**Email transport is optional and env-gated.** `sendPasswordResetLink` (`internal/services/auth.go`) branches on `BREVO_API_KEY`: unset (the default — nothing in `devops/env/develop.env` or CI sets it), it only `log.Printf`s the link (`<FRONTEND_BASE_URL>/reset-password?token=...`, `FRONTEND_BASE_URL` from the env with a `http://localhost:4000` fallback), the way Rails/Django development mailers do — until then the link is readable by anyone with access to the server logs. The integration tests read the token back out of that log line (`log.SetOutput` into a buffer, `strings.Cut` on `"?token="`), since it's the only place the raw value ever exists in this mode — this is exactly why the log-only path had to stay byte-for-byte unchanged when Brevo support was added. Set, it instead calls `sendViaBrevo` (`internal/services/mailer.go`), which POSTs to Brevo's transactional email API (`https://api.brevo.com/v3/smtp/email`, header `api-key: <BREVO_API_KEY>`) with a sender read from `BREVO_SENDER_EMAIL` (required alongside the key — must be a sender verified in the Brevo account; `BREVO_SENDER_NAME` optionally overrides the display name, default `"Calciotto"`). Either mode is fire-and-forget from the caller's perspective — `ForgotPassword`/`InviteExistingPlayer` have already committed the token to the DB by the time this runs, so a delivery failure (including a quota breach — Brevo's free tier caps at 300 emails/day and returns a non-2xx with a `{"code": "...", "message": "..."}` body once exhausted) is only logged (`[password reset] failed to email %s via Brevo: %v`), never surfaced to the HTTP caller or retried.

This same token type has a **second producer**: `AuthService.InviteExistingPlayer(playerID, email)`, backing the admin-only `POST /groups/:id/members/:playerId/invite`, which attaches an email to a credential-less "ghost" player and issues them a link to set their first password. `ForgotPassword` and `InviteExistingPlayer` differ only in how they establish that the caller may set that player's password (knowing the email vs. being an admin of one of the player's groups) — they share the private `issuePasswordResetToken(db, playerID)` helper and the same `sendPasswordResetLink` stub, and both are consumed by the one `POST /auth/reset-password`. See "Group bootstrapping" below for the authorization side and the `ErrPlayerAlreadyClaimed` guard.

**Known limitation:** resetting a password does **not** revoke JWTs already issued to that player. There is no revocation mechanism anywhere in this system — no token blacklist, no per-player token version, no session table — so a stolen token stays valid until it expires naturally (7 days, `tokenTTL`), reset or no reset. Logging out is purely client-side (`clearToken()` in `api.js`). Fixing this means adding real revocation (e.g. a `token_version` on `Player` checked in `ParseToken`), which is out of scope of the reset flow itself.

**Rate limiting** (`internal/handlers/ratelimit.go`) covers exactly the four `/auth/*` routes above, and nothing else in the app. Every other unauthenticated route (`GET /groups`, `GET /groups/:id`) is read-only public data behind a DTO with no per-caller cost to amplify, and every route with a real cost requires `authRequired` — these four are the whole unauthenticated attack surface. `GET /players` and `GET /players/search` used to be the other two: unauthenticated and, worse, letting anyone enumerate every player's name and id system-wide with no group scoping at all. Neither was actually called from the frontend any more (`MatchDetails.vue` moved to the group-scoped `getGroupMembers` — see "Frontend" below), so they were removed outright rather than gated, closing the enumeration surface with nothing to migrate. `RateLimit(r rate.Limit, burst int)` (`golang.org/x/time/rate`) is a per-client-IP token bucket — one `*rate.Limiter` per distinct `c.ClientIP()`, held in an `ipRateLimiter` map that a background goroutine sweeps every `ipRateLimiterIdleTTL` (2 hours) so a public endpoint's IP set doesn't grow the process's memory forever. Each of the four routes in `main.go` gets its own instance (its own map, its own budget) rather than sharing one: `Login` (~10/min, burst 10) is the main target — bcrypt already slows down one guessed password, but not a script making thousands from one IP — while `Signup`/`ForgotPassword`/`ResetPassword` (~5/hour, ~5/hour, ~20/hour) are throttled mainly so none of them can be turned into a spam or cost vector (`ForgotPassword` in particular shares a budget with Brevo's 300-email/day free tier, see "Production deployment" above). This is IP-level and deliberately coarse — it does not distinguish a wrong password from a right one, so a legitimate user mistyping their password a few times shares the same budget as an attacker, which is why the burst is generous rather than tight. It is also **not** a substitute for the missing account lockout/2FA a larger app might want; it only bounds how fast one IP can try.

### Group bootstrapping (invite codes and roles)
Every group carries an `InviteCode` (`models.Group`, 8 characters over an alphabet with no `0/O/1/I/L`, `uniqueIndex`, `json:"-"`), generated by `GroupService.CreateGroup`, which stays agnostic about who created the group. `CreateGroup(name string, teams [2]TeamSpec) (*models.Group, error)` takes the group's own name plus exactly two `TeamSpec{Name, Colour}` values — one per team — instead of hardcoding a black/white default: there's no reasonable team name to invent on the caller's behalf, so the caller (the admin creating the group, via `POST /groups`'s request body) has to supply both. This is a deliberate break from an earlier version of this doc that said `CreateGroup(name string)` "keeps its signature so `cmd/seed` still works" — that constraint no longer holds, since `cmd/seed` now passes `services.DefaultTeamSpecs` (`{Name: "Black", Colour: "black"}, {Name: "White", Colour: "white"}`) explicitly, the same default most integration tests reach for when the team name/colour don't matter to the scenario under test. Both fields are validated non-empty (after trimming) inside the same transaction that creates the group and its teams, via `ErrTeamNameRequired`/`ErrTeamColourRequired` (`internal/services/groups.go`, same sentinel style as `PlayerService.ErrEmptyPlayerName`) — mapped to 400 in `GroupHandler.CreateGroup`, which also 400s upfront if the request's `teams` array isn't exactly length 2. The flow `CreateGroup` enables:

1. `POST /groups` is `authRequired` (no `requireGroupMember` — there is no group to be a member of yet). `GroupHandler.CreateGroup` creates the group, then adds the JWT's player as its first member via `GroupMembershipService.AddPlayerToGroupWithRole(..., models.RoleAdmin)` — the same handler-does-the-membership split as `PlayerHandler.CreatePlayer`. Without that, a new group could never gain a member: `POST /groups/:id/players` requires membership of the target group; and without the *admin* role specifically it could never gain an admin either, since promoting a member is itself admin-only.
2. `POST /groups/join` (`authRequired` only, for the same reason — the caller is by definition not a member yet) takes `{"invite_code": "..."}`. `GroupService.JoinByInviteCode` normalizes the code to upper case (like `normalizeEmail` in `AuthService`), returns `ErrInviteCodeNotFound` → 404 for an unknown or empty code, `ErrAlreadyMember` → 400, else enrolls the player (as `models.RoleMember`, via the plain `AddPlayerToGroup`) and returns the group.
3. `GET /groups/:id/invite-code` (`authRequired` + `requireGroupMemberByPathID`) is the **only** place the code is exposed — `Group.InviteCode` has `json:"-"` so the public `GET /groups` and `GET /groups/:id` never leak it, not even to a member. There's an integration test asserting exactly that.

4. `GET /groups/me` (`authRequired` only) returns `GroupMembershipService.GetGroupsWithRoleByPlayerID` for the JWT's player — the list the `/groups` view is built on. The public `GET /groups` can't serve that: it lists every group in the system and, being unauthenticated by design, can't be narrowed nor carry a role. Each entry is a `models.GroupWithRole` (`customModels.go`) — `Group` embedded plus the **caller's own** `role` — so a client can tell where it may act as an admin without one member-only request per group; embedding keeps the JSON flat and keeps `Group.InviteCode` behind `json:"-"`. `GetGroupsByPlayerID` is untouched and still used by `StandingsService.GetPlayerProfile`, which has no use for the role. The handler normalizes GORM's nil slice to `[]` so a player belonging to no group gets an empty array rather than `null`.
5. `GET /groups/:id/players` (`authRequired` + `requireGroupMemberByPathID`, open to any member — seeing the roster isn't privileged, only acting on it is) returns `[]models.PlayerWithRole` via `GroupMembershipService.GetPlayersWithRoleByGroupID` — the same "embed the base type, add a `Role` field" pattern as `GroupWithRole`, just embedding `Player` instead of `Group`, so its JSON keeps `Player`'s own lowercase convention (`id`, `name`, `email`) with `role` riding alongside. `GetPlayersByGroupID` (no role) is untouched — it's still used by `HasMemberNamed`'s duplicate-name check, `StandingsService.currentMemberIDs` (see "Standings" below), and a few integration tests that have no use for the role.

**Favorite group** — `GroupMembership.IsFavorite bool` (`json:"-"`, exposed instead via `GroupWithRole.IsFavorite` on `GET /groups/me`) marks which one of a player's groups the frontend's `resolveActiveGroup()` falls back to on a fresh device or right after logging in, instead of an arbitrary "first group" ordering. Every player who belongs to at least one group always has exactly one favorite:
- `AddPlayerToGroupWithRole` grants it automatically to a player's very first membership ever (counts existing memberships first; zero means this one becomes the favorite) — covers `POST /groups`, `POST /groups/join`, and the admin-created "ghost player" flow, since all three eventually call it.
- `PATCH /groups/:id/favorite` (`authRequired` + `requireGroupMemberByPathID` — a personal preference, not an admin action) → `GroupHandler.SetFavoriteGroup` → `GroupMembershipService.SetFavoriteGroup(playerID, groupID)`, which unsets the caller's current favorite and sets the new one in one transaction. This is the only way the flag moves without a membership being deleted.
- `LeaveGroup` and `RemoveMember` both call the private `reassignFavorite` helper when the membership row they just deleted held the flag — it promotes the player's oldest remaining membership (by `CreatedAt`, same ordering as `GetFirstGroupForPlayer`), or does nothing if none are left. Without this, a player could end up with zero favorites just by leaving (or being removed from) their favorited group, breaking the "always exactly one, as long as you belong to at least one group" invariant everywhere else relies on.
- A one-time backfill in `pkg/database/connect.go` (next to the existing `role = 'owner'` rewrite) handles the migration case: `AutoMigrate` adds the column with its declared default (`false`) for every existing row, which would otherwise leave every pre-existing player with zero favorites. It promotes each player's oldest membership, guarded by `NOT EXISTS (... is_favorite = true)` so it's a no-op on every startup after the first.

`GroupMembership.Role` (`models.RoleAdmin` = `"admin"` / `models.RoleMember` = `"member"`, a plain string like `Team.Colour` rather than a dedicated enum type) separates a group's admins from its plain members. A group can have **several** admins: its creator is the first, and any admin can promote or demote another member. Everyone else added via invite code or `POST /groups/:id/players` goes through the plain `AddPlayerToGroup`, which defaults to `RoleMember`. The one invariant, enforced on both sides, is that **a group with at least one member always has at least one admin**: `LeaveGroup` promotes the oldest remaining member when the *last* admin leaves (and does nothing when another admin remains), and `UpdateMemberRole` refuses to demote the last admin (`ErrLastAdmin`).

`RequireGroupAdmin`/`RequireGroupAdminByPathParam` (`internal/handlers/groupadmin.go`) mirror `RequireGroupMembership`/`RequireGroupMembershipByPathParam` exactly — body/query resolution via `resolveGroupIDForMembership` for the first, URL param for the second — but check `GetRole(...) == models.RoleAdmin` instead of `IsMember`, and answer 403 identically for "member but not admin" and "not a member at all", so the middleware can't be used to probe group membership. They gate five routes: `DELETE /groups/:id/members/:playerId` and `PATCH /groups/:id/members/:playerId/role` (path param), and `POST /matches` / `PUT /matches/:id` / `DELETE /matches/:id` (body/query, since those carry `group_id` in the payload — a `DELETE` has no body, so it's carried in the query string only, which `resolveGroupIDForMembership` already handles). **Reading** matches and standings stays open to any member and keeps `requireGroupMember`.

`PATCH /groups/:id/members/:playerId/role` takes `{"role": "admin"}` or `{"role": "member"}` and is the only way a group gains an admin besides its creator. `GroupMembershipService.UpdateMemberRole(groupID, actingPlayerID, targetPlayerID, newRole)` holds the rules, mirroring `RemoveMember`'s shape: any other role value is `ErrInvalidRole` → 400; targeting yourself is `ErrCannotChangeOwnRole` → 400 (there is no self-service "step down" — an admin who wants out uses `LeaveGroup`, which hands the role over for them); a target who isn't a member propagates `gorm.ErrRecordNotFound` → 404; demoting the last admin is `ErrLastAdmin` → 400; and setting the role the target already has is a **successful no-op**, so a retried request never fails for nothing. `ErrLastAdmin` is unreachable through the HTTP route (the acting admin is themselves an admin and can't be the target, so another admin always survives) — it's a service-level safety net, and its test calls the service directly. Note `PATCH` had to be added to the CORS `AllowMethods` list in `main.go`, which previously only allowed GET/POST/PUT/DELETE.

`POST /groups/:id/members/:playerId/invite` (`authRequired` + `requireGroupAdminByPathID`, `GroupHandler.InvitePlayer`) closes the loop on the admin-created "ghost player": it takes `{"email": "..."}`, attaches that email to a member who has none, and sends them a link to set their own password — turning a roster entry into a real account without the player ever having to sign up separately (their match history is already attached to that `Player` row).

It **reuses the password-reset machinery verbatim** rather than introducing a claim-specific token type: `AuthService.InviteExistingPlayer(playerID, email)` calls the same `issuePasswordResetToken` helper `ForgotPassword` does (extracted so both share it) and the same `sendPasswordResetLink` log-stub, so the link is an ordinary `<FRONTEND_BASE_URL>/reset-password?token=...` consumed by the existing `POST /auth/reset-password`. Nothing new is needed on the consuming side because `ResetPassword` overwrites `Player.PasswordHash` **unconditionally** — it never asks whether a password was there before — and `ResetPassword.vue`'s existing copy already reads correctly for a first password. Hence **no frontend change at all** for this feature. The email-attach and the token creation run in one `s.DB.Transaction`, with the link sent only after it commits: a player left with an email but no outstanding invite would be a dead end (they can't log in, and a retry would now hit `ErrPlayerAlreadyClaimed`).

Two guards, both reusing existing sentinels rather than new ones:
- **`ErrPlayerAlreadyClaimed` → 400** when `player.Email != nil`. This path must never rewrite a live account's email — that would be an account-takeover vector, and "change my email" is an unrelated feature that doesn't exist. It also means an invite can't be re-issued once claimed; a player who then forgets their password uses `POST /auth/forgot-password` like anyone else. `ErrEmailAlreadyUsed` → 400 (another player holds that address) and `ErrEmailRequired` → 400 round out the mapping; `ErrPlayerNotFound` → 404 is kept defensively although the `IsMember` check below already proves the row exists.
- **An explicit `h.MembershipService.IsMember(groupID, targetPlayerID)` check in the handler, 404 otherwise** (reusing `RemoveMember`'s "player is not a member of this group" message). `RequireGroupAdminByPathParam` only establishes that the *caller* is an admin of `:id`; it says nothing about `:playerId`. Without this check an admin of group A could hand an email — and therefore an account — to any player id in the system, including one belonging solely to group B. Like the `uuid.Parse` calls, it's request validation guarding the route's authorization, not business logic, so it belongs in the handler.

`GroupHandler` therefore takes `*services.AuthService` as a third constructor dependency (`NewGroupHandler(groupService, membershipService, authService)`) — credentials live in `AuthService`, not `GroupService`, so the handler composes the two rather than either service reaching into the other.

`Profile.vue` has a frontend for the promote/demote/remove half of member management, and for inviting a "ghost" player by email (`POST /groups/:id/members/:playerId/invite`) — both described in "Frontend" below (this used to be `Groups.vue`, since folded into Profile — see that section for why). Out of scope still: regenerating a compromised code, and any role beyond admin/member.

Groups created **before** this change keep `invite_code = NULL` — Postgres treats NULLs as distinct in a unique index, so `AutoMigrate` adds the column and index without complaint, but those legacy groups can't be joined by code and `GET /groups/:id/invite-code` reports `""` for them. Reseed (`go run ./cmd/seed -reset`) or backfill by hand to give them one.

The role rename carries the same "AutoMigrate never rewrites data" hazard, and is handled explicitly: `pkg/database/connect.go` runs `UPDATE group_memberships SET role = 'admin' WHERE role = 'owner'` after `AutoMigrate`, next to the older `DROP INDEX IF EXISTS idx_players_name` step. Without it every group created before the rename would keep `role = 'owner'`, which no longer matches `models.RoleAdmin`, and its creator would be locked out of every admin-gated action with no admin left able to grant it back. The statement is idempotent — after the first startup there are no `'owner'` rows left.

Any group created by calling `GroupService.CreateGroup` directly instead of going through `POST /groups` gets no admin from the HTTP flow, since `POST /groups` is the only place `RoleAdmin` is assigned there. That used to be a harmless gap for the "Default" group in `cmd/seed/main.go`; now that admin gating is actually enforced, a group with no admin is a group where nobody can create a match or edit a score. The seed script therefore adds its **first** player (`thibaut`) with `AddPlayerToGroupWithRole(..., models.RoleAdmin)` and everyone else as a plain member. Any *other* group built the same way still needs a backfill by hand.

### Data model
`MatchPlayer` is the join table that carries both roster membership *and* the score: `(match_id, team_id, player_id, goals_scored)`. There's no separate "goals" or "events" table — a team's score is always derived by summing `goals_scored` over its players.

`Match` carries four **nullable** scheduling columns alongside `Date` — `ScheduledAt`, `RegistrationOpensAt`, `RegistrationsClosedAt` (all `timestamptz`, since a kick-off is an instant and not a calendar day) and `MaxPlayers` — and `MatchRegistration` is a second join table holding one row per sign-up, `(match_id, player_id)` under a composite `uniqueIndex` (which is what makes a double-clicked "Participate" harmless) plus a `CreatedAt` that *defines* the waiting list. Both are covered in "Scheduled matches and sign-ups" below. A match is scheduled iff `ScheduledAt` is set — use `Match.IsScheduled()` rather than scattering nil checks — and all-`NULL` is exactly the state every match predating the feature is in, which is why `AutoMigrate` needed no backfill for them, unlike `GroupMembership.IsFavorite` whose non-null `default:false` broke an invariant and had to be repaired in `connect.go`.

`Match.CreatedAt` (a plain, non-nullable `time.Time`, GORM's usual auto-populate-on-create convention — the same as `MatchRegistration.CreatedAt`/`MatchVote.CreatedAt`) was added later, originally purely for the Man of the Match voting window (see below) to anchor on for a match with no kick-off at all — the voting window has since moved to a simpler `Date`-based rule that needs neither this nor `ScheduledAt`, so this field is currently unread by that feature (or any other), kept as plain metadata rather than removed. Unlike the four scheduling columns, this one **did** need a backfill: `matches` already had rows when the column was added, `AutoMigrate` gives it no default, and GORM errors scanning a `NULL` column into a non-pointer `time.Time` field on every later read of a row that predates it. `connect.go` backfills every `NULL` to `date::timestamptz` (the closest available stand-in for "when this was created" — not the real instant, but close enough for a row that's necessarily already years past any voting window either way), the same "repair the invariant a new non-null-shaped column broke" move as the `IsFavorite` backfill just above it, just for a genuine scan error instead of a business-logic one.

`Team` carries both a `Name` (the display name an admin picks at group creation, e.g. "Les Rouges") and a `Colour` (`gorm:"type:string" json:"colour"`, the swatch key the frontend's `getTeamColor()` palette maps to a hex code — `red`/`blue`/`green`/`yellow`/`purple`/`orange`/`pink`/`cyan`/`white`/`black`). The two are independent: a team can be named "Les Rouges" and coloured `blue`. Every group has exactly two teams, created together with the group (see "Group bootstrapping" below) and renameable/recolourable afterwards via `PATCH /groups/:id/teams/:teamId` (`TeamHandler.UpdateTeam` → `TeamService.UpdateTeam`, admin-only, scoped to `(team_id, group_id)` in one query so a team belonging to a different group reads as 404 rather than being silently updatable).

### The flatten/reconstruct pattern (matches.go)
`MatchService.GetMatchesDetails` / `GetMatchDetailsByID` do not use GORM associations or `Preload`. They run a raw SQL query with `LEFT JOIN`s across `matches → match_players → teams/players`, scan into flat `RowsMatchDetails` rows, then manually rebuild the nested `MatchWithDetails{ Teams: []TeamWithPlayers{ Players: []PlayerCustom } }` structure in Go (matching by ID in loops, appending as new IDs are encountered). When a match has no rows in `match_players` for a given team (or at all), there's a fallback path that queries all `teams` directly to still return empty team shells. Any change to the JSON shape returned to the frontend needs to touch both the SQL query and this reconstruction loop, not just the model struct — `TeamWithPlayers.Name` (added alongside the pre-existing `Colour`) is a worked example: it required adding `teams.name as team_name` to both `SELECT`s, `TeamName` to `RowsMatchDetails`, and setting `Name` at all four `models.TeamWithPlayers{...}` construction sites (two "get or create this team while scanning rows", two "backfill a team with no roster yet" — one pair per function). The pre-existing sort-by-colour (`match.Teams[i].Colour < match.Teams[j].Colour`) is unrelated to this and untouched — it's about deterministic ordering, not display.

The scheduling fields are the second worked example, and the instructive one is the field that *isn't* in the join. The four `matches.*` scheduling columns were added to both `SELECT`s, to `RowsMatchDetails`, and to the two `models.MatchWithDetails{...}` construction sites (one per function; row 0 is as good as any, since the `Match*` columns repeat identically on every row of a match — including the single all-NULL-team row of a match with no roster yet, which is the *normal* state of a scheduled match). But `RegistrationCount` deliberately does **not** come from there: `match_registrations` is a second one-to-many on `matches`, so joined alongside `match_players` it would multiply the rows (one per sign-up × one per assigned player) and silently corrupt every `Score` and goal total in this file, all of which are derived by summing those rows. It's fetched by a separate grouped count instead — `registrationCountsByGroup` for the list, `registrationCount` for the single match, both on the GORM query builder rather than raw SQL, since the group scope is a subquery and no joined columns are needed. `GetMatchesDetails` skips that second round-trip entirely unless at least one scanned row has a non-nil `scheduled_at`, which is what keeps it free for every group predating the feature — and this is also the function all four `StandingsService` calls go through, so an unconditional extra query would be charged to every standings request for nothing.

`Match.CreatedAt` is a third, smaller worked example of the same pattern (`matches.created_at as match_created_at` in both `SELECT`s, `MatchCreatedAt` on `RowsMatchDetails`, `CreatedAt` set at both `models.MatchWithDetails{...}` construction sites) — originally added so the frontend could compute the Man of the Match voting window's own anchor for an unscheduled match without a second request; the voting window is Date-based now (see "Man of the Match voting" below) and no longer needs it, but it's still exposed on the DTO as ordinary metadata. Unlike the scheduling fields it carries no `omitempty` on the DTO: every match has a `CreatedAt`, so there is no "doesn't apply" case to keep an old client from seeing.

`MatchService.UpdateMatch` performs a diff: for each team in the incoming payload it loads existing `MatchPlayer` rows for that `(match_id, team_id)`, creates rows for players not yet present, updates `goals_scored` for players still present, and deletes rows for players removed from the payload. The whole diff runs inside `s.DB.Transaction(...)`.

`MatchService.DeleteMatch(matchID, groupID)` backs `DELETE /matches/:id` (admin-only, `requireGroupAdmin`, same as create/update): it scopes its lookup to `WHERE id = ? AND group_id = ?` exactly like `GetMatchDetailsByID` — a match ID from another group reads as `ErrMatchNotFound` rather than being reachable — then, inside a transaction, deletes every `MatchPlayer` row for that match before deleting the match itself. That ordering is required, not just tidy: `MatchPlayer.MatchID` has a plain FK to `matches(id)` with **no `ON DELETE CASCADE`**, so deleting a match that still has roster rows fails with a database constraint error unless they're removed first. `MatchHandler.DeleteMatch` resolves `group_id` via the same query-param-or-caller's-first-group logic as the read handlers (`resolveGroupID`) — deliberately the same group `requireGroupAdmin`'s `resolveGroupIDForMembership` already authorized against, since resolving a different one in the handler would let an admin of group A delete a match in group B. On success it responds `{"deleted": true}`, the same convention as `LeaveGroup`'s `{"left": true}`/`RemoveMember`'s `{"removed": true}`. The same transaction also deletes the match's `MatchRegistration` and `MatchVote` rows — nothing *forces* either one, since neither declares an association on `Match` and there's no FK to violate, but leaving a deleted match's sign-up list or Man of the Match votes behind would be dead rows nothing can ever read or clean up again.

### Scheduled matches and sign-ups
A match can be **scheduled**: created for a future kick-off, with a sign-up list members add themselves to and a waiting list past a maximum number of players. The whole feature is additive — a match created with none of the scheduling fields behaves exactly as it always did (an admin records a game already played and scores it right away) and serializes to byte-for-byte the same JSON, since every scheduling field on `MatchWithDetails` carries `omitempty` so a client that knows nothing about scheduling sees no new keys at all.

Four product decisions shape the implementation, each one removing machinery a reader might otherwise go looking for:
- **Two distinct timestamps.** `RegistrationOpensAt` is when the sign-up button goes live, `ScheduledAt` is kick-off. A single field couldn't express "opens Friday, played Sunday".
- **The admin closes sign-ups manually**, in order to *then* compose the teams — hence `RegistrationsClosedAt` as a nullable timestamp rather than a bool: `NULL` means open, a value records when they were closed, and clearing it re-opens them after a mis-click. Kick-off is a hard backstop regardless.
- **The waiting list is derived, never stored.** No status column, no promotion job: sign-ups are ordered by `CreatedAt`, the first `MaxPlayers` are confirmed and the rest are waiting. A withdrawal is then a plain row delete that mechanically promotes the next player with no race to lose, and lowering `MaxPlayers` rolls the tail of the list into the waiting list for free.
- **A sign-up is not a `MatchPlayer` row.** Beyond a `MatchPlayer` needing a `TeamID` and a goal count that don't exist yet when a player merely says they'll come, `ComputePointsStandings` treats any match whose two teams both have players as played — so recording sign-ups there would make next Sunday's match appear in the standings as a 0-0 draw.

**Creating one.** `CreateMatch(spec MatchSpec, groupID uuid.UUID)` takes a `MatchSpec` struct rather than a growing positional parameter list, the same call shape as `CreateGroup`'s `TeamSpec`. `spec.validate()` treats the three client-supplied scheduling fields as **all-or-nothing** — none (an ordinary match) or all three, else `ErrIncompleteSchedule`, since half a schedule has no defined behaviour at all — plus `ErrRegistrationOpensAfterKickoff` (a window opening at or after kick-off could never be used, given that kick-off closes sign-ups) and `ErrInvalidMaxPlayers` for a non-positive roster size (which would bench every single sign-up). All three map to 400 in `MatchHandler.CreateMatch`. A `ScheduledAt` in the past is deliberately *not* rejected: backfilling a match that already happened is legitimate, and the unscheduled flow has always accepted any date.

`POST /matches` binds into a dedicated `createMatchRequest` struct instead of `models.Match` (the same choice the auth handlers already make). That's what makes `registrations_closed_at` unrepresentable at creation — "sign-ups closed before anyone could make one" is not an admin action that exists — rather than something a later filter has to remember to strip. Its timestamps are plain `*time.Time`, so `encoding/json` parses them as RFC3339 and keeps **the offset the client sent**; that is load-bearing and must not be "normalized" to UTC, because a scheduled match's `Date` is *derived* from `ScheduledAt` via `models.DateOf` in the kick-off's own location, so a 21:00 Paris kick-off keeps the calendar day — and therefore the season — the client meant. `Date` stays the single write path for the day (seasons, ordering and the existing JSON contract are all built on it), which is why a caller can't supply both and have them drift apart.

**Routes**, all five `authRequired` and all in `main.go`:
- `POST /matches/:id/registrations` (any member) — signs the **caller** up; answers with their resulting `MatchRegistrationEntry`.
- `DELETE /matches/:id/registrations` (any member) — withdraws the caller's own sign-up.
- `GET /matches/:id/registrations` (any member) — the ordered list; seeing who's coming isn't privileged, only closing it is.
- `POST /matches/:id/registrations/close` → `{"closed": true}` and `POST /matches/:id/registrations/reopen` → `{"reopened": true}` (admin only, like every other write on a match).

The player always comes from the JWT, never from the body or the path: there is no "register someone else" capability, and taking a player id from the request would silently create one. That's also why the `DELETE` has no `/me` suffix — a suffix would imply an alternative target that doesn't exist. `Register` answers with the caller's entry rather than a bare `{"registered": true}` because *reaching the cap is not an error*: the surplus sign-up succeeds and lands on the waiting list, so that response is the only place a client can learn "you are #17, you're on the bench". The position is read back from `ListRegistrations` rather than guessed from a count, since position and waiting status are properties of the whole ordered list.

**A third way of resolving the group** (`internal/handlers/matchscope.go`) exists for these routes, and it's the security-relevant part of the feature. `RequireGroupMembershipByMatchPathParam` / `RequireGroupAdminByMatchPathParam` derive the group from the *match* named in the path (`MatchService.GetGroupIDByMatchID`) and authorize against that one. Neither pre-existing pair fits: `RequireGroupMembership`/`RequireGroupAdmin` resolve the group from a query param, the JSON body, or — failing both — the caller's own first group, which used here would be a genuine hole, since the path names a match and a member of group A could act on group B's match just by supplying their own group id (or none at all); and `...ByPathParam` reads a group id straight from a path that doesn't carry one. They also differ from the four older middlewares in one deliberate way: they **publish** the group they authorized into the Gin context (`authorized_group_id`, read back with `authorizedGroupIDFromContext`, the way `AuthMiddleware` publishes `player_id`), and the two admin handlers read it back instead of resolving a group themselves. That saves a duplicate lookup, but the real reason is structural — it makes "an admin of group A acting on a match in group B" impossible to express, which is exactly the bug `MatchHandler.DeleteMatch` still has to avoid by hand.

Status codes are chosen to keep match ids unenumerable. A caller who isn't a member gets **404** "match not found", identical to a genuinely unknown id and emitted from one shared `abortMatchNotFound` so the two wordings can't drift apart either — a 403 would confirm the match exists, and anyone could then enumerate other groups' match ids by watching the status flip. A member who merely isn't an admin gets **403**, because they can already read the match through `GET /matches/:id/details`, so there's nothing left to hide. Beyond authorization, `respondMatchRegistrationError` maps `ErrMatchNotFound` → 404, `ErrMatchNotScheduled` → **400** (a match with no schedule has no sign-up list at all: malformed request, not a state to retry) and the four state conflicts — `ErrRegistrationsNotOpenYet`, `ErrRegistrationsClosed`, `ErrAlreadyRegistered`, `ErrNotRegistered` — → **409**.

`MatchRegistrationService` keeps the policy in two package-level pure functions, the same split as `ComputePointsStandings` versus its data loading, so the whole thing is unit-testable without a database:
- `RegistrationWindowError(match, now)` is the entire "is this list open" rule, and **both** `Register` and `Unregister` call it — withdrawing is gated on the same window as signing up, because once the admin has closed the list the roster is being turned into teams, and once the match has kicked off the list is history (a player who wants out after that talks to an admin). `ErrRegistrationsClosed` covers both ways sign-ups stop, an explicit close *and* kick-off having passed: the refusal and the remedy are identical from the caller's side, so splitting them would leak scheduling detail without changing anything a client could do. It's `!now.Before(*ScheduledAt)` rather than `After`, so kick-off itself is closed. `RegistrationOpensAt` is nil-guarded rather than dereferenced — `CreateMatch` guarantees it, but a row hand-crafted in SQL might not, and "no stated opening time" is best read as open since creation.
- `ComputeRegistrationPositions(entries, maxPlayers)` numbers an already-ordered list 1-based and flags the tail beyond `maxPlayers` as waiting (a nil `maxPlayers` means no cap, so nobody waits). The ordering itself is `ListRegistrations`' job and is **total**: `created_at ASC, id ASC`. The tie-break is not decoration — two sign-ups landing in the same microsecond would otherwise be ordered arbitrarily by the database, and right at the confirmed/waiting boundary that could swap the last confirmed player and the first reserve between two reads of unchanged data.

`Register` checks for an existing sign-up rather than leaving it to the composite unique index, so the caller gets a clean `ErrAlreadyRegistered` instead of a driver-level constraint error — the index is still the real guarantee under a concurrently double-clicked button. `CloseRegistrations`/`ReopenRegistrations` scope their lookup to `(match_id, group_id)` exactly as `DeleteMatch` does, and are both **no-op successes** when the match is already in the target state: same reasoning as `UpdateMemberRole` setting a role a member already holds — a retried request must not fail for nothing, and the *first* close's timestamp is the one worth keeping. Re-opening writes `NULL` through a `map[string]any`, since GORM skips zero values passed to `Updates` as a struct. It's allowed even after kick-off, where it simply has no effect (the backstop still refuses every sign-up) — refusing it there would add a rule that protects nothing. `ListRegistrations` treats an unscheduled match as an empty list rather than an error, unlike `Register`, so a caller doesn't have to know about scheduling just to render a match.

The service deliberately does **not** check that the player belongs to the match's group: that's authorization, enforced one layer up by the route, exactly as `MatchService` relies on `requireGroupAdmin` instead of re-checking roles itself.

### Man of the Match voting
Any group member can vote for who they thought was best in a match once its roster is composed — an ordinary already-recorded match, or a scheduled one after "Fill teams from sign-ups"/manual composition. It deliberately reuses as much of the sign-up feature's shape as it can (the match-scoped middleware, the derive-don't-store philosophy, the tie-inclusive-award pattern already established by `ComputeRegistrationPositions`), while diverging from it in the two places the product is actually different: voter eligibility, and what a repeated action means.

`models.MatchVote` (`(match_id, voter_id, voted_for_id)`) is the join table, with a composite `uniqueIndex` on `(match_id, voter_id)` — **not** "at most one sign-up" the way `MatchRegistration`'s identical-looking index is, but "exactly one *current* vote per voter per match". That difference in meaning is the whole feature:
- **Voting is an upsert, not a one-shot action.** `MatchVoteService.Vote(matchID, voterID, votedForID)` replaces an existing vote from the same voter rather than rejecting a second call with something like `ErrAlreadyRegistered` — a player changing their mind about who deserves MOTM, before or after the final whistle, is the ordinary case here, not a mistake to refuse. `POST /matches/:id/votes` therefore always answers 200 with the resulting tally, never a 409 for "you already voted".
- **Voter eligibility is broader than "played in the match".** Any group member can judge, including a sub who never got on or a member who only watched — the route only requires `RequireGroupMembershipByMatchPathParam`, the exact same middleware the sign-up routes use, with no admin-only route anywhere in this feature (unlike sign-ups' Close/Reopen). The *candidate*, on the other hand, must actually be on the roster: `playerOnRoster` checks for a `MatchPlayer` row on either team, and voting for a real group member who simply never played in this match is `ErrVotedForPlayerNotOnRoster` → 400. Self-votes are also rejected outright (`ErrCannotVoteForSelf` → 400) — there is no legitimate self-nomination for "best player on the pitch". Both are 400s rather than 409s, unlike the sign-up window's state conflicts: whether the voter is themselves, and whether the candidate is on the roster, are true or false regardless of timing, so there is nothing to retry into validity the way a closed sign-up window eventually reopens.
- **There is still no admin close/reopen** — nobody manually freezes voting the way sign-ups are closed. What voting *does* have, added after real product feedback, is a fixed 24-hour window (below); once that has elapsed there is nothing left to reopen, unlike sign-ups.
- **The award is derived, never stored**, mirroring the waiting list's own choice: there is no "winner" or "award" column anywhere. `ComputeMotmWinners(tally []models.MatchVoteTally) []uuid.UUID` is the entire rule, kept as a pure function of an already-computed tally (unit-tested without a database, the same split as `ComputeRegistrationPositions`): find the max vote count, return every candidate at that count. **Ties are inclusive by product decision** — a three-way tie makes three Men of the Match for that game, not one picked arbitrarily. An empty tally (nobody voted, or every vote was later withdrawn) returns no winners at all, not a default.

**The voting window.** Casting, changing, or removing a vote is only allowed through the calendar day *after* the match was played — reading the tally never is (see `GET` below). `VotingWindowError(match models.Match, now time.Time) error` (`internal/services/matchVotes.go`) is that entire rule, mirroring `RegistrationWindowError`'s own split between a pure window-check function and its thin callers (`Vote`/`Unvote`), so it's unit-tested without a database exactly the same way. The rule is deliberately **Date-based**, not instant-based, and identical for a scheduled or an unscheduled match: `deadline := time.Time(match.Date).AddDate(0, 0, 2)`, closed once `!now.Before(deadline)`. A match played September 3rd accepts votes through September 4th, closing at the stroke of September 5th.

This replaced an earlier rule — 24 hours after `ScheduledAt` for a scheduled match, or after `CreatedAt` for one with no kick-off — that was internally consistent but anchored differently depending on whether a match happened to be scheduled. That divergence surfaced as a real product problem once the frontend grew a "has this match been played" status badge fed by the same idea (see `MatchesPanel.vue`'s `matchStatus` below): the badge looked inconsistent from one match to the next depending on scheduling and on whether goals had been entered yet, which real feedback flagged directly. Anchoring purely on `Date` — the one field every match already carries, scheduled or not — sidesteps that: neither `ScheduledAt` nor `CreatedAt` play any part in this any more, and `Match.CreatedAt` (added originally *for* this purpose — see "Data model" above) is consequently unused by this feature today, though left on the model rather than removed.

Past the deadline, `Vote`/`Unvote` both return the new `ErrVotingClosed` → **409**, the same status-code family as `ErrRegistrationsClosed` (a state conflict — the identical request would have succeeded a moment earlier — not a malformed one). `ListVotes`/`GET /matches/:id/votes` is **not** gated on this at all: the tally past the deadline is the finalized result, still worth serving, just no longer worth letting anyone change. `Unvote` keeps its pre-existing "no such match is still a no-op, never a 404" behaviour (see its own comment and `TestVote_Integration_UnknownMatchNotFound`) for a match `findMatch` can't even load — there is no window to enforce against a match that doesn't exist, and the route this backs is unreachable for an unrecognised id anyway (`RequireGroupMembershipByMatchPathParam` 404s first). The roster-must-be-composed rule from before is untouched and now simply ANDs with the window: `playerOnRoster` already requires the candidate to have a `MatchPlayer` row, which requires the roster to be at least partly built, regardless of timing.

**Routes**, all three `authRequired` + `RequireGroupMembershipByMatchPathParam` (the same match-scoped middleware from `matchscope.go` the sign-up routes use, and for the same reason — the group has to come from the match named in the path, never from a query param or the caller's own first group, or a member of group A could vote on group B's match):
- `POST /matches/:id/votes` takes `{"voted_for_id": "..."}` and casts or replaces the **caller's** vote — the voter always comes from the JWT, never the body, the same "no acting on someone else's behalf" rule as `MatchRegistrationHandler.Register`. It answers with the same summary `GET` returns, so a client sees the updated tally without a second request. 409s with `ErrVotingClosed` past the 24h window.
- `DELETE /matches/:id/votes` withdraws the caller's own vote. Like `ReopenRegistrations`, it's a **no-op success** when the caller had never voted — never a 404 — since removing a vote that was never cast is still exactly nothing to do. Also 409s with `ErrVotingClosed` past the window, since changing your mind about withdrawing is still an action on the vote, not a read.
- `GET /matches/:id/votes` returns `models.MatchVoteSummary { Tally []MatchVoteTally, MyVoteFor *uuid.UUID }` — every candidate with at least one vote, ordered by vote count desc then name asc, plus which player (if any) the caller has voted for. `MyVoteFor` is a pointer with `omitempty` for the same reason `MatchWithDetails.RegistrationCount` isn't a plain value: "the caller has not voted" has to stay distinguishable from a real player id, and `uuid.Nil` is a value a genuine vote could never hold but would be an ambiguous way to say so. Seeing the tally isn't privileged — only casting a vote is scoped to the caller's own choice — so this is open to any member, same as `ListRegistrations`, and it is never gated on the voting window either.

Status codes follow the sign-up routes' own unenumerability rule: a non-member gets 404 "match not found" (identical to a genuinely unknown id, via the same shared `abortMatchNotFound`), since a 403 would confirm the match exists and let match ids be enumerated by watching the status flip.

`MatchVoteService.tallyForMatch`/`TallyVotesForMatches` are GORM query-builder aggregations (`Joins` + `Group` + `Count`), **not** raw SQL — this is a single join with a `GROUP BY`, exactly the case the query builder is for, unlike the multi-table flatten/reconstruct `matches.go` needs raw SQL for (see "The flatten/reconstruct pattern" above). `TallyVotesForMatches` exists as its own batched query, keyed by match id, specifically for `StandingsService.GetMotmStandings` below — one round-trip for a whole group's matches rather than one query per match, the same reasoning `registrationCountsByGroup` already established for sign-up counts.

**The season leaderboard**, `GET /standings/motm?season=...`, follows `GetPointsStandings`/`GetScorers`'s exact shape: `StandingsService.GetMotmStandings(groupID, season)` loads the group's matches, filters by season in Go, then runs the pure `ComputeMotmStandings(matches, votesByMatch)` — which counts, per player, how many matches' `ComputeMotmWinners` included them, tie-inclusive (a three-way tie increments three rows, not one), then sorts by award count desc, name asc as the tie-break, mirroring `ComputePointsStandings`/`ComputeScorers`'s own convention. `IsMember` is set the same post-processing way as `PointsStandingRow`/`ScorerRow`, via the same `currentMemberIDs` helper — a player who has since left the group keeps every award their match history earned them, just tagged `IsMember: false`. Votes are **not** part of `MatchWithDetails` and never joined alongside `match_players` — the same reason `RegistrationCount` isn't (see "The flatten/reconstruct pattern"): `match_votes` is a second one-to-many on `matches`, so joining it in would multiply every scanned row and corrupt every goal total the file derives by summing them. It's fetched separately instead, once per `GetMotmStandings` call, via `TallyVotesForMatches` over every match id in the already-season-filtered result.

### Seasons
A season runs September 1st → August 31st and has **no table**: `models.SeasonOf(Date) string` (`internal/models/date.go`) derives its label (`"2025-2026"`) from a match date alone — a date in September or later belongs to the season starting that year, an earlier one to the season that started the previous year. `GET /standings/seasons` just maps `SeasonOf` over the group's matches and dedupes/sorts in Go, so no new query or migration is involved.

`ComputeSeasons` counts **every** match, including a scheduled one nobody has played yet — so scheduling a match into a future season makes that season appear in `GET /standings/seasons` before a ball has been kicked. That's a decision, not an oversight, and there's a test pinning it: `GET /matches/details` is filtered by whichever season the frontend has selected, so dropping a future season from this list would make the upcoming match unreachable in the UI, which is strictly worse than one extra dropdown entry.

The frontend's default selection is deliberately **not** "the last season in the list" for exactly this reason — that was the original approach, and real testing surfaced its cost immediately: scheduling one match far enough out silently hid every other match behind a near-empty future season, since it's now the new last entry. `MatchesAndStandings.vue`'s `loadSeasons()` instead defaults to `seasonOf(new Date())` (`src/services/datetime.js`, mirroring `models.SeasonOf` exactly) — the season *today* actually falls in, independent of what matches happen to exist. A future scheduled match changes the *list* `GET /standings/seasons` returns; it must not change what "today" defaults to. The one fallback case — today's own season has no matches logged yet, so it isn't in the returned list — still falls back to the last season that does, the same "no filtering" degradation as before.

`GET /matches/details` takes the same optional `?season=` query param as the standings endpoints (`MatchHandler.GetMatchesDetails` reads `c.Query("season")` and passes it to `MatchService.GetMatchesDetails(groupID, season)`, which applies `FilterMatchesBySeason` to its result before returning). The filter is applied in Go rather than as a SQL `WHERE`, for the same reason the endpoint above needs no query: a season is a derived label, not a stored column. Empty means "no filtering", and that is what **every** call site in `standings.go` passes explicitly (`GetPointsStandings`, `GetScorers`, `GetSeasons`, `GetPlayerProfile`) — they load a group's whole history and run their own `FilterMatchesBySeason` pass (or, for `GetSeasons`, need every season there is), so pushing the season down would double-filter or collapse the seasons list to the one asked for.

### Standings (matches.go → standings.go)
`StandingsService` (`internal/services/standings.go`) wraps a `MatchService` and exposes `GetPointsStandings(groupID, season)`/`GetScorers(groupID, season)`/`GetSeasons(groupID)`, backing `GET /standings/points`, `GET /standings/scorers` and `GET /standings/seasons` — plus `GetMotmStandings(groupID, season)` backing `GET /standings/motm`, which follows the identical shape but needs one extra data source (a match's votes); see "Man of the Match voting" above for why that source is a separate query rather than another join. The actual aggregation lives in package-level pure functions, `ComputePointsStandings`/`ComputeScorers`/`ComputeSeasons`, which take an already-loaded `[]models.MatchWithDetails` and know nothing about how that slice was produced. That split is what made both scoping axes cheap to add: the service loads a group's matches via `MatchService.GetMatchesDetails(groupID)` (the SQL-level scope) then narrows the slice in Go with `FilterMatchesBySeason` before handing it to the aggregators, which never changed. An empty `season` means "don't filter", so callers that don't pass one keep the all-time behaviour. Points standings only count matches where both teams have at least one player (an empty team means "not played yet", not a 0-0 draw — this is also the check that keeps a scheduled, not-yet-played match out of the standings, and the reason sign-ups live in their own table instead of as `MatchPlayer` rows); a match's result (win/draw/loss) is derived by comparing `Team.Score` between the two sides and applied to every player on each side.

`models.PointsStandingRow`/`models.ScorerRow` each carry an `IsMember bool` (json `"IsMember"`, matching these two structs' existing PascalCase convention). `GetPointsStandings`/`GetScorers` set it as a **post-processing step** after calling `ComputePointsStandings`/`ComputeScorers` — those two pure functions are untouched and still know nothing about group membership, only about already-loaded match data. The service loads the group's current member IDs via the private `currentMemberIDs(groupID)` helper (itself a thin wrapper over `GroupMembershipService.GetPlayersByGroupID`, built into a `map[uuid.UUID]bool`) and sets `row.IsMember` per row by `PlayerID`. A player removed from the group keeps every row their match history earns them — standings are computed from match history, not current membership — just tagged `IsMember: false`, which is what `PointsStandingsTable.vue`/`ScorersTable.vue` use to label the row "(left the group)" rather than hiding or altering it. `StandingsService.GetPlayerProfile` (below) deliberately does **not** call `currentMemberIDs`: every group it walks is, by construction, one the caller currently belongs to, so the field would be trivially `true` everywhere and isn't worth the extra query — its rows are left at the zero value (`false`), which `Profile.vue` doesn't read anyway.

### Player profile (cross-group)
`GET /players/me/stats` is the one standings-shaped endpoint that isn't scoped to a single group. `StandingsService.GetPlayerProfile(playerID, season)` walks the caller's groups (`GroupMembershipService.GetGroupsByPlayerID`, injected into `StandingsService` alongside `MatchService` and wired in `main.go`), loads and season-filters each group's matches exactly like the group-scoped endpoints, then runs `ComputePointsStandings` once per group (`PerGroup`) and once over the concatenation of every group's matches (`Overall`) — the aggregators themselves are untouched. A group the player belongs to but has never played in still gets a zeroed `PerGroup` entry, and a player with no matches anywhere gets a zero `Overall` row rather than an error; `models.PlayerGroupStanding` embeds `PointsStandingRow` so the JSON stays flat.

`MotmAwards` rides alongside at both scopes — `models.PlayerGroupStanding`/`models.PlayerOverallStanding` each embed `PointsStandingRow` and add their own `MotmAwards int` rather than growing `PointsStandingRow` itself, since that type is also `GET /standings/points`' own row shape and has no business carrying a Man of the Match count. Computing it follows the exact same "load once, compute at two scopes" shape the rest of this method already has: for each group, the already-loaded (season-filtered) matches are turned into match ids, `MatchVoteService.TallyVotesForMatches` loads their votes in one round-trip (the same call `GetMotmStandings` makes, just per group here), and `ComputeMotmStandings` finds this one player's award count via the new `findMotmAwards` helper (mirroring `findPointsRow`, defaulting to 0 when the player has no awards rather than treating absence as an error). Every group's `votesByMatch` map is merged into one combined map as the loop goes — match ids are globally unique, so two groups' entries can never collide under the same key — which is what lets `Overall.MotmAwards` be computed once, at the end, over the concatenation of every group's matches, the same way `Overall`'s points/goals already are.

The player comes from the JWT, never from the URL — there is deliberately no `/players/:id/stats`. Group membership is itself privileged information, so returning another player's cross-group profile would leak which groups they belong to, including groups the caller isn't in, bypassing `RequireGroupMembership`. That's also why the route is wired with `authRequired` only and no `requireGroupMember`: there is no single `group_id` to authorize against, and the handler only ever reports on the token holder's own groups. Viewing someone else's profile would need a visibility model of its own and doesn't exist.

### Input validation
`PlayerService.CreatePlayer` trims the name and rejects empty input (`ErrEmptyPlayerName`, a sentinel in `internal/services/players.go`), mapped to HTTP 400 in `PlayerHandler.CreatePlayer` via `errors.Is`. It has no duplicate-name check of its own, and `Player.Name` carries no DB-level uniqueness either (see the auth section above) — `PlayerService` stays entirely group-agnostic.

Duplicate protection for the admin-created "ghost player" flow (`POST /players`, used by `MatchDetails.vue`'s create-on-the-fly search) instead lives in `GroupMembershipService.HasMemberNamed(groupID, name)`, called from `PlayerHandler.CreatePlayer` after resolving the target group but before creating the player. It's a soft, per-group check only — an admin accidentally creating "Marco" twice in the same roster (a typo, a double click) is rejected with `ErrDuplicatePlayerNameInGroup` (`internal/services/groupMemberships.go`) → 400, but the same name used in a different, unrelated group is unaffected. Match date validation happens for free via the `Date` type's `UnmarshalJSON`: a malformed date fails JSON binding in the handler and surfaces as a 400 through the existing `ShouldBindJSON` error path, with no extra service-side check needed.

**Self-service rename** (`PATCH /players/me`, `authRequired` only — same reasoning as `GET /players/me/stats`: it only ever acts on the JWT's own player id, so there's no single `group_id` to authorize against) is the one place `Player.Name` uniqueness *is* enforced, and deliberately **globally** rather than per-group — a real divergence from every other name-touching path in this codebase, driven by an explicit product call rather than a technical one. `PlayerHandler.UpdateMyName` reads the caller's id via `playerIDFromContext`, trims the incoming name, and calls `PlayerService.UpdateName(playerID, newName)`, which: rejects an empty/whitespace-only name with the existing `ErrEmptyPlayerName` sentinel (shared with `CreatePlayer`); else checks `LOWER(name) = LOWER(?) AND id != ?` against every other player row and rejects a collision with the new `ErrPlayerNameAlreadyUsed` sentinel (`internal/services/players.go`) — both map to 400 via `errors.Is` in the handler; else updates the row. The `id != ?` exclusion is what makes renaming to your own current name (or the same name in a different case) a no-op success instead of a false collision against yourself. This is intentionally inconsistent with `CreatePlayer`/`SignupNewPlayer`'s total permissiveness on name collisions (see above): creation stays cheap and collision-tolerant because a display name legitimately isn't a unique identifier at that point, but a player *actively choosing* to rename themselves into a name someone else already holds is a different, narrower action product wants blocked outright, everywhere in the system, not just within one group — there is no per-group angle here since a rename isn't scoped to any group at all.

### Frontend
- `src/router/index.js` defines the app routes: `/` (`MatchesAndStandings`), `/matches/:id/edit` (`MatchDetails`), `/profile` (`Profile.vue`, `PlayerProfile`), and the auth pages `/login`, `/signup`, `/forgot-password` (`ForgotPassword.vue`) and `/reset-password` (`ResetPassword.vue`). The last four are the ones exempted from the `getToken()` check in `beforeEach` (`publicRoutes`), and are also listed in `App.vue`'s `isAuthenticatedRoute` — a page reachable without a token must not try to load `/groups/me`, nor show nav links that need a session. `ResetPassword.vue` takes its token from `$route.query.token` (the emailed link is `/reset-password?token=...`) and, on success, pushes `/login?reset=success`, which `Login.vue` turns into a confirmation notice — the same hand-off `Signup.vue` does. `App.vue`'s `<main>` is a bare `<router-view />`: it used to be gated on an `isRouterRoute` computed, with an `v-else` branch rendering `'teams'`/`'players'` "Coming soon" placeholders off an `activeTab` data field. Since `isRouterRoute` listed every named route in the router, it was always true and that branch was unreachable — it, `activeTab`, the `$route` watcher that maintained it and the `.tab-content*` CSS are all gone. There is deliberately still no catch-all route, so an unmatched URL renders an empty `<main>`, exactly as it did before. `/m/:code` is a bare `{ redirect }` entry too, but a computed one rather than a fixed path — see the "Share on WhatsApp" `/m/:code` bullet further down for why it exists, how the code is validated, and why it now redirects to `/?match=<code>` rather than `/matches/:id/edit`. `/standings` and `/groups` are both bare `{ redirect }` entries now, not pages: matches/standings merged into `/` (below), and group management moved into `Profile.vue` (see "Frontend" further down) — both redirects only exist so an old bookmark still lands somewhere sane instead of a 404. `.nav-menu` in `App.vue` is down to two links, "Matches" (`/`) and "Profile" (`/profile`) — `Profile` was promoted from an icon-only button in `nav-actions` to a full labelled tab once it started doing more than showing stats (see below), which is also what keeps the nav from reading as a single lonely link. `App.vue` itself no longer holds any group-related state (`groups`/`activeGroupId`/`refreshGroups()` were all removed) — nothing outside Matches/Standings ever consumed it, so once the group selector moved off the navbar (see below) it had no remaining caller.
- **`/matches/:id/edit` is admin-only, enforced by a real `beforeEnter` guard, not just hidden links.** Real product feedback: every editing control on `MatchDetails.vue` was already `v-if="isAdmin"`-gated (see "Role-based UI hiding" below), but a plain member could still land on the page itself — worse, the confirmed/waiting sign-up list and Man of the Match voting used to live there too, so there was a real reason for a non-admin to visit. Both moved into `MatchesPanel.vue` (below), which closed that reason and is exactly what makes gating the page itself viable. This is a **frontend-only** gate — `GET /matches/:id/details` stays open to any group member on the backend unchanged, since `MatchesPanel.vue` (reachable by every member) depends on reading it. `canEditMatch(matchId)` (exported from `router/index.js` for its own unit test — see the Commands section) does the check: it loads the caller's groups via `loadMyGroups()` (`activeGroup.js`, the same cached `GET /groups/me` call `resolveActiveGroup()` already shares — no new request pattern), then calls the shared `findGroupForMatch(matchId, groups)` helper (also exported, also unit-tested on its own) to try `getMatchDetailsByID(matchId, group.id)` for each of the caller's groups **in turn** until one succeeds, and returns whether *that* group's role is `'admin'`. The naive alternative — call `getMatchDetailsByID(matchId)` with no `group_id` — resolves on the backend to the caller's *first* group (`resolveGroupID`'s fallback), which silently 404s the moment the match belongs to any other group the caller is in; trying every group explicitly is what makes this correct for a player in more than one group, at the cost of up to one request per group (acceptable for a one-time page-entry check, and there is no new backend endpoint to avoid exactly this cost). A 404 for one group means "not this one, keep looking"; any other failure aborts and is treated the same as "not allowed" one level up, in the route's own `beforeEnter`, which redirects to `/` either way — covering "not an admin" and "not a member of the match's group at all" with the same outcome, and failing closed on a network error rather than letting a half-verified navigation through. `MatchesPanel.vue`'s own "Edit Match" link is hidden (not just relabelled, as it used to be) for a non-admin, so a member is never shown a link that would only bounce them straight back — see "Role-based UI hiding" below. `findGroupForMatch` has a second caller besides `canEditMatch`: `MatchesAndStandings.vue`'s own resolution of a shared `/m/:code` deep link (see "Share on WhatsApp" further down) needs the exact same "which of my groups owns this match" search, just to answer a different question (which group to switch into, not whether the caller may edit) — factoring it out is what keeps that from being a second copy of the same try-each-group loop.
- `src/services/api.js` is the single Axios client (`API_BASE_URL` from the `VUE_APP_API_BASE_URL` env var, default `http://127.0.0.1:8080` — the `VUE_APP_` prefix is mandatory, see the deployment section) — every backend call goes through here. The five sign-up calls (`registerForMatch`/`unregisterFromMatch`/`getMatchRegistrations`/`closeMatchRegistrations`/`reopenMatchRegistrations`) and the three Man of the Match vote calls (`voteForMotm`/`removeMotmVote`/`getMatchVotes`) are the only match calls that take **no** `groupId`, and deliberately so: the backend derives the group from the match in the path, and passing one would be the very hole that design closes. `getMotmStandings(season, groupId)` mirrors `getPointsStandings`/`getScorers` exactly, hitting `GET /standings/motm` through the same `query({...})` builder.
- **Active group** — `src/services/activeGroup.js` holds the group `MatchesAndStandings`/`MatchDetails` are scoped to. It's a per-device preference in `localStorage` (`calciotto-active-group`, same pattern as the token in `api.js`), not server state: the backend has no notion of an "active" group, `resolveGroupID`/`resolveGroupIDForMembership` just take whatever `group_id` a request carries. Without it every scoped view silently fell through to `GetFirstGroupForPlayer`, so a player in two groups could only ever see the first.
  - `resolveActiveGroup()` is the whole contract: it loads `GET /groups/me`, and if the stored id isn't in that list (the player left the group, another account used this browser, or this is a fresh device/session with nothing stored yet — e.g. right after logging in) it falls back to the player's **favorite group** (`group.is_favorite`, set server-side — see "Group bootstrapping" above) and rewrites the stored value, rather than sending a `group_id` `RequireGroupMembership` would reject. `groups[0]` is kept only as a further defensive fallback if no group is marked favorite (shouldn't happen given the backend invariant, but costs nothing to guard). `resolveActiveGroupId()` is the thin wrapper the views call in `created()`; it swallows errors and returns `''`, which just means "send no `group_id`" — i.e. degrade to the old first-group behaviour instead of taking the view down.
  - The `GET /groups/me` promise is cached at module scope (failures aren't), so all four consumers on a page share one request. That's safe precisely because the active group only ever changes through a **full page reload**. There is no reactive store (no Vuex/Pinia) and the views read the group once, in `created()`, so a reload is what actually re-scopes the app.
  - **The group selector** lives in `MatchesAndStandings.vue`'s `.controls-bar`, at the same level as its season `<select>` — not the navbar. It used to be a global popover (`GroupSwitcher.vue`, since deleted) in `App.vue`'s `nav-actions`, but nothing outside Matches/Standings ever consumed the active group, so a navbar-wide selector was solving a problem only one page had. It's a plain `<select v-model="activeGroupId" @change="switchGroup">` populated from the same `groups` array `resolveActiveGroup()` already returns; `switchGroup()` does `setActiveGroupId(...)` then `window.location.reload()`, the same full-reload contract as before. A player with no groups sees a text hint ("No group yet — join or create one from your Profile") instead of an empty dropdown.
  - **Creating and joining a group** moved to `Profile.vue`'s "Your groups" card header — two small icon buttons (a "join" arrow-into-bracket icon and a "+") next to the "Your groups" title, opening `JoinGroupModal.vue` / `CreateGroupModal.vue` respectively. Both still switch straight into the group just joined/created (`setActiveGroupId(group.id); window.location.reload()`) rather than leaving the player on whatever was active before.
  - `#app` carries an explicit `color: var(--text-primary)`, restating exactly what `body` already declares in `global-styles.css`. Not redundant: `.dark-mode` toggles on `#app`, a *descendant* of `body`, so `body`'s own `color: var(--text-primary)` resolves against `:root`'s (light) value — `body` never sees the `.dark-mode` class at all — and that already-resolved literal colour is what plain CSS inheritance then hands down to every element below it. Most components never notice, because they redeclare `color: var(--text-primary)` (or `--text-secondary` etc.) themselves, which re-resolves the variable against the nearer `#app.dark-mode` scope and correctly picks up the dark value. Anything that instead relies on plain inheritance — no `color` of its own — stays stuck on the light-mode colour even with dark mode on (found via `MatchDetails.vue`'s `.signup-list-title`, unreadable dark-grey-on-navy in dark mode; verified with `getComputedStyle` before and after, not by eye). Restating the declaration on `#app` breaks the frozen inheritance chain at the one point that actually sees the theme class.
  - `CreateGroupModal.vue` and `JoinGroupModal.vue` are both `<Teleport to="body">`'d (their `.modal-overlay` would otherwise resolve `position: fixed` against an ancestor's `backdrop-filter` containing block) — which also means neither can inherit the `.dark-mode` class `App.vue` toggles on `#app`. Since both are opened from `Profile.vue`, a routed view with no prop path back to `App.vue`, they snapshot the theme via `src/services/theme.js`'s `isDarkModeActive()` instead of a prop: `document.querySelector('.dark-mode') !== null`, deliberately not `document.getElementById('app')` — `public/index.html`'s own mount container also carries `id="app"`, and Vue 3 nests its rendered root (the one actually carrying `.dark-mode`) inside that container rather than replacing it, leaving two elements sharing the id, so `getElementById` can return the wrong (always class-less) one. `GroupSettingsModal.vue` (below) uses the same helper.
  - `api.js` threads `group_id` as a query param through `getMatchesDetails`/`getMatchDetailsByID`/`getPointsStandings`/`getScorers`/`getSeasons` via a shared `query({...})` builder that drops empty values (it replaced the old `seasonQuery` helper). `getMatchesDetails(groupId, season)` also carries the optional `season`, the same way `getPointsStandings`/`getScorers` do — that's what lets the unified page's one selector scope all three of its sub-tabs. `updateMatch` needs nothing: it posts back `this.match`, whose `GroupID` came from `getMatchDetailsByID`. `createMatch(matchData, groupId)` puts the group in the **body**, under the snake_case key `group_id` — `CreateMatch` binds into `models.Match` whose tag is `json:"group_id"`, and Go's case-insensitive fallback does not see past the underscore, so a `GroupID` key binds to nothing and the match silently lands in the player's first group instead. `MatchDetails.vue`'s `createNewPlayer()` hits the same gotcha: it posts `{Name, group_id: this.match.GroupID}` to `createPlayer` (`POST /players`, now `authRequired` + `requireGroupAdmin`) — sending `GroupID` instead would silently fail to bind and let the new "ghost" player fall through to `PlayerHandler.CreatePlayer`'s own-first-group fallback instead of joining the match's actual group.
  - `Profile.vue` deliberately sends no `group_id` for its own stats call: `GET /players/me/stats` is cross-group by design (it walks every group the JWT's player belongs to), and group management (now folded into the same page, see below) has no notion of an active group either — the per-group actions there take whichever group's card the caller clicked, not the nav's active one.
- **The unified home page** — `MatchesAndStandings.vue` (route `/`) is one page with one season selector over four sub-tabs: **Matches**, **Points**, **Scorers**, **MOTM**, both bars merged into a single `.controls-bar` (tabs on the left, season picker on the right, stacked on mobile) rather than two separate bars stacked vertically. It replaces the old split between a `/` matches page and a `/standings` page. It is a composition shell and owns only what the tabs share: the active group (`resolveActiveGroup()`, once, in `created()`), the caller's `isAdmin` role on it, `seasons` (`GET /standings/seasons`, preselected on the last — i.e. most recent — label the backend returns) and `selectedSeason`, plus the standings data itself. Its children are deliberately kept as separate files rather than concatenated into one component, so each keeps its own scoped CSS and methods:
  - `MatchesPanel.vue` (the old `MatchesPanel.vue`, renamed and demoted from routed page to child) — takes `activeGroupId`/`isAdmin`/`season` as props and loads its own matches, since it's the only piece that knows how; a `watch` on `season` reloads them. It no longer resolves the active group or the role itself, and its gradient page header is gone (the page owns it). The admin-only "Create Match" action is not a separate toolbar button any more — it's a trailing dashed "+" card (`.add-match-card`) at the end of the horizontal match list itself, same size class as a match card, so creating a match reads as "add one more to this list" instead of a disconnected button above it. Its create-match modal carries the **optional scheduling block**, behind a checkbox that is unchecked by default so the ordinary "record a match already played" flow is untouched: ticking it swaps the date picker's role (kick-off time, sign-ups opening, max players — defaulting to 16, since a calciotto is 8v8) and validates the same rules the backend does, so the reason lands next to the field instead of coming back as an opaque 400 — with the backend's own message surfaced verbatim if it rejects anyway. A scheduled match's card then shows its kick-off instead of a plain date, plus a one-line sign-ups badge and count (`RegistrationCount ?? 0` — `??` and not `||`, since a present-but-zero count is a real state these cards render as "0/16").
  - `PointsStandingsTable.vue` / `ScorersTable.vue` / `MotmStandingsTable.vue` — pure presentation, `rows` + `isLoading` props, no fetching. Next to a row's name, all three render a small muted "(left the group)" tag (`.left-group-tag`) whenever `row.IsMember === false` — the row itself (goals, points, rank, or MOTM award count) is untouched, this only labels a departed player's historical stats as belonging to someone no longer in the group. `MotmStandingsTable.vue`'s own empty state ("No Man of the Match awards yet") is reached both by a group with no votes anywhere and by one whose votes never produced a played-match tally, since `GET /standings/motm` collapses both into the same empty array. `getPlayerInitials`/`formatPlayerNameForDisplay` are duplicated across these files, the same way `getTeamColor()` is duplicated between `MatchesPanel.vue` and `MatchDetails.vue`.
  - The page loads **all three** standings tables together on a season change (one `Promise.all`, `isLoadingStandings`), as the old `Standings.vue` did for the first two, so switching between Points, Scorers and MOTM costs no request; the matches list instead reloads through the `season` prop. The tab content is `v-if`'d per tab and gated on `isInitializing`, so no child ever mounts (and fetches) before the active group is resolved.
- **`Profile.vue`** (route `/profile`, component name `PlayerProfile`) is now "your stats", "your groups", *and* the onboarding entry point (create/join) — the standalone `Groups.vue` page was folded in here, since once group management was scoped to a single active group (see the changelog below) its own tab had nothing left to justify a whole nav entry, while browsing per-group stats and a group's roster are naturally the same kind of task ("me, and the people I play with"). It renders `GET /players/me/stats`: an overall card on top (unchanged, no aggregation, no `season` support yet — its seven stats, `overallStats`, are Played/Won/Drawn/Lost/Goals/MOTM/Points, `overall.MotmAwards` slotted in right before the highlighted Points figure), then a **horizontal carousel** (`.groups-bar`, same scrolling-card pattern as `MatchesPanel.vue`'s match list) with one card per group in `PerGroup` — a favorite star, group name, an "Admin" badge when `groupMeta[row.GroupID].role === 'admin'`, and that group's own Played/Points/Goals/MOTM (`row.MotmAwards`, the cumulative Man of the Match award count added alongside the other three, real product feedback after the MOTM feature itself shipped with nowhere on the profile to see a running total). `groupMeta` is a `GroupID -> { role, isFavorite }` map resolved separately via a plain `getMyGroups()` call (`GET /players/me/stats` has no reason to know about either), so it costs one extra request `Profile.vue` doesn't share with any other view's own `resolveActiveGroup()` call — accepted as the cost of keeping "cross-group stats" and "active/favorite group" as two unrelated concerns.
  - **Favorite star** — filled and disabled for the group `groupMeta[groupId].isFavorite` is already true (nothing to do); an outline star on any other card is clickable (`@click.stop`, so it doesn't also toggle the roster panel) and calls `setFavoriteGroup(groupId)` → `PATCH /groups/:id/favorite`, then re-fetches `groupMeta` so both the old and new favorite's stars update together (setting a new favorite always un-favorites whichever one held it before — see "Group bootstrapping" above).
  - **Create/join** — two icon buttons in the card header (`.groups-header-actions`) open `JoinGroupModal.vue` / `CreateGroupModal.vue` (see "Active group" above); shown even with zero groups, since that's exactly when a player needs them.
  - Clicking a card toggles a roster panel below the carousel open/closed (`selectedGroupId`), fetching `getGroupMembers(groupId)` on first open and caching per group (`membersByGroup`) so reselecting a group already opened this session costs no request. The list itself scrolls (`max-height` + `overflow-y: auto`) rather than growing the page indefinitely for a large roster. Viewing is open to any member; **admin-only actions** (gated per the *specific* group the row belongs to, via `groupMeta`, not just "is admin of some group") are: a role-toggle ("Make admin"/"Make member" → `updateMemberRole`) and "Remove" (→ `removeMember`, behind a `window.confirm(...)`) — both re-fetch the roster on success rather than patching in place — never on the caller's own row (`member.id !== currentPlayerId`, from the same JWT-decode `currentPlayerIdFromToken()` helper as before), even though the backend would refuse a self-targeted call anyway (`ErrCannotChangeOwnRole`/`ErrCannotRemoveSelf`).
  - **Ghost-player invite** — a member with no `email` (an admin-created "ghost" player, per `PlayerWithRole` embedding `Player`'s own `email,omitempty` tag) shows a "No account yet" badge; an admin of that group additionally gets an "Invite" button that reveals an inline email input + "Send invite", calling the new `invitePlayer(groupId, playerId, email)` → `POST /groups/:id/members/:playerId/invite` (backend-only until now — see the auth section above). On success the roster reloads, so the badge/button disappear once `member.email` is set; the success message explicitly warns there's no real email delivery configured in this environment (the reset-style link is only logged server-side), so an admin testing this locally isn't left wondering why no email arrived.
  - **`GroupSettingsModal.vue`** holds the admin-only "occasional config" actions that don't belong in a stats/roster page: invite code (`getInviteCode`, show + copy) and team management (`getTeamsByGroup`/`updateTeam`, one editable name + `TeamColourPicker` + Save per team) — exactly what `Groups.vue`'s "Show invite code"/"Manage teams" used to do, just moved into a dialog. It opens from a small gear icon on a group's card (admin-only, `@click.stop`) rather than being folded into the roster panel itself, since it's a separate, infrequent action. Teleported and theme-snapshotted the same way as `CreateGroupModal.vue`/`JoinGroupModal.vue` (see "Active group" above).
- `MatchesPanel.vue` (the Matches sub-tab of the page above, not a route of its own) lists matches and lets you create one (custom date-picker, no external date library); `MatchDetails.vue` is the **admin-only** editing page (see the router-guard bullet above) where teams are populated (player search/create-on-the-fly) and goals are edited, then persisted via a single `updateMatch` call that sends the whole match payload. `reloadAllPlayers()` (the "add an existing player to a team" search backing `this.allPlayers`) fetches `getGroupMembers(this.activeGroupId)` — **scoped to this match's own group** — rather than the old `getPlayers()` (every player in the database): a player removed from the group, or belonging to an unrelated one, is no longer offered here. Since `getGroupMembers` returns `PlayerWithRole`'s lowercase `id`/`name` fields, the result is translated to the `{ID, Name}` shape (`role` unused) the rest of this component already expects for players, matching `PlayerCustom`'s convention from the `getPlayers()` call it replaced. If `activeGroupId` never resolved (`resolveActiveGroup()` failed), this degrades to an empty list rather than requesting a malformed URL. Creating a player on the fly (`createNewPlayer()`) is only reachable by a group admin (`POST /players` is admin-gated), and its own client-side "already exists" check only looks at `this.allPlayers` (now the current group's members, no longer every player globally) — the backend's per-group `HasMemberNamed` check can still reject a name that collides only within this match's group, surfaced via the backend's own error message rather than a generic one.
  - **Role-based UI hiding** — the first place in this codebase that hides controls by role rather than only relying on the backend's 403, and now **defense-in-depth** rather than the only thing standing between a non-admin and this page: `/matches/:id/edit` itself is admin-gated by the router guard above, so this `v-if="isAdmin"` sprinkling is cheap insurance if that guard is ever bypassed, not the sole protection — left in place deliberately rather than ripped out as "redundant" now. `isAdmin` is derived from the **caller's own** `role` on the matching entry of the `groups` array `resolveActiveGroup()` returns (`groups.find(g => g.id === activeGroupId)?.role === 'admin'`) — the same `GroupWithRole.Role` field `GET /groups/me` already carried, just read for the first time. `MatchDetails.vue` still does that resolution itself in `created()` (it's a routed page); `MatchesPanel.vue` no longer does — `MatchesAndStandings.vue` resolves it once for the whole page and passes it down as a prop. `MatchesPanel.vue` wraps its "Create Match" button (both the toolbar one and the empty-state one), and its "Edit Match" link (see the router-guard bullet above), in `v-if="isAdmin"`. `MatchDetails.vue` wraps every editing control the same way — "Add Player", "Save Changes", each player card's remove (X) button, and both goal +/- buttons — while leaving player name/avatar/goal count as always-visible plain content, so an admin who somehow still reaches this page in a stale or degraded state can look without necessarily touching. This is UI convenience only, not the authorization boundary: the boundary is still `requireGroupAdmin` on `POST /matches` / `PUT /matches/:id` / `DELETE /matches/:id` — a non-admin who forges a request directly still gets a 403.
  - **Delete Match** — `MatchDetails.vue` has an admin-only (`v-if="isAdmin"`) "Delete Match" button (`.btn-danger`, `.delete-match-btn` for extra spacing so a click can't land on it while reaching for "Save Changes"), next to "Save Changes" in the action bar. It reuses the `window.confirm(...)` pattern `beforeRouteLeave`'s unsaved-changes guard already established in this file, rather than a custom modal. On confirmation it calls the new `deleteMatch(matchId, groupId)` in `api.js` (`DELETE /matches/:id?group_id=...`, mirroring `updateMatch`/`createMatch`'s structure) and, on success, navigates back the same way `goBack()` does elsewhere in this file; a failure shows the existing toast (`showMessage(..., 'error')`) instead of failing silently.
  - **The sign-up panel** — `MatchDetails.vue` renders it only for a scheduled match (`isScheduled`, i.e. the match carries a kick-off), below the teams: the state label and detail from `deriveRegistrationState`, the confirmed roster and the waiting list split out of the one `GET /matches/:id/registrations` list, Participate/Withdraw for any member, and Close/Reopen for an admin. A few non-obvious choices, all of which have a reason a reader would otherwise have to reconstruct:
    - The list is **always fully re-fetched**, never patched locally: `Position`/`IsWaiting` are derived server-side from the stored order, and the promotion of the first reserve when someone withdraws is exactly the thing the panel exists to show — patching locally is how the display drifts from reality.
    - `registrationsClosedAt` is held in the component's own state, deliberately **not** written back into `match`. Close/Reopen change it server-side, and mutating `match` would make `hasUnsavedChanges()` see the match as dirty against `matchSnapshot` and pop the "leave without saving?" confirm — or, if the snapshot were refreshed too, silently swallow real unsaved goal edits.
    - `nowMs` is sampled **once**, in `created()`. There is no polling timer and no reactive clock anywhere in this feature: the app has no reactive store and re-reads its data on navigation, so a player who had the page open from before sign-ups opened sees the button after a reload — which is also how they find out at all, since nothing notifies them. The copy is written to match, and says nothing about being told when sign-ups open.
    - Two separate in-flight flags (member action vs. admin action), so an admin closing the list doesn't grey out the member-facing buttons. Landing past the cap is reported as a success naming the waiting-list position, not as an error; a 409 is surfaced verbatim, and the list is reloaded either way since a rejection usually means the page's view is stale.
  - **"Fill teams from sign-ups"** — offered to an admin only once the list is closed (by them, or by kick-off), which is the flow the product described: close sign-ups *in order to* pick the teams. `canFillTeamsFromSignups` gates the button itself; it no longer also checks `allConfirmedAlreadyPlaced` (see below) — the button stays offered even once every confirmed sign-up already has a team, since building manually is still meaningful then (a late substitute, reassigning someone off the waiting list, and so on).
    - **Clicking it opens a compose-choice modal** rather than acting immediately — two ways to build the roster from the sign-up list, not one:
      - **Auto-split** — the original mechanical behaviour, unchanged: `fillTeamsFromRegistrations` returns fresh rosters and the component assigns them into its local match state; the existing "Save Changes" persists them through the usual `PUT /matches/:id` diff. There is no endpoint for this and there should not be one. Confirmed entries only (the waiting list is by definition who didn't get a place), in `Position` order, each going to whichever team is currently smaller with ties to the first — a plain alternation on an empty match, a gap-closing fill on one an admin has already partly filled. **Additive**: a player already in either team is left exactly where they are and counted as skipped, so it can be re-run without duplicating anyone or discarding manual work (including goals already recorded) — explicitly chosen over balanced allocation by past stats. Identity is checked on id first and name second — never name-first, since this app deliberately lets two players share a display name, and the second "Marco" would otherwise be silently dropped. This option alone is hidden — not disabled — once `allConfirmedAlreadyPlaced` (a computed that runs `fillTeamsFromRegistrations` itself, the exact function this option calls, against the current rosters and checks whether it would place anyone) is true; deliberately narrower than "nothing to fill", an *empty* confirmed list still offers it, since hiding it there would leave an admin who closed sign-ups on an empty list with no explanation for why choosing it does nothing — `fillTeamsFromSignups()`'s own "nothing to fill the teams with" error message is what answers that.
      - **Build manually** — opens the existing Add Player modal (the same one the per-team "+" icon opens once a roster exists), which is what makes this the bridge across the one gap that icon can't reach on its own: before any player has been placed, `.team-management` (and its "+" icon) stays hidden by `showTeamRoster`, but the compose-choice modal lives in `.signup-actions`, a sibling that's never behind that gate.
    - **The Add Player modal tiers its candidate list by sign-up, for any scheduled match, from either entry point.** `filterAvailablePlayers()` — with no search term active — shows confirmed sign-ups first (in `Position` order), then the waiting list, and leaves the rest of the group out of the default view entirely; the moment a search term narrows the list, it searches the whole group again, sign-up or not. Each tiered entry carries a `registrationBadge` (`{ position, waiting }`) the template renders as a small pill (`#N`, muted when waiting) next to the name — reusing the same "waiting is deliberately muted" convention as `.signup-list-waiting` elsewhere in this file. An unscheduled match is untouched: no registrations exist for it, so tiering would just be an expensive no-op, and `filterAvailablePlayers()` short-circuits straight to the plain, unsorted group list it always returned. This is why the two entry points (the compose-choice modal's "Build manually", and the ordinary "+" icon once composition has started) never disagree — they share the exact same filtering method, not two copies of "sort registrants first" that could drift apart.
  - **"Share on WhatsApp"** (`.signup-actions`, next to Close sign-ups, admin-only and only while `registrationsOpen` — there's nothing to invite people to once the list is closed) solves a narrower problem than it sounds: the goal was posting into a WhatsApp *group*, not to one person, and neither WhatsApp integration option fits that. The official Cloud API cannot post into a group at all — it's built for 1:1 business/customer messaging only, with no endpoint for group chats. The only programmatic alternative is an unofficial client (Baileys, whatsapp-web.js) posing as a logged-in device, which risks the number it runs on being banned by WhatsApp and needs a persistent authenticated session, not a stateless API call — too fragile for what this app actually needs. `src/services/whatsappShare.js` instead builds a plain [`wa.me`](https://wa.me) link (`buildWhatsAppShareText`/`buildWhatsAppShareUrl`, both pure and unit-tested): WhatsApp's own published "click-to-chat" URL format, `https://wa.me/?text=<message>`, which needs no API key, no business account, and no signup. Crucially, **omitting the phone number** is what makes group-sharing possible at all: with no recipient specified, WhatsApp opens its own contact/group picker instead of a specific chat, letting the admin choose any contact or group they're already in. The link is rendered as a plain `<a target="_blank">` (`.whatsapp-share-btn`, `MatchDetails.vue`) rather than a click handler — it is genuinely just a URL, opened the same way any other outbound link would be. The message body is deliberately plain: `Match: <kickoffLabel>`, then `Sign-ups are open — Join Calciotto:`, then the link on its own line — no emoji (dropped after one didn't render for a real user testing this on their device) and no markdown link syntax (WhatsApp's text messages support *bold*/_italic_/~strikethrough~ but nothing that hides a URL behind custom anchor text — "Join Calciotto" can only ever be a label, with the actual URL still spelled out on the next line so WhatsApp auto-linkifies it). The whole feature is deliberately semi-automatic: the admin still clicks, still picks the group, still presses send inside WhatsApp — that human step is what keeps this reliable with zero infrastructure and zero ban risk, at the cost of not being a real "send automatically when registration opens" notification.
    - **The link itself is a self-hosted "tinylink", not the full `/matches/:id/edit` URL.** A raw UUID reads badly next to "Join Calciotto" in a chat, and a public shortener (TinyURL, is.gd, ...) was ruled out for the same reason a WhatsApp Business integration was: most don't set the CORS header a browser needs to read their response, and either way it's an external dependency's uptime for something this simple. `src/services/shortLink.js`'s `encodeMatchId`/`decodeMatchId` instead re-encode the match id's own 128 bits as base62 (`92bbe7a1-fa67-49dc-9058-85837504d0d4` → something like `4kX9pQz...`, no hyphens) — losslessly and reversibly, with **no lookup table and no new backend route or storage at all**: the "short link" *is* the id, just spelled in a smaller alphabet, so there's nothing to keep in sync or garbage-collect. `router/index.js`'s `/m/:code` is a bare `redirect: to => ...` entry (no component of its own): it calls `decodeMatchId(to.params.code)` once, purely to validate the code, then redirects to `/?match=<code>` — the **raw code**, not the decoded id; a malformed code (hand-edited, truncated in transit) falls back to `/` rather than throwing mid-navigation.

      Every code is left-padded with `'0'` to a **fixed width** (`CODE_LENGTH`, the length of encoding `2^128 - 1` — computed once from `BASE62_ALPHABET`'s own length rather than hardcoded) — this is load-bearing, not cosmetic. Base62, like any positional numeral system, strips leading zero bits the same way `parseInt` would, so a UUID with several leading zero bytes would otherwise encode to a noticeably *shorter* code than a typical one. Without a fixed width, `decodeMatchId` has no way to tell a genuinely short code from a longer one truncated in transit (a copy-paste cut short, say) — every character of a truncated code is still valid base62, so it doesn't fail to parse, it just silently produces a different, wrong-but-plausible UUID (an actual bug this codebase shipped and then fixed once a code review caught it — the fix is the fixed width plus a length check, not a "try to detect corruption" heuristic bolted on after the fact). `decodeMatchId` rejects any code whose length isn't exactly `CODE_LENGTH` before decoding at all, and separately rejects a same-length code whose value still exceeds `2^128 - 1` (possible since `62^CODE_LENGTH` overshoots `2^128`) rather than letting the fixed-width hex slicing silently drop its high bits. Decoding itself re-pads the reconstructed hex to the UUID's fixed 32 digits before re-inserting the hyphens, same reasoning one level down (a decoded value with leading zero bytes needs its hex grouping restored).

  - `src/services/datetime.js` — the whole date path, both directions. Outbound (`toLocalRFC3339`, `dateTimeLocalToRFC3339`, `formatUTCOffset`): a local `YYYY-MM-DD` day plus an `HH:MM` time into RFC3339 **carrying the browser's own UTC offset**, because the backend derives the match's day (and season) from `scheduled_at` in the offset it was sent in. Nothing here goes through `toISOString()`, which always emits `Z` and would file a 00:30 Paris kick-off under the previous day; `<input type="datetime-local">` has the mirror-image problem (its value carries no offset at all), so it routes through here too. The offset is read from a `Date` built at that exact local instant rather than from `new Date()`, so a match scheduled across a DST boundary is stamped with the offset in force *then*. Inbound (`formatDateTimeForDisplay`, `formatDateTimeShort`): rendered in the **browser's** zone, no `timeZone` option — a kick-off is a single instant and a player elsewhere wants to know when it happens for them — returning `''` rather than "Invalid Date" for unparseable input. Calendar days (`Match.Date`'s `YYYY-MM-DD`) are the third case and the opposite one, handled by `parseCalendarDay` plus `formatCalendarDay`/`formatCalendarDayLong`/`formatCalendarDayShort`: `new Date('2026-09-06')` is specified to parse a date-*only* string as **UTC** midnight (a date-*time* string with no offset parses as local — the inconsistency is in the language), so formatting it in the browser's zone rendered the *previous* day for anyone west of Greenwich, which is what the components used to do by hand. The parse is explicitly local because a calendar day is not an instant: `Match.Date` is the day the group played, identical for every viewer, where `ScheduledAt` is one instant deliberately shown in each viewer's own zone. An out-of-range day (`2026-02-31`) is rejected rather than rolled over into March, and unusable input **echoes the raw string** instead of returning `''` — a kick-off line can be dropped from a card harmlessly, but a match's date is the card's identity, so a blank would just look broken.

### Seeding data
`app/cmd/seed/main.go` is the real seeding tool (replaces an older set of ad hoc `*_test.go` files that abused `go test` to insert rows with no isolation or cleanup — those are gone). It reuses the normal `internal/services` layer, so seeded data goes through the same code path as the API. Run via `go run ./cmd/seed` (locally, with `DB_HOST=localhost` etc. exported) or `docker compose exec backend go run ./cmd/seed` (inside the network, where the `db` hostname resolves).

## Gotchas

- `AutoMigrate` runs on every backend startup (`InitDB` in `connect.go`), so schema changes to the GORM models in `internal/models/database.go` take effect automatically on next run/restart — no separate migration files exist.
- **Schema application is serialized by a Postgres advisory lock**, not merely made less likely to race: `InitDB` calls `applySchema` through `withSchemaMigrationLock`, which takes `pg_advisory_lock(schemaMigrationLockKey)` (an arbitrary fixed key, `726750310`; nothing else in this codebase takes an advisory lock). Two situations hit this for real — several backend replicas each calling `InitDB` on startup in production, and `go test ./...` in CI, where every package is its own binary running concurrently and `testutil.OpenDB`'s `sync.Once` only dedupes *within* one binary. Without it two processes can both see a table as absent and issue concurrent `CREATE TABLE`s, which Postgres does **not** fully serialize on its own: one loses a race on the implicit row type registered in `pg_type` and fails with `duplicate key value violates unique constraint "pg_type_typname_nsp_index"` (SQLSTATE 23505) — not an app bug, just two DDL statements arriving at once. The mechanics are load-bearing: a session-level advisory lock belongs to the *connection* that took it, so the helper pins one physical `*sql.Conn` out of the pool and hands `fn` a `*gorm.DB` built on that same connection (`postgres.Config{Conn: conn}`) rather than the pool-backed `db` — which could otherwise route `AutoMigrate`'s own statements onto a different connection than the one holding the lock. Release is `defer`red and only logs a warning on failure, since closing the connection drops a session-level lock anyway.
- Outside Docker (e.g. running `go run .` or `go run ./cmd/seed` directly on the host), `DB_HOST` defaults to `db` which won't resolve — override it to `localhost` and match the port Postgres is published on (`POSTGRES_PORT`/`DB_PORT` in `devops/env/develop.env`, 5432 by default).
- Forgetting `--env-file env/develop.env` on `docker compose up` silently breaks the `db` service: `${POSTGRES_PORT}`/`${POSTGRES_PASSWORD}` and the bare `DB_NAME`/`DB_USER`/`DB_PASSWORD` refs resolve to empty, and the `pg_isready` healthcheck then fails with `role "root" does not exist` (it falls back to the container's default OS user). Adding `environment:`/`env_file:` on the `db` service itself does not fix this — those only populate the container's runtime env *after* Compose has already resolved the `${...}` placeholders in the YAML from the flag/shell env.
