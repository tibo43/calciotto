# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Agoran is a small full-stack app for organizing amateur football ("calciotto") matches: creating matches, assigning players to color-named teams, and tracking goals per player. Backend is Go (Gin + GORM + PostgreSQL), frontend is Vue 3 (Vite).

**Naming.** The product is called **Agoran** (domain `agoran.app`) everywhere a user sees it: page title, PWA manifest, passkey display name, emails, push notifications, share messages, the guide. The code still says `calciotto` where renaming would break something or buys nothing: the repository, the Go module path, the Docker image, the database, the `calciotto-*` localStorage keys (renaming them would log every player out and drop their theme and active group), and the legacy domains. The word "calciotto" in comments and in the manifest description is the sport (8-a-side football), not the brand. The `BREVO_SENDER_NAME` GitHub variable overrides the mailer's default sender name, so it must say Agoran too.

## Commands

### Dev environment (all services)
```bash
cd devops
docker compose --env-file env/develop.env up
```
This starts Postgres (with healthcheck), the Go backend (via `air` for live reload, port 8080), the Vue frontend (`npm ci && npm run serve`, port 4000), and a one-shot `seed` service that runs `go run ./cmd/seed` as soon as `db` is healthy. The `--env-file` flag is required — without it, `${POSTGRES_PORT}`/`${POSTGRES_PASSWORD}` and the bare `DB_NAME`/`DB_USER`/`DB_PASSWORD` refs in `docker-compose.yaml` resolve to empty strings (Compose only auto-loads a file literally named `.env` next to the compose file, which this repo intentionally doesn't ship since `.env` is gitignored). The backend and frontend containers bind-mount `../app` and `../frontend`, so local edits are picked up without rebuilding the image. The `db` service is configured from three checked-in files rather than left at the image's defaults: `devops/scripts/init.sh` runs as a `docker-entrypoint-initdb.d` hook on a fresh volume and creates the *application's* role and database (`DB_USER`/`DB_PASSWORD`/`DB_NAME`, granted `CREATEDB`) alongside the image's own superuser (`POSTGRES_USER`/`POSTGRES_PASSWORD`) — which is why both credential pairs exist in `env/develop.env` and why an empty `DB_USER` breaks startup in the way the Gotchas below describe — while `devops/configs/postgresql.conf` and `devops/configs/pg_hba.conf` are passed as `--config_file`/`--hba_file` (the former mainly for `wal_level = logical` and `log_min_duration_statement`, the latter to accept connections from outside the container).

`seed` is idempotent (`cmd/seed` skips itself once players already exist), so it's safe to run on every `up` — after the first successful run it just logs "skipping" and exits. Force a fresh reseed with `docker compose exec backend go run ./cmd/seed -reset`.

### Backend (`app/`)
```bash
go build ./...                 # build
go run .                       # run directly (needs Postgres reachable — set DB_HOST/DB_PORT/DB_USER/DB_PASSWORD/DB_NAME, see Gotchas)
go run ./cmd/seed              # populate the DB with demo players/teams/matches (skips if players already exist)
go run ./cmd/seed -reset       # wipe players/teams/matches/match_players first, then reseed
go run ./cmd/seed -matches 10  # control how many past matches get generated (default 6)
go run ./cmd/demoseed          # WIPE the dev DB and rebuild a full demo dataset dated relative to now (see "Seeding data")
```
There is no lint *script* for the Go module the way `frontend/package.json` has one — the checks are run directly by CI (see "Continuous Integration" below): `gofmt -l .` for formatting and `go run honnef.co/go/tools/cmd/staticcheck@v0.7.0 ./...` for static analysis, both runnable locally with those exact commands from `app/`. The module is clean under both.

### Frontend (`frontend/`)
```bash
npm run serve       # dev server on port 4000
npm run build       # production build
npm run lint        # eslint . (flat config in eslint.config.mjs; never rewrites files)
npm run test:unit   # Vitest unit tests, see tests/unit/
npm run test:visual        # Playwright visual regression tests, in Docker (see below)
npm run test:visual:update # same, accepting the current rendering as the new baselines
```
`tests/unit/` mirrors `src/`. Under `services/`: `activeGroup.js` (the stored active group, the stale-id/no-group fallbacks and the shared `GET /groups/me` promise), `featureStatus.js` (the feature and guide status cached per session), `datetime.js` (local-offset RFC3339 round-tripping, DST boundaries, half-hour zones, calendar days), `matchRegistration.js` (the registration states, `teamsAreComposed`, the v1 team split), `matchPrediction.js` (the prediction window, display states and `settlePrediction`'s odds − 1 / −1 arithmetic), `motmVoting.js` (the voting deadline), `shareMessages.js`, `shortLink.js` (base62 round-trips and the rejection of truncated, over-long or out-of-range codes), `pushNotifications.js`, `pwaInstall.js`, `api.js` (paths, and which calls carry no `group_id`), and the v2 page logic in `v2Auth.js`, `v2Edit.js`, `v2Home.js`, `v2Match.js`, `v2NewMatch.js` and `v2Positions.js` (including `splitByPositions`). Under `router/`: `canEditMatch` and `findGroupForMatch`. Under `components/`: the shell `App.vue`, `AppToast.vue`, `MatchesAndStandings.vue`, `PlayerGuide.vue`, `ShareButton.vue`, and each v2 page with a state machine worth pinning (`HomeV2`, `MatchView`, `EditMatchV2`, `NewMatchV2`, `RankingsV2`, `PredictionsV2`, `ProfileV2`, `InvitationV2`, `PasskeysV2`, `GearLink`, and the four auth pages). Also `config/apiBaseUrl.js`, `directives/fitTwoLines.js`, `public/sw.js` (notification wording, retiring the legacy worker) and `scripts/vercel-domains.mjs` (the committed `vercel.json` against `domains.env`). It is not a mandate for full coverage: pure logic is tested directly, components only where a state machine drives what is rendered. Vitest config is the `test` block in `vite.config.mjs`; the unit-test globals are declared for `tests/unit/**` in `eslint.config.mjs`.

**Visual regression tests** live in `tests/visual/` (Playwright, `playwright.config.js`) and are a separate suite from `test:unit`: Vitest runs in jsdom and renders no pixels, so a CSS or layout regression is invisible to it. The specs are `auth.spec.js`, `login.spec.js`, `guide.spec.js` and one per v2 area (`v2-home-match`, `v2-edit`, `v2-new-match`, `v2-predictions`, `v2-rankings`, `v2-profile`), each run on a `desktop` and a `mobile` (390 px) project. `tests/visual/__screenshots__/` **is committed**: the baselines are the assertion. A screenshot isn't the only check: tests also assert on the page (a tag's text, a count), and **every** test ends with `expectEverythingStubbed(unstubbed)` (see below).

`expectNoHorizontalOverflow(page)` (`fixtures/app.js`) is a hard assertion (`document.documentElement.scrollWidth <= clientWidth`) that mobile tests call rather than trusting the pixel diff: a slightly wider page can still look plausible in a screenshot. It exists because a row of `flex: 1` buttons without `min-width: 0` once overflowed a phone's width unnoticed.

Horizontal carousels need care, learned from several CI flakes:
- `gotoApp` forces `scroll-behavior: auto` globally: a smooth scroll triggered by a click runs before `toHaveScreenshot` starts disabling animations, so a test could capture mid-scroll, intermittently and only under the parallel load of `run-in-docker.sh` and CI.
- A carousel's **resting** position after Playwright's own auto-scroll isn't reproducible either (failures reading `captured a stable screenshot`, every differing pixel inside the carousel). `pinCarouselScroll(page, selector, 'start' | 'end')` parks it at an end stop (`0` or `scrollWidth - clientWidth`), which is exact by construction, waits for it to hold (`waitForCarouselToSettle`), then pins again so the position is the end stop of the final layout. Pin **after** waiting for whatever the click expands; calling `scrollIntoView` first lands somewhere else again. Any test that clicks a card in a carousel the screenshot covers should pin, not wait.

Four things make the screenshots reproducible, and all four are load-bearing:
- **They only ever run in one environment.** `npm run test:visual` shells out to `tests/visual/run-in-docker.sh`, which runs the suite inside `mcr.microsoft.com/playwright:v1.62.1-noble`; the `visual` job in CI uses the *same image* as its `container:`. Font rasterisation and antialiasing differ between macOS and Linux, so a baseline generated on a Mac fails against CI on every screenshot, and a loose pixel threshold would mean the suite no longer catches anything. There is deliberately **no script that runs Playwright on the host**. The image tag is pinned to the `@playwright/test` version in `package.json` (the image ships the browser build that version expects) and to the tag in `.github/workflows/ci.yml`: bump all three together. `snapshotPathTemplate` carries `{projectName}` but no `{platform}`: two viewports are a real dimension, two platforms are not. Arguments go spec file first, then flags: `sh tests/visual/run-in-docker.sh v2-edit.spec.js --update-snapshots=changed`.
- **The backend is stubbed, not run.** `tests/visual/fixtures/app.js` intercepts `http://127.0.0.1:8080/**` (the `VUE_APP_API_BASE_URL` fallback the tested bundle is built with) and serves the frozen fixtures in `fixtures/data.js`; `gotoApp(page, path, overrides)` picks the variant (role, theme, positions, a refusal...). Running the real stack would make every screenshot a fresh diff, and stubbing turns awkward states into a different fixture rather than a setup script. A **catch-all route registered first** (Playwright checks handlers newest-first) records any call that reached no stub and answers 500, and `expectEverythingStubbed` asserts that list is empty: otherwise a forgotten stub would quietly photograph an error state and pass forever.
- **The clock is frozen** at `FIXED_NOW` (2026-09-04, two days before the fixtures' kick-off) via `page.clock.setFixedTime` before `goto`. Sign-up, prediction and vote states derive from `Date.now()`, so without this the calendar decides what the screenshots contain. A fixed *time* rather than fake timers, so transitions and timeouts keep working.
- **`Math.random` is seeded** in `gotoApp`, so the automatic team split photographs the same teams every run.

The app is served from `dist/` by `tests/visual/serve-dist.js`, a ~75-line static server that reproduces `vercel.json`'s SPA rewrite (the tests deep-link into pages such as `/matches/:id`, and the router is `createWebHistory`, so without the fallback every screenshot would capture a 404). It 404s a *missing asset* rather than falling back for it, so a broken build fails visibly instead of looking like a styling bug.

When a visual diff is intentional (a deliberate design change), regenerate with `npm run test:visual:update` and commit the new PNGs **in the same commit as the CSS change** — a baseline update sitting in its own commit is indistinguishable from a rubber-stamped regression.

## Continuous Integration

CI is split across **two** workflow files, and the split is the point: `.github/workflows/ci.yml` holds the three build/test jobs and triggers on `pull_request` only, while `.github/workflows/deploy.yml` holds the two deploy jobs and triggers on `push` to `master` only. A pull request therefore lists exactly the jobs it can act on — Backend (Go), Frontend (Vue), Frontend visual regression — and nothing else.

That layout exists because **GitHub reports a job whose `if:` evaluates false as a *skipped check*, not as an absent one**. While both deploy jobs lived in `ci.yml` behind `if: github.ref == 'refs/heads/master' && github.event_name == 'push'`, every PR carried "Deploy backend (Koyeb): skipped" and "Deploy frontend (Vercel): skipped" beside its real results — noise that reads like something went wrong. The same property is what made an unrestricted `push:` trigger worth narrowing (see the paragraph below): a cancelled job is likewise reported as a *failed* check.

Splitting them must not weaken the gate, so `deploy.yml` **calls `ci.yml` directly** (`jobs.ci.uses: ./.github/workflows/ci.yml`, enabled by `workflow_call` on `ci.yml`'s side) rather than reacting to it with a `workflow_run` trigger. `workflow_run` fires on *completion*, so it would happily deploy a failed build unless an explicit `conclusion == 'success'` check said otherwise; `uses:` + `needs:` makes a failing test mechanically unable to reach a deploy step, which is exactly the property the old single-file layout had. It also keeps the three jobs defined **once**: a push to master runs that same definition through the call, not a copy free to drift from what PRs run.

The gate stays **per-job rather than all-or-nothing**, which a bare `needs: [ci]` would not give (a called workflow succeeds or fails as a unit). `ci.yml` declares one `workflow_call` output per job — `backend`/`frontend`/`visual`, each `'success'` or empty — fed by a terminal `Record result` step in each job that, having no `if:` of its own, only runs when every step before it passed. `deploy.yml`'s jobs then read those outputs under `if: always() && ...`: `deploy-backend` requires `backend` and `frontend` only, `deploy-frontend` additionally requires `visual`. `always()` is load-bearing — without it, `needs: [ci]` would skip both deploys whenever *any* job in the called workflow failed, visual included, quietly turning a screenshot diff into a backend-rollout blocker. That is the one behaviour this restructuring was most careful to preserve, and the visual suite's own history of infrastructure flakes (see "Visual regression tests" above) is why it matters in practice rather than in principle.

Neither deploy job needs an `if: github.event_name == 'push'` guard any more: `deploy.yml` only triggers on a push to `master`, so a pull request — including a fork's, which has no access to the `production` environment's secrets — cannot reach it at all.

The trade-off of PR-only triggering is explicit: **pushing a branch with no PR open runs no CI at all.** Opening the PR starts it, and a draft is enough (`pull_request` fires on drafts).

`push` used to be unrestricted on `ci.yml`, and a push to a branch with an open PR then fired *both* events for the same commit. The `concurrency` group (`${{ github.workflow }}-${{ github.head_ref || github.ref_name }}`) kept that from running every job twice, including the two Docker/Vercel builds, by cancelling the older of the two. That worked, but cancelling is not the same as never starting: the cancelled run's jobs stay attached to the commit, and GitHub counts a cancelled job as a **failed check** — so every PR carried a red X beside each green one and sat at `mergeable_state: UNSTABLE`, which reads exactly like a real failure to anyone glancing at it (and to any automation gating on it). The trigger split above removes the duplicate event at the source. The concurrency group stays on `ci.yml`, since successive pushes to a PR branch still each fire a `synchronize` event and the newer run should still cancel the older; `head_ref` is only set on a `pull_request` event, so when `deploy.yml` calls the workflow on a master push it falls back to `ref_name` (`master`), where `cancel-in-progress` is false — cutting that run off would take the deploy that needs it down with it. `deploy.yml` carries its own `concurrency: deploy-master` with `cancel-in-progress: false`, so two merges landing close together queue in merge order rather than racing a half-done Docker push or Vercel deploy.
**Every `uses:` in all three workflows sits on a major that runs on Node 24**, and that is maintained deliberately rather than drifted into. GitHub reports an action whose `runs.using` is `node20` as a deprecation **warning on every single run** — not a failure, but noise on a check list whose whole value here is that a red or odd-looking entry means something. The majors that cross over are not uniform (`checkout` at v5, `setup-go`/`setup-node` at v6, `upload-artifact` at v6, `download-artifact` at v7, `github-script` at v8, the three `docker/*` at v4/v4/v7), so "bump everything by one" is not the rule; what is pinned here is the **latest** major of each, which buys the longest runway before the next runtime deprecation repeats this. Actions are pinned to a major tag rather than a commit SHA, matching how the rest of this repo pins (the image tag, `staticcheck`, `govulncheck`): the trade-off is accepting upstream patch releases silently in exchange for not needing a bot to keep SHAs current. `koyeb-community/koyeb-actions@v2` is the one entry deliberately left alone — it is a **composite** action (`runs.using: composite`, just shell steps), so it has no Node runtime to deprecate and no newer major exists.

One consequence worth knowing, since it overlaps something documented below: **`actions/setup-go` v6+ exports `GOTOOLCHAIN=local` itself**, globally for the job. That was the breaking change in its v6 — it stops `go` from silently downloading a second toolchain when a `go`/`toolchain` directive asks for a newer version than the one the action installed. The explicit `GOTOOLCHAIN: local` on the `staticcheck` and `govulncheck` steps is therefore now redundant, and is kept anyway: it states the requirement at the step that actually depends on it, and doesn't quietly become load-bearing-by-accident on a future `setup-go` that changes its mind.

- **Backend**: `actions/setup-go` pinned via `go-version-file: app/go.mod` (not a hardcoded Go version), a `postgres:17` service container with a `pg_isready` health check backing the network connection integration tests need (see `app/internal/testutil`), then from `app/`: `go build ./...`, a **`gofmt -l .` formatting gate** (`-l` lists offenders and exits 0 regardless, so the step tests its output and fails explicitly — `-l` rather than `-w` so a formatting change always lands in a reviewed commit rather than being rewritten under CI; it was added after `internal/models/database.go` was found to have drifted with no build ever noticing), `go vet ./...`, **`staticcheck` pinned at `v0.7.0`** (what `go vet` deliberately leaves out: unused code, simplifiable constructs, stdlib misuse — pinned because a floating `@latest` turns an upstream release into a surprise red build on an unrelated PR, and because v0.8+ requires Go 1.26 and would make `go run` pull a second toolchain on every run; `GOTOOLCHAIN: local` makes that mismatch fail loudly instead of silently downloading one), `go test ./... -count=1` (every package's tests share that one database and run concurrently — safe only because schema application takes an advisory lock, see Gotchas) with `DB_HOST=localhost`/`DB_PORT`/`DB_USER`/`DB_PASSWORD`/`DB_NAME` matching the service container's own credentials, plus a placeholder `JWT_SECRET` (required by `main.go`'s fail-fast check, though no test currently reads it from the environment — they hardcode their own test secrets instead).
- **Frontend**: `actions/setup-node` at `node-version: 24` (matching `devops/docker-compose.yaml`'s `node:24-alpine`), then from `frontend/`: `npm ci` (not `npm install` — installs strictly from the committed lockfile, and cached via `setup-node`'s `cache: npm` with `cache-dependency-path: frontend/package-lock.json` — that path is not optional, since the lockfile isn't at the repo root and the action would otherwise look for `./package-lock.json`, find nothing and silently cache nothing), **`npm run lint`**, `npm run test:unit`, `npm run build` — unit tests run before the build so a broken test fails fast instead of waiting on a full Vite build.


- **Frontend visual regression**: a third job, `visual`, running *inside* `mcr.microsoft.com/playwright:v1.62.1-noble` as its `container:` — no `actions/setup-node` and no `playwright install`, because the point is that the rendering environment is byte-identical to the one that produced the committed baselines (see "Visual regression tests" above). It runs `npm ci` → `npm run build` → `npx playwright test` against the production build, and uploads `playwright-report/` as an artifact on **every** run, not just a failing one (`if: always()`) — the HTML reporter writes it either way. `trace`/`video` in `playwright.config.js`'s `use` block are both `'on'` rather than the more common `'retain-on-failure'`, specifically so a *passing* run's report is inspectable too: `toHaveScreenshot` itself only attaches its expected/actual/diff triptych when the comparison fails, so without this a green run's report would be a bare list of step titles with nothing to look at. With it, every test — pass or fail — carries a video (a literal recording of that run) and a trace (open in the report's own Trace Viewer for a DOM snapshot, the console and the network at every action), which is what actually answers "what did this test do" rather than only "did it match". Costs ~5.6 MB across the suite when it was 12 tests; it is well over a hundred now, so worth revisiting to `'retain-on-failure'` if the suite grows enough for that to matter. `deploy-frontend` gates on `[backend, frontend, visual]`, so a visual diff blocks a deploy from master too — `deploy-backend` deliberately stays at `[backend, frontend]` only, since a screenshot diff has nothing to do with the safety of a backend rollout.

The CI Postgres credentials are chosen independently of `devops/env/develop.env` (a separate, local-only dev credential set) — they only need to be internally consistent between the service container and the job's own env vars.

### Scheduled checks (weekly, master only)

`.github/workflows/scheduled-checks.yml` runs three checks every Monday at 06:00 UTC (plus `workflow_dispatch` for a manual run), and **none of them gate a pull request**, deliberately. `schedule` only ever fires on the default branch, so "on master" is true by construction rather than through an `if:` someone has to maintain.

Two different reasons for a check living here rather than in `ci.yml`:
- **`go test -race`** is ~10x a normal test run — 3 minutes against 20 seconds, measured — which is a bad trade on every PR for a codebase that has no data race today (verified: the suite passes clean under `-race`). Weekly still surfaces one within days of it being written. The concurrency actually worth watching is `InitDB`'s advisory-lock path and the rate limiter's per-IP map with its sweeper goroutine.
- **`govulncheck` and `npm audit`** fail on data published *outside* this repo. An advisory landing on a Tuesday would turn an unrelated Wednesday PR red through no fault of its author; what matters is noticing within a week, not within a push.

**`govulncheck` is pinned to `v1.1.4`, and that pin is load-bearing** in a way version pins usually aren't. govulncheck evaluates *standard library* advisories against whichever toolchain it runs under, and `@latest` (v1.8.0) requires Go ≥ 1.26 — so with the default `GOTOOLCHAIN` it silently downloads 1.26 and pronounces the stdlib clean, while the deployed image is built from `golang:1.25-alpine`. Measured on the same tree: `@latest` reported **0** findings, `v1.1.4` under Go 1.25 reported **32**, every one of them real for the binary in production. A falsely-green security check is worse than no check. Only the tool is pinned; its advisory database is fetched live on every run, so new advisories still arrive weekly. `GOTOOLCHAIN: local` makes a future mismatch fail loudly instead of papering over it — `setup-go` has already installed exactly what `go.mod` asks for.

The scheduled frontend audit runs `npm audit --omit=dev` and reports high or critical advisories affecting runtime dependencies. Run `npm audit` from `frontend/` to include the build and test toolchain.

**On failure, the `report` job opens a GitHub issue** (`permissions: issues: write`, via `actions/github-script`) carrying each failed check's actual output, not just a link to a log that expires. It labels the issue `scheduled-checks` and, while an issue with that label is open, posts later failures as **comments** rather than opening a duplicate every week — close it once handled and the next failure opens a fresh one.

There is deliberately **no frontend analogue of `-race`**: the browser code is single-threaded, so there is no data race to detect. The one frontend-specific candidate not implemented is re-running the visual suite N times to catch flakes before they surprise a PR (see "Visual regression tests" above for the two that did).

## Production deployment

Frontend on **Vercel**, backend on **Koyeb**, database on **Neon** (project `calciotto`, `aws-eu-central-1`, branch `production` — the Koyeb region `fra` is Frankfurt too, deliberately, so app-to-database latency stays local). Everything is driven from GitHub Actions: the `deploy-backend` and `deploy-frontend` jobs live in `.github/workflows/deploy.yml`, which triggers on a push to `master` and **calls `ci.yml`** as its first job, so that `needs: [...]` is still a genuine gate — a failing Go test, Vitest test, or (for `deploy-frontend` only, which additionally requires the `visual` output) a visual regression makes deployment impossible. They used to sit in `ci.yml` itself for exactly that reason; the move out is about what a *pull request* displays, not about the gate, and it deliberately uses `uses:` rather than a `workflow_run` trigger — the latter fires on *completion* and would need an explicit `conclusion == 'success'` check to avoid deploying a broken build. See the CI section above for the full rationale, including why the gate is read per-job from `ci.yml`'s `workflow_call` outputs instead of from a bare `needs: [ci]`. Both jobs target the `production` GitHub environment and need no event guard of their own, since the workflow they live in only ever triggers on a push to master; a pull request never deploys, and a fork's PR has no access to that environment's secrets anyway.

### Backend (Koyeb)
`devops/Dockerfile.prod.backend` is the deployable image — `devops/dockerfile.dev` runs `air` against a bind-mounted tree and is not. It builds from the **repository root** (it needs `app/`), so `.dockerignore` at the root is what keeps `frontend/node_modules` out of the build context. Two details are load-bearing:
- The runtime stage installs **`ca-certificates`**, which the base `alpine` image does not ship. Both outbound TLS clients need it — Neon refuses plaintext connections, and Brevo's API is HTTPS — and without it the app starts fine and then fails every query and every email with `x509: certificate signed by unknown authority`.
- The build stage is pinned to `golang:1.26.11-alpine`, matching `app/go.mod`'s `go 1.26.11`. An older base fails outright at `go build`, and the *patch* level in the `go` directive is deliberate and not cosmetic: `govulncheck` reports every unfixed standard-library advisory against whatever patch release the toolchain is, and `go 1.25.0` was carrying 31 of them (`crypto/tls`, `crypto/x509`, `net/http`, `net/url`, `net/mail`, `encoding/pem`, …, all reachable through gorm/pgx/gin). Raising the directive is what pins the floor for both this build and CI's `setup-go` (`go-version-file: app/go.mod`), so the directive, this image tag and govulncheck's pin below move together.

The image is tagged with both `${{ github.sha }}` and `latest`, and the **SHA tag is what gets deployed**: `:latest` alone gives no rollback target and does not reliably tell Koyeb that anything changed.

`main.go` gained three deployment affordances:
- `PORT` (default `8080`) instead of a hardcoded `r.Run(":8080")` — the host assigns it.
- `allowedOrigins()` reads `CORS_ALLOWED_ORIGINS` (comma-separated) and falls back to the local dev origins when unset *or* entirely blank. The fallback rather than an empty slice is deliberate: gin-contrib/cors with no allowed origin and `AllowAllOrigins` false rejects every cross-origin request, which would be a silent outage instead of a startup failure.
- `GET /health`, wired as Koyeb's healthcheck (`--checks 8080:http:/health`). It deliberately does **not** touch the database: the platform restarts an instance whose healthcheck fails, so reporting unhealthy on a transient database hiccup (Neon waking from scale-to-zero, a pooler blip) would turn a few slow seconds into a restart loop. `InitDB` already fails fast at startup if the database is unreachable, which is the check that matters.

The route is `/:8080`, **not** `/api:8080`: Koyeb passes the route path through unchanged, so an `/api` prefix would reach Gin as `/api/auth/login` and match none of its routes. The frontend lives on its own domain; Vercel's `/api/auth/*` rewrite strips the `/api` before forwarding to Koyeb's `/auth/*` (see "Sessions" below).

Secrets are synced GitHub → Koyeb by the workflow before each deploy, then referenced in the service definition as `--env NAME=@NAME`. GitHub is the source of truth, but Koyeb needs its own copy because these are read at *every container start*, not only at deploy time. The CLI has no upsert, and `koyeb secrets get` cannot tell whether a rewrite is needed — it masks the value as `*****` — so the step runs `koyeb secrets reveal`, compares that to the GitHub value, and writes only when the secret is missing (`secrets create --value-from-stdin`) or the value differs (`secrets update --value-from-stdin`). Stdin keeps the value out of the process argument list; reveal's stdout (the raw value, plus the one trailing newline the CLI appends, which is stripped before the comparison) is compared with `cmp` from a mode-600 file and never printed. Skipping an unchanged rewrite is load-bearing: on 11 Nov 2026 (run 43053082184, both attempts) the step updated all six secrets and `services update` ran a few seconds later, and Koyeb failed the deployment at provisioning with every secret reported missing (`secret:workspace:jwt_secret` and the rest, names lowercased) even though the secrets existed and the `@NAME` refs were the same ones the previous successful deploy had used. When a secret was actually written, the deploy step waits 20s before provisioning. `services update` is not chained with `|| services create` any more: `services get` is the existence check, and an update that fails on a service that already exists fails the job with that deployment error instead of falling through into a create the free-instance quota then rejects with "maximum number of instances of type free". `BREVO_API_KEY` is the one optional secret: without it the app keeps logging reset links instead of emailing them (see `internal/services/mailer.go`), a degraded but working state, so the job warns rather than failing.

### Frontend (Vercel)
Deployed by the CLI from Actions, not by Vercel's Git integration — `frontend/vercel.json` sets `"git": {"deploymentEnabled": false}` so a push can't trigger a second, ungated deployment in parallel. The job runs `vercel pull` → `vercel build --prod` → `vercel deploy --prebuilt --prod`, authenticating with `VERCEL_TOKEN` plus `VERCEL_ORG_ID`/`VERCEL_PROJECT_ID` in the environment (which is what replaces an interactive `vercel link`). The Vercel project's **Root Directory must be set to `frontend`**; that is what makes `frontend/vercel.json` the config Vercel reads.

`vercel.json` also carries the SPA rewrite (`/(.*)` → `/index.html`). The router is `createWebHistory`, so without it a refresh on `/profile` or a visit to an emailed `/reset-password?token=…` link returns a Vercel 404. It is expressed as a `rewrite` rather than a `route` precisely because rewrites apply only after the filesystem check, leaving static assets alone.

Vite reads the existing `VUE_APP_API_BASE_URL` and `VUE_APP_API_TIMEOUT_MS` through `import.meta.env`. The `envPrefix` in `frontend/vite.config.mjs` keeps those names available to the client build. The API URL defaults to `http://127.0.0.1:8080` in local development.

Because `vercel build` runs the framework build with the environment from `.vercel/.env.production.local` (what `vercel pull` writes) rather than with the job's arbitrary env vars, the workflow **appends** the value to that file after pulling. That keeps GitHub the single source of truth instead of duplicating the setting in the Vercel dashboard.

### Domains (agoran.app)
The app lives on `https://club.agoran.app` (front) and `https://api.agoran.app` (API), and every setting names those two alone. The legacy front, `https://calcio-otto.vercel.app`, only redirects to the new one. The legacy API host, `https://calciotto.koyeb.app`, still answers because it is Koyeb's own name for the same service, but nothing points at it any more.

The four origins have their defaults in **one place**, `devops/env/domains.env` (`LEGACY_FRONTEND_ORIGIN`, `LEGACY_API_ORIGIN`, `NEW_FRONTEND_ORIGIN`, `NEW_API_ORIGIN`), next to the switch `LEGACY_FRONTEND_REDIRECT` (`true` or `false`; anything else fails the deploy). A repository/environment variable of the same name overrides each one. `devops/scripts/domain-env.sh` reads them (rejecting anything that isn't a bare `https://host` origin) and prints the derived settings, each of which can itself be overridden by a variable of its own name:

| Setting | `LEGACY_FRONTEND_REDIRECT=true` (the default) | `false` (the way back) |
| --- | --- | --- |
| `CORS_ALLOWED_ORIGINS` (CORS, the Origin check on the session routes, the passkey RPs, the reset link's origin) | `https://club.agoran.app` | both fronts |
| `VUE_APP_API_BASE_URL_BY_HOST` | `club.agoran.app=https://api.agoran.app` | plus `calcio-otto.vercel.app=https://calciotto.koyeb.app` |
| CSP `connect-src` | `'self' https://api.agoran.app` | plus `https://calciotto.koyeb.app` |
| `redirects` in `vercel.json` | the legacy host's, below | none |
| `FRONTEND_BASE_URL`, `VUE_APP_API_BASE_URL`, `AUTH_PROXY_TARGET` | the new pair | the new pair |

- `FRONTEND_BASE_URL` is the front a reset link uses when the request's Origin isn't an allowed one (see "Auth" below).
- One Vercel build serves every front host: `src/config/apiBaseUrl.js` picks the API by `window.location.hostname` from `VUE_APP_API_BASE_URL_BY_HOST`, and falls back to `VUE_APP_API_BASE_URL` for any other host (a preview, say).
- `AUTH_PROXY_TARGET` is the destination of the `/api/auth/*` rewrite in `vercel.json`, server to server. `api.agoran.app` must therefore resolve, or logging in, signing up and resetting a password all fail.
- **The legacy redirect** is one `redirects` rule, conditioned on the `calcio-otto.vercel.app` host, sending every path but one (`/((?!sw\.js$).*)`) to the same path on `club.agoran.app`. Vercel applies redirects before rewrites and keeps the query string, so a shared `/m/:code`, `/signup?invite=` or `/reset-password?token=` link still lands on the right page. It is a **307**, not a 308: browsers cache a permanent redirect, which could then not be taken back. Setting the GitHub variable `LEGACY_FRONTEND_REDIRECT` to `false` and redeploying brings back both fronts side by side, with no code change.
- **`/sw.js` is left out of the redirect** so that a service worker installed on the legacy host can still fetch its update (the browser checks on a visit, even a redirected one, and on a push or a notification click). On `calcio-otto.vercel.app` (`LEGACY_HOST` in `public/sw.js`, kept equal to `LEGACY_FRONTEND_ORIGIN` by `sw.spec.js`) the new worker unsubscribes from push and unregisters at `activate`, so a player who turns notifications on again on `club.agoran.app` does not get every push twice. The backend deletes the dead subscription the next time a push to it answers 404/410. The retirement depends on the host, not on `LEGACY_FRONTEND_REDIRECT`: after a switch back to `false`, push notifications do not work on the legacy front (its worker retires as soon as it activates) until `LEGACY_HOST` is changed. Accepted, since that switch is an emergency path.

Both deploy jobs run the script: the backend job appends its output to `$GITHUB_ENV` before the Koyeb step, the frontend job writes the two `VUE_APP_` values to `.vercel/.env.production.local` and runs `frontend/scripts/vercel-domains.mjs`, which rewrites the CSP `connect-src` (`'self'` plus every API origin), the auth rewrite destination and the `redirects` list (which it owns entirely) in `vercel.json`. The committed `vercel.json` equals that script's output for the defaults; `tests/unit/scripts/vercel-domains.spec.js` fails otherwise, so a change to `domains.env` must be followed by running `domain-env.sh` and then `node frontend/scripts/vercel-domains.mjs` with its output in the environment.

The switch was made together with the launch of push notifications and the install card (#79), deliberately. Push subscriptions (bound to the origin's service worker), the installed PWA, the session (the token in `localStorage`, the host-only refresh cookie) and passkeys (RP ID = host, stored with their `rp_id`) all belong to one origin. Launching push and the install card on the domain players were about to leave would have meant re-subscribing and reinstalling a few days later, with duplicated notifications for anyone subscribed on both. Each player logs in once on the new domain, and a passkey made on the legacy one has to be made again. Share and invite links use `window.location.origin`, so they are all `club.agoran.app` links now.

### Configuration inventory
Set on the `production` GitHub environment. Secrets: `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`, `KOYEB_API_TOKEN`, `DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `JWT_SECRET` (must be generated fresh for production — never the one in `devops/env/develop.env`), `BREVO_API_KEY` (optional), `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`, `SIGNUP_RATE_LIMIT_PER_HOUR`/`SIGNUP_RATE_LIMIT_BURST` (optional overrides — see "Rate limiting" above). Variables: `DOCKERHUB_IMAGE`, `CORS_ALLOWED_ORIGINS`, `TRUSTED_PROXIES` (optional — the load balancer's own IPs/CIDRs, see "Rate limiting" above; unset falls back to the private/loopback ranges), `FRONTEND_BASE_URL`, `VUE_APP_API_BASE_URL` (these three, plus `VUE_APP_API_BASE_URL_BY_HOST` and `AUTH_PROXY_TARGET`, are optional overrides of what `devops/scripts/domain-env.sh` derives — see "Domains" above), `LEGACY_FRONTEND_ORIGIN`/`LEGACY_API_ORIGIN`/`NEW_FRONTEND_ORIGIN`/`NEW_API_ORIGIN`/`LEGACY_FRONTEND_REDIRECT` (optional), `BREVO_SENDER_EMAIL`, `BREVO_SENDER_NAME`, `VUE_APP_API_TIMEOUT_MS` (optional, perf-load-test-only — see `api.js` above), `VAPID_PUBLIC_KEY`, `VAPID_SUBJECT` (the bare contact email, for example `bref.tibo@gmail.com`, or an https URL — no `mailto:` prefix) and the secret `VAPID_PRIVATE_KEY` (optional, push notifications — see "Push notifications" below). At the **repository** level rather than in that environment: the secret `NOTIFICATIONS_TICK_SECRET`. `deploy.yml` copies it to Koyeb on each deploy, and the GitHub secret value must match the one configured in cron-job.org, which calls `POST https://api.agoran.app/internal/notifications/tick` every minute with header `Authorization: Bearer <NOTIFICATIONS_TICK_SECRET>`. The repository variable `BACKEND_URL` was read only by the removed tick workflow and may now be unused. The URLs/addresses among these are variables rather than secrets to keep them readable in build logs, which is what you want when diagnosing a CORS rejection; the two perf-test overrides are variables/secrets for the same reason their non-perf-test counterparts (`CORS_ALLOWED_ORIGINS`, `JWT_SECRET`) are split the way they are — a rate limit is sensitive enough to gate like a secret, a client-side timeout is not.

The database role in `DATABASE_URL`/`DATABASE_URL_UNPOOLED` must **own** the tables (or be a member of the role that does). `AutoMigrate` issues DDL at *every* boot, so a role with only read/write grants starts fine, reports `Successfully connected to the database!`, and then dies on the first `ALTER TABLE` with `must be owner of table … (SQLSTATE 42501)` — ownership is not a privilege that `GRANT ... ON TABLE` confers. Neon projects come with two roles (here `calciotto_owner` and `calciotto`); the secrets use the owner. The alternative, if you want the app on a non-owner role, is `GRANT calciotto_owner TO calciotto;` — Postgres accepts an ownership check from any *member* of the owning role.

There is **no seeding step in production**: `cmd/seed` is a development tool, and the schema is created by `AutoMigrate` on first boot (through `DATABASE_URL_UNPOOLED`, off the pooler).

## Architecture

### Backend layering
Strict `handlers/` → `services/` → `models/` layering:
- `internal/handlers/*.go` — Gin controllers only: bind JSON, call the service, map errors to HTTP status/JSON. No business logic here.
- `internal/services/*.go` — one service struct per entity (`PlayerService`, `TeamService`, `MatchService`, `MatchPlayerService`, `MatchRegistrationService`, `StandingsService`), each wrapping a `*gorm.DB`.
- `internal/models/database.go` — GORM models (`Player`, `Team`, `Match`, `MatchPlayer`, `MatchRegistration`), all embedding `BaseModel` which generates a `uuid.UUID` ID (`github.com/google/uuid`) in a `BeforeCreate` hook. All FK-style fields (`MatchPlayer.MatchID/TeamID/PlayerID`) are `uuid.UUID`, not `string` — comparisons against "no value" use `uuid.Nil`, not `""`.
- `internal/models/date.go` — `Date` is a `time.Time`-backed type used everywhere a calendar day is stored (`Match.Date`, DTO date fields). It marshals/unmarshals as `"YYYY-MM-DD"` over JSON (matching the original string-based API contract exactly) and scans/values as a SQL `date` column — this is why `Match.Date` could switch from `string` to a typed date without changing the wire format or requiring frontend changes. `DateOf(time.Time) Date` truncates a timestamp to its calendar day **in the timestamp's own location**, which is how `CreateMatch` derives a scheduled match's `Date` from its kick-off: normalizing to UTC first would move a kick-off near midnight onto the adjacent day.
- `internal/models/customModels.go` — DTOs used only for the "match with nested teams/players" API shape (`MatchWithDetails`, `TeamWithPlayers`, `PlayerCustom`) plus a flat row struct (`RowsMatchDetails`) used to scan the raw SQL join in `matches.go`, plus `MatchRegistrationEntry` (one line of a scheduled match's sign-up list, `Position`/`IsWaiting` derived rather than stored). IDs are `uuid.UUID`, dates are `Date`.

There is **no `MatchPlayerHandler`**, and no HTTP path of any kind to create or edit a standalone `MatchPlayer` row — `MatchService.UpdateMatch`'s diff is the only way `match_players` rows ever get written. `MatchPlayerService` (`internal/services/matchPlayers.go`) does exist and is fully implemented, but nothing in `internal/handlers/` references it: its only callers are `cmd/seed` and `cmd/richseed`, which compose rosters directly through the service layer. `TeamHandler` is partially wired: `GET /groups/:id/teams` (any member) and `PATCH /groups/:id/teams/:teamId` (admin-only, renames) exist, but there is still no route to create a standalone `Team` — the only way a `Team` row is created is as one of the two teams `GroupService.CreateGroup` makes alongside a new group.

Every handler that reads an ID from the URL (`c.Param("id")`, etc.) parses it with `uuid.Parse` and returns 400 on failure before calling the service — service methods take `uuid.UUID`, never a raw path string.

### Auth, password reset and account deletion
`POST /auth/signup` calls `AuthService.SignupSession` to create a new `Player`, group membership, and browser session in one transaction. The response returns the player ID and an access token. The player uses the same browser session flow as after login. Display names may be shared by several accounts.

Signup requires an active group invitation. The service checks its code before hashing the password and rechecks it under the group row lock before writing the membership. Missing, expired, revoked, or unknown codes return 400. Codes are case-insensitive. Revoking a code (`Group.InviteExpiresAt`) stops it at once; an active one never expires (see "Group bootstrapping" below).

`AuthService.Signup(playerID, email, password)` still attaches credentials to an existing test or seed player. HTTP login calls `LoginSession`. See [Browser sessions and group invitations](README.md#browser-sessions-and-group-invitations) for the session and deploy contract.

#### Passkeys

- Passkeys are off by default. An administrator enables `passkeys` in `player_features` for a player (`design-v2` used to be required too; it is launched now, see "Hidden features"). Eligible players add or remove their passkeys under **Profile → Manage account → Passkeys**. Enrollment asks for their current password.
- The signed-out screen offers **Log in with a passkey** on a browser that has already seen an eligible signed-in account. The first sign-in on a new browser uses the password. The API checks both flags on every passkey enrollment and sign-in. Removing either flag disables passkey use for that account. The password stays available for sign-in and recovery.
- The API uses WebAuthn for discoverable credentials with user verification required. `CORS_ALLOWED_ORIGINS` supplies the exact permitted frontend origins. The RP ID is each frontend hostname. Passkeys work over HTTPS and on `http://localhost` for local testing. The browser and the installed app use the same origin.
- Enrollment uses authenticated `POST /players/me/passkeys/options` and `POST /players/me/passkeys`. Login uses `POST /auth/passkeys/options` and `POST /auth/passkeys/login` through the same-origin `/api/auth` proxy. A successful assertion starts the same renewable browser session as password login. The device verifies the player and holds the private key. The server stores the public credential in `passkeys`.
- The database holds the five-minute challenges so every backend instance can verify them. A finish request consumes its challenge once. Enrollment challenges are bound to the player and the version of their credentials. A password reset or account deletion removes the player's passkeys and pending enrollments in the same transaction.

The reset flow is deliberately non-committal about what exists:
- `ForgotPassword(email)` emails a reset link when the address matches a player. With the mailer configured, `POST /auth/forgot-password` returns the same 200 response for known and unknown accounts, including after a delivery failure. It returns a generic 503 before a database lookup when the mailer is unconfigured.
- `ResetPassword(token, newPassword)` collapses *every* token failure — unknown, expired, already used, player since deleted — into the single `ErrInvalidResetToken` → 400. Empty password is `ErrPasswordRequired` (the sentinel `Signup` already uses) → 400, and a password shorter than `minPasswordLength` is `ErrPasswordTooShort` → 400 (see just below). Both are checked *before* the token is looked up, so a too-short password doesn't burn the link over a typo.

**Password policy** — the two paths where a caller *chooses* a password, `SignupNewPlayer` and `ResetPassword`, both go through `validateNewPassword` (`internal/services/auth.go`): empty is the pre-existing `ErrPasswordRequired`, and fewer than `minPasswordLength` = 8 runes is the new `ErrPasswordTooShort`, mapped to 400 in `AuthHandler.Signup`/`ResetPassword` right next to `ErrPasswordRequired`. Before this the only rule anywhere was "not empty", so a one-character password was accepted. Length is counted in runes rather than bytes, so a non-ASCII passphrase isn't waved through on byte count alone, and the sentinel's message is built with `fmt.Errorf` from the constant so raising the floor can't leave the wording behind. Three callers are deliberately *not* covered: `Login` (it must only ever compare a hash — validating a format there would lock out every account whose password predates the policy), `DeleteAccount` (its password is a confirmation of an existing one, not a new choice), and `AuthService.Signup` (wired to no route, used only by test/seed fixtures). This matters more here than in an app with account lockout or 2FA, since neither exists — the limiters on `/auth/login` (see "Rate limiting" below) only bound how fast one client, and how many failures per account, can guess. There is no client-side `minlength` on `SignupV2.vue`/`ResetPasswordV2.vue`; a short password is refused by the backend and the 400's message is what the page's toast shows, as a sentence ("Password must be at least 8 characters long.").
- A successful reset updates `Player.PasswordHash` **and** marks every unused `PasswordResetToken` of that player as used, in one transaction: requesting a second reset email must not leave the first link live.

`models.PasswordResetToken` stores only the **SHA-256 hex digest** of the raw token, never the token itself. That's a deliberately different choice from `Player.PasswordHash` (bcrypt): a reset token is 32 random bytes, so there is nothing to brute-force and bcrypt's cost buys nothing; a human-chosen password is the opposite case. Raw tokens are `base64.RawURLEncoding` so they drop straight into a query string, and live one hour (`passwordResetTTL`).

Password reset email requires `BREVO_API_KEY` and `BREVO_SENDER_EMAIL`. `BREVO_SENDER_NAME` defaults to Agoran, and the reset link points to the request's `Origin` when it is one of `CORS_ALLOWED_ORIGINS` (`ResetLinkBase`), else to `FRONTEND_BASE_URL`. The raw link only goes to the mailer. Delivery failures emit a generic log message, and the integration tests capture the link with a test mailer.

Without a mailer configured (`docker compose` and CI set no Brevo variables), `POST /auth/forgot-password` answers **503** for every email, before any lookup, rather than logging the link: reset by email simply isn't available locally. The admin "invite a ghost player by email" flow that once also issued reset tokens has been removed along with the rest of the ghost-player feature (see "Group bootstrapping" below), so `ForgotPassword` is the only producer.

**JWT revocation.** `Player.TokenVersion` (`internal/models/database.go`) is a per-player counter, stamped into every freshly-issued token by `GenerateToken` (one extra indexed lookup, at issuance time only) and re-checked against the database by `ParseToken` on every authenticated request (one more indexed lookup, this time on the hot path — the trade-off a stateless JWT's own "no revocation" property requires, since there is no other way to invalidate a token before it expires on its own). A mismatch is `ErrInvalidToken`, the same sentinel an expired or forged token gets — revocation isn't distinguishable from any other reason a token stops working, the same "collapse the failure modes" posture `ErrInvalidCredentials`/`ErrInvalidResetToken` already take elsewhere in this file. `ResetPassword` and `DeleteAccount` both bump it (`token_version + 1`, a SQL expression rather than read-then-write, so two concurrent bumps can't race and lose one), which is the actual point of each: a stolen token must not outlive its own victim's password change, and an anonymized (deleted) account must not still authenticate through routes that only ever checked `player_id`. No migration/backfill was needed adding the column — a token issued before it existed carries no `token_version` claim at all, which decodes as Go's zero value (`0`), identical to what the column defaults every pre-existing row to.

**Last activity.** `Player.LastSeenAt` (nullable `timestamptz`, `json:"-"`) is when the player last used the app, not when they last typed a password — a session lasts days, so a login timestamp would say little. `AuthMiddleware` calls `AuthService.TouchLastSeen` after a token is accepted, on every authenticated request, and only logs a failure rather than failing the request. It writes at most once per `LastSeenThrottle` (5 min) per player: a per-process cache skips the query entirely, and the `UPDATE` only matches a value older than that, so several replicas don't each rewrite it. It uses `UpdateColumn`, so `updated_at` doesn't move. `NULL` means not seen since the column was added (no backfill). `DeleteAccount` clears it with the rest of the anonymization. **No route exposes it yet**, by product decision: read it in SQL (`SELECT name, last_seen_at FROM players ORDER BY last_seen_at DESC NULLS LAST`).

Logging out is still purely client-side (`clearToken()` in `api.js`) — this app has no "log out everywhere" affordance, and a plain logout doesn't bump `TokenVersion` (it's a voluntary client-side action, not a compromise response, and there is nothing left to protect against on that one device). Only the two events above bump it.

**Deleting your own account.** `DELETE /players/me` (`authRequired` only — same reasoning as the other two `/players/me` routes: it acts on the JWT's own player id, so there is no single `group_id` to authorize against) is `AuthHandler.DeleteAccount` → `AuthService.DeleteAccount(playerID, password)`. It lives on `AuthHandler` rather than `PlayerHandler` because it is fundamentally a credential-lifecycle action, the same reasoning that already puts `Login`/`Signup`/`ResetPassword` there. The body carries the caller's **current password** as a safety confirmation — this is the one truly irreversible self-service action in the whole app, unlike reopening sign-ups or demoting an admin, both of which can be undone — checked with the same `bcrypt.CompareHashAndPassword` `Login` uses. A wrong password and an unknown player both collapse into `ErrInvalidCredentials` → 400 (mapped alongside `ErrPasswordRequired`), the same "don't tell the caller which check failed" posture `Login` takes with its own two failure modes, though in practice only "wrong password" is reachable through the route, since the player always comes from an already-validated JWT. Success answers `{"deleted": true}`, the same convention as `LeaveGroup`'s `{"left": true}`. It is one of the three callers deliberately **not** covered by the password policy above: the password here confirms an existing credential, it isn't a new choice.

**The `Player` row is anonymized, never deleted**, and that is forced rather than preferred: `MatchPlayer` and `MatchVote` both hold a real FK to `players(id)` with no `ON DELETE CASCADE` (the same kind of FK `MatchService.DeleteMatch` already has to work around for `matches(id)`), so a genuine row delete would either fail outright or, if forced first, corrupt every *other* player's shared match history — goals scored, MVP awards — in every match this player ever took part in. Stripping `Name` to `deletedAccountName` (`"Deleted account"`), `Email` to `NULL` and `PasswordHash` to `""` is what actually satisfies "this account no longer exists" without touching a single match record. `TokenVersion` is bumped in the same statement (see "JWT revocation" just above): nothing about `player_id` — the only claim a token carried before that column existed — becomes invalid just because the row was anonymized, so without the bump a JWT issued moments earlier would keep reading and acting for the rest of its 7-day life.

What *is* deleted outright, all inside the one transaction: every `GroupMembership`, every `PasswordResetToken` (nothing left to reset a password on), every `MatchRegistration` (a pending intention to show up, safe to drop — unlike a `MatchPlayer` row, which is historical record), every `MatchVote` **cast by** this player, and every `MatchPrediction` they made (their own guesses, same footing as a vote cast — kept, they'd leave a "Deleted account" row on the prediction leaderboard), every `PlayerFeature` row (the hidden features enabled for them, see "Installable app (PWA)" below), and every `PushSubscription` (the devices they got notifications on) and every `NotificationPreference` (which of those notifications they had turned off, see "Push notifications" below). Votes *for* them as MVP are deliberately left alone: like a `MatchPlayer`'s goals, they are a fact about a match that already happened, not something tied to the voter's account still existing. Admin succession mirrors `LeaveGroup`'s rule — in each group where this player was the only admin, the oldest remaining member is promoted first — with one deliberate divergence: a group where they were the only *member* is left with nobody, rather than refused the way `LeaveGroup`'s own `ErrLastMember` refuses a voluntary departure, since there is no "hand the group off first" option once the account itself is going away.

Frontend side, the **Danger zone** at the bottom of the Account page (`/profile/account`, `ProfileV2.vue`) holds the button, kept apart so an irreversible action doesn't sit next to routine ones. A confirmation (a pop-up on a desktop, a bottom sheet on a phone) collects the password, calls `deleteMyAccount(password)` (`api.js`), then `clearToken()` and `window.location.href = '/login?accountDeleted=success'` — a full navigation out of the app rather than a router push, since every routed view would otherwise fail on its next request. `LoginV2.vue` turns that query param into a confirmation notice, exactly the hand-off `?reset=success` already uses. A failure leaves the confirmation open with the backend's message and the session intact.

**Sessions.** Login and signup start a server-side session (`models.AuthSession`, `internal/services/sessions.go`, `internal/handlers/sessions.go`): the response carries a short access token (15 minutes, the JWT every other route checks, kept in `localStorage` by `api.js`) and sets a refresh cookie (`HttpOnly`, `SameSite=Strict`, `Path=/api/auth`, `Secure` when `GIN_MODE=release`) that `POST /auth/refresh` rotates for a new access token, for up to 7 days. The cookie is first-party because the frontend reaches every `/auth/*` route through Vercel's `/api/auth/*` rewrite to Koyeb (`frontend/vercel.json`; the dev server proxies the same path) rather than calling Koyeb cross-site. `/auth/refresh` and `/auth/logout` also refuse an unknown `Origin` and require the `X-Session-ID` header, which a cross-site form cannot send. `POST /auth/logout` ends the session server-side. The access token is still readable by any script on the page, but only for 15 minutes.

**Rate limiting** (`internal/handlers/ratelimit.go`) covers the eight `/auth/*` routes (signup, login, the two passkey login steps, refresh, logout, forgot-password, reset-password), all through `ProxiedRateLimit` since the frontend reaches them through Vercel's `/api/auth` rewrite, plus passkey enrollment under `/players/me/passkeys`, which goes straight to Koyeb and keeps a plain per-IP `RateLimit`. They are the whole unauthenticated attack surface: every other route in the app requires `authRequired`, and the only exception left is `GET /health`, which touches nothing (deliberately — see "Production deployment" below). `GET /groups` and `GET /groups/:id` used to be unauthenticated as well — read-only public data behind a DTO (`Group.InviteCode` is `json:"-"`), so nothing in the *body* was dangerous per se, but unscoped and anonymous they let anyone on the internet enumerate the name of every group in the system with a single request, which is never something this app wanted and never something the frontend relied on (it only ever calls `GET /groups/me`). Both carry `authRequired` now, and both are scoped: `GET /groups` lists only the caller's own groups and `GET /groups/:id` requires membership of that group. `GET /players` and `GET /players/search` used to be the other two: unauthenticated and, worse, letting anyone enumerate every player's name and id system-wide with no group scoping at all. Neither was called from the frontend any more (player pickers use the group-scoped `getGroupMembers`), so they were removed outright rather than gated, closing the enumeration surface with nothing to migrate. `RateLimit(r rate.Limit, burst int)` (`golang.org/x/time/rate`) is a per-client-IP token bucket — one `*rate.Limiter` per distinct `c.ClientIP()`, held in an `ipRateLimiter` map that a background goroutine sweeps every `ipRateLimiterIdleTTL` (2 hours) so a public endpoint's IP set doesn't grow the process's memory forever. Each route in `main.go` gets its own instance (its own map, its own budget) rather than sharing one: `Login` (~10/min, burst 10) is the main target — bcrypt already slows down one guessed password, but not a script making thousands from one IP — while `Signup`/`ForgotPassword`/`ResetPassword` (~5/hour, ~5/hour, ~20/hour) are throttled mainly so none of them can be turned into a spam or cost vector (`ForgotPassword` in particular shares a budget with Brevo's 300-email/day free tier, see "Production deployment" above). This is IP-level and deliberately coarse — it does not distinguish a wrong password from a right one, so a legitimate user mistyping their password a few times shares the same budget as an attacker, which is why the burst is generous rather than tight. It is also **not** a substitute for the missing account lockout/2FA a larger app might want; it only bounds how fast one IP can try.

**Behind Vercel's rewrite, `c.ClientIP()` is Vercel, not the player**, so the `/auth/*` routes use `ProxiedRateLimit` rather than `RateLimit`. A plain per-IP bucket would be shared by every player arriving through the same Vercel address: ten bad logins from anyone would lock everyone out of login, five forgot-password requests would block every reset for an hour. `ProxiedClientKey` instead keys the client on the `X-Forwarded-For` hop just left of `c.ClientIP()`, the address Vercel received the request from. That hop is only trustworthy for requests that really came through Vercel: someone calling Koyeb directly can write anything there. So the peer (`c.ClientIP()`) also gets its own bucket, `proxyPeerFactor` (6) times the per-client budget, which caps how much forging a new hop per request can buy. With no forwarded hop both keys are the peer and it behaves exactly like `RateLimit`. A full table (`maxRateLimitBuckets`) evicts an arbitrary bucket rather than refusing newcomers, so spraying keys can only make a limit more lenient for one caller, never lock new ones out.

**Login also has two per-account limits** (`AuthHandler.loginByAccount`/`loginFailures`, keyed on a hash of the normalized email). The tight one (burst 12, one per minute) is per account *and* client, so someone guessing at a player's password only ever locks themselves out, not the player. The wide one (burst 100, one per 30 s) is per account alone and is only charged on a wrong password, so guesses spread over many addresses still run out while a player who knows their password is never charged for logging in. Forgot-password has its own per-account limit (3, one per 30 minutes) that answers the usual 200 rather than a 429, so it reveals nothing about the account.

**`c.ClientIP()` is only trustworthy because `handlers.ConfigureTrustedProxies(r)` runs first** (`internal/handlers/trustedproxies.go`, called from `main.go` right after `gin.Default()`), and without it every limiter above was decorative. gin's default `trustedProxies` is `["0.0.0.0/0", "::/0"]` — it trusts *every* caller, the client included — so `c.ClientIP()` returned whatever address the request's own `X-Forwarded-For` began with, and a script rotating that header got a brand-new, unpenalized bucket on every single request to all four routes. The policy settled on is "trust the immediate proxy, and only it": `TRUSTED_PROXIES` (comma-separated IPs/CIDRs, parsed the same way `allowedOrigins()` parses `CORS_ALLOWED_ORIGINS`) when set, the loopback + RFC1918/RFC4193 private ranges when unset — which is what both `docker compose` (bridge network) and a platform load balancer reaching the container over its internal network look like, while a request arriving straight off the public internet has a public peer address and is therefore never believed. Trusting the proxy is not the same as trusting the header: gin walks `X-Forwarded-For` right-to-left and returns the right-most address that isn't itself a trusted proxy (`Engine.validateHeader`), so the hops a client prepends are skipped in favour of the one the proxy appended. `RemoteIPHeaders` is narrowed to `X-Forwarded-For` alone, dropping gin's default `X-Real-IP`, which carries a single address with no chain to validate and would therefore be believed verbatim from a trusted peer — the exact property being removed here.

`TRUSTED_PROXIES=none` is the explicit "believe nobody" setting (spelled out, not an empty string, so a blank env var can't silently change the policy): `c.ClientIP()` then always reports the real TCP peer. It is deliberately **not** the default even though it is the strictest option — behind a load balancer every visitor shares that one peer address, so it would put the whole internet in a single bucket and cap signups at 5/hour globally. For the same reason, if the platform's LB should turn out to have a *public* address (not in the default private ranges), the failure mode is the conservative one: the header is ignored, every caller shares the LB's bucket, and the fix is to set `TRUSTED_PROXIES` to its range — it fails toward over-limiting, never toward spoofability.

Signup defaults to 5/hour per IP with a burst of 5. Set `SIGNUP_RATE_LIMIT_PER_HOUR` and `SIGNUP_RATE_LIMIT_BURST` on the local Go process for the performance test. The deployment workflow also accepts these as optional environment settings.

### Group bootstrapping (invite codes and roles)
Every group carries an `InviteCode` (`models.Group`, 8 characters over an alphabet with no `0/O/1/I/L`, `uniqueIndex`, `json:"-"`), generated by `GroupService.CreateGroup`, which stays agnostic about who created the group. A code **never expires**: it works until an admin generates a new one or revokes it (`GroupService.ChangeInvitation`, `POST`/`DELETE /groups/:id/invite-code`). `Group.InviteExpiresAt` stays as the revocation mechanism (`models.InviteNeverExpires`, year 9999, for an active code; the moment of revocation for a revoked one). Codes briefly expired after 7 days; `applySchema` lifts that on every code still active, and leaves revoked ones alone. What protects a code that reached the wrong person is that it can't go unnoticed: every signup tells the group's admins who joined (`member_joined` push, see "Push notifications" below), and they can remove the newcomer and replace the code in two taps. `CreateGroup(name string, teams [2]TeamSpec) (*models.Group, error)` takes the group's own name plus exactly two `TeamSpec{Name}` values — one per team, in the order they are shown (`Team.Position` 0 then 1) — instead of hardcoding a default: there's no reasonable team name to invent on the caller's behalf, so the caller (the admin creating the group, via `POST /groups`'s request body) has to supply both. This is a deliberate break from an earlier version of this doc that said `CreateGroup(name string)` "keeps its signature so `cmd/seed` still works" — that constraint no longer holds, since `cmd/seed` now passes `services.DefaultTeamSpecs` (`{Name: "Black"}, {Name: "White"}`) explicitly, the same default most integration tests reach for when the team names don't matter to the scenario under test. Both names are validated non-empty (after trimming) inside the same transaction that creates the group and its teams, via `ErrTeamNameRequired` (`internal/services/groups.go`, same sentinel style as `PlayerService.ErrEmptyPlayerName`) — mapped to 400 in `GroupHandler.CreateGroup`, which also 400s upfront if the request's `teams` array isn't exactly length 2. The flow `CreateGroup` enables:

1. `POST /groups` is `authRequired` (no `requireGroupMember` — there is no group to be a member of yet). Undisabled, `GroupHandler.CreateGroup` would create the group, then add the JWT's player as its first member via `GroupMembershipService.AddPlayerToGroupWithRole(..., models.RoleAdmin)`. Without that, a new group could never gain a member: `POST /groups/:id/players` requires **admin** of the target group; and without the *admin* role specifically it could never gain an admin either, since promoting a member is itself admin-only. **This route is currently disabled** — see the note at the end of this section.
2. `POST /groups/join` (`authRequired` only, for the same reason — the caller is by definition not a member yet) takes `{"invite_code": "..."}`. `GroupService.JoinByInviteCode` normalizes the code to upper case (like `normalizeEmail` in `AuthService`), returns `ErrInviteCodeNotFound` → 404 for an unknown or empty code, `ErrAlreadyMember` → 400, else enrolls the player (as `models.RoleMember`, via the plain `AddPlayerToGroup`) and returns the group. **This route is currently disabled too** — see below.
3. `GET`, `POST`, and `DELETE /groups/:id/invite-code` require a group administrator. They read, rotate, and revoke the invitation respectively. The response includes its expiration and uses `Cache-Control: no-store`. `GET /groups` lists the caller’s groups and `GET /groups/:id` requires a membership.

4. `GET /groups/me` (`authRequired` only) returns `GroupMembershipService.GetGroupsWithRoleByPlayerID` for the JWT's player — the list the `/groups` view is built on. `GET /groups` can't serve that: it lists the caller's own groups too, but without the role. Each entry is a `models.GroupWithRole` (`customModels.go`) — `Group` embedded plus the **caller's own** `role` — so a client can tell where it may act as an admin without one member-only request per group; embedding keeps the JSON flat and keeps `Group.InviteCode` behind `json:"-"`. `GetGroupsByPlayerID` is untouched and still used by `StandingsService.GetPlayerProfile`, which has no use for the role. The handler normalizes GORM's nil slice to `[]` so a player belonging to no group gets an empty array rather than `null`.
5. `GET /groups/:id/players` (`authRequired` + `requireGroupMemberByPathID`, open to any member — seeing the roster isn't privileged, only acting on it is) returns `[]models.PlayerWithRole` via `GroupMembershipService.GetPlayersWithRoleByGroupID` — the same "embed the base type, add a `Role` field" pattern as `GroupWithRole`, just embedding `Player` instead of `Group`, so its JSON keeps `Player`'s own lowercase convention (`id`, `name`, `email`) with `role` riding alongside. `GetPlayersByGroupID` (no role) is untouched — it's still used by `StandingsService.currentMemberIDs` (see "Standings" below) and a few integration tests that have no use for the role.

**`POST /groups` and `POST /groups/join` are both temporarily disabled** — a deliberate business decision, not a technical limitation: a player must no longer be able to self-service creating or joining a group. `GroupHandler.CreateGroup`/`JoinGroup` (`internal/handlers/groups.go`) were reduced to a single `c.JSON(http.StatusForbidden, ...)` each; `authRequired` still runs first, so an unauthenticated call gets 401, never reaching that 403. Neither `GroupService.CreateGroup` nor `JoinByInviteCode` themselves were touched — `cmd/seed` and every service-level/integration test still call them directly, and re-enabling the routes later is a matter of restoring the handlers' old bodies (see git history), not rebuilding anything. The only way into a group today is an admin sharing the invite-code link from the group's settings (`InvitationV2.vue`, see "Design v2" below), which routes a new player through the now-mandatory invite code on signup instead (see "Auth" above).

**Favorite group** — `GroupMembership.IsFavorite bool` (`json:"-"`, exposed instead via `GroupWithRole.IsFavorite` on `GET /groups/me`) marks which one of a player's groups the frontend's `resolveActiveGroup()` falls back to on a fresh device or right after logging in, instead of an arbitrary "first group" ordering. Every player who belongs to at least one group always has exactly one favorite:
- `AddPlayerToGroupWithRole` grants it automatically to a player's very first membership ever (counts existing memberships first; zero means this one becomes the favorite) — covers `POST /groups`/`POST /groups/join` (disabled today, but the underlying service calls are unchanged) and `AuthService.SignupNewPlayer`'s own invite-code join, since all of them eventually call it.
- `PATCH /groups/:id/favorite` (`authRequired` + `requireGroupMemberByPathID` — a personal preference, not an admin action) → `GroupHandler.SetFavoriteGroup` → `GroupMembershipService.SetFavoriteGroup(playerID, groupID)`, which unsets the caller's current favorite and sets the new one in one transaction. This is the only way the flag moves without a membership being deleted.
- `LeaveGroup` and `RemoveMember` both call the private `reassignFavorite` helper when the membership row they just deleted held the flag — it promotes the player's oldest remaining membership (by `CreatedAt`, same ordering as `GetFirstGroupForPlayer`), or does nothing if none are left. Without this, a player could end up with zero favorites just by leaving (or being removed from) their favorited group, breaking the "always exactly one, as long as you belong to at least one group" invariant everywhere else relies on.
- A one-time backfill in `pkg/database/connect.go` (next to the existing `role = 'owner'` rewrite) handles the migration case: `AutoMigrate` adds the column with its declared default (`false`) for every existing row, which would otherwise leave every pre-existing player with zero favorites. It promotes each player's oldest membership, guarded by `NOT EXISTS (... is_favorite = true)` so it's a no-op on every startup after the first.

`GroupMembership.Role` (`models.RoleAdmin` = `"admin"` / `models.RoleMember` = `"member"`, a plain string rather than a dedicated enum type) separates a group's admins from its plain members. A group can have **several** admins: its creator is the first, and any admin can promote or demote another member. Everyone else added via invite code or `POST /groups/:id/players` goes through the plain `AddPlayerToGroup`, which defaults to `RoleMember`. That route is **admin-only** (`requireGroupAdminByPathID`): it takes an arbitrary `player_id` in the body, so under the plain `requireGroupMemberByPathID` it used to hold before, any member could enrol any player whose UUID they knew — no invite code, no admin rights — which contradicts the invite-only model this section's disabled `POST /groups`/`POST /groups/join` exist to enforce. No frontend code calls it (the live flow is the invite link → mandatory invite code at signup), so it is kept gated rather than removed purely as the one server-side way an admin can enrol an already-existing player directly. The one invariant, enforced on both sides, is that **a group with at least one member always has at least one admin**: `LeaveGroup` promotes the oldest remaining member when the *last* admin leaves (and does nothing when another admin remains), and `UpdateMemberRole` refuses to demote the last admin (`ErrLastAdmin`).

`RequireGroupAdmin` and `RequireGroupAdminByPathParam` check the player's role and store the authorized group in the Gin context. `POST /matches` uses that group for creation. `PUT /matches/:id` and `DELETE /matches/:id` use `RequireGroupAdminByMatchPathParam` to authorize against the group stored on the match. For deletion, an optional `group_id` query parameter still asserts the match's group. Match and standings reads are available to members through `requireGroupMember`.

`PATCH /groups/:id/members/:playerId/role` takes `{"role": "admin"}` or `{"role": "member"}` and is the only way a group gains an admin besides its creator. `GroupMembershipService.UpdateMemberRole(groupID, actingPlayerID, targetPlayerID, newRole)` holds the rules, mirroring `RemoveMember`'s shape: any other role value is `ErrInvalidRole` → 400; targeting yourself is `ErrCannotChangeOwnRole` → 400 (there is no self-service "step down" — an admin who wants out uses `LeaveGroup`, which hands the role over for them); a target who isn't a member propagates `gorm.ErrRecordNotFound` → 404; demoting the last admin is `ErrLastAdmin` → 400; and setting the role the target already has is a **successful no-op**, so a retried request never fails for nothing. `ErrLastAdmin` is unreachable through the HTTP route (the acting admin is themselves an admin and can't be the target, so another admin always survives) — it's a service-level safety net, and its test calls the service directly. Note `PATCH` had to be added to the CORS `AllowMethods` list in `main.go`, which previously only allowed GET/POST/PUT/DELETE.

**Ghost players — an admin-created, credential-less roster entry, and the `POST /groups/:id/members/:playerId/invite` email-invite flow that turned one into a real account — have been removed entirely**, per an explicit product decision: every player must now have a real account, created through `POST /auth/signup`. `GroupHandler.InvitePlayer`, `AuthService.InviteExistingPlayer`, `PlayerHandler.CreatePlayer` (the `POST /players` route the old match editor's create-on-the-fly search used), and their supporting pieces (`GroupMembershipService.HasMemberNamed`, `ErrDuplicatePlayerNameInGroup`, `ErrPlayerAlreadyClaimed`'s use in that flow specifically) are all gone. `GroupHandler`'s constructor dropped its third `*services.AuthService` dependency as a result (`NewGroupHandler(groupService, membershipService)`) — credentials had lived in `AuthService` solely for that one method. `PlayerService.CreatePlayer` itself is untouched and still used directly (never through an HTTP route) by `cmd/seed` and by integration tests across the codebase as a quick way to create a test player — that's a test/seed convenience, not the removed feature.

Groups created **before** this change keep `invite_code = NULL` — Postgres treats NULLs as distinct in a unique index, so `AutoMigrate` adds the column and index without complaint, but those legacy groups can't be joined by code and `GET /groups/:id/invite-code` reports `""` for them. Reseed (`go run ./cmd/seed -reset`) or backfill by hand to give them one.

The role rename carries the same "AutoMigrate never rewrites data" hazard, and is handled explicitly: `pkg/database/connect.go` runs `UPDATE group_memberships SET role = 'admin' WHERE role = 'owner'` after `AutoMigrate`, next to the older `DROP INDEX IF EXISTS idx_players_name` step. Without it every group created before the rename would keep `role = 'owner'`, which no longer matches `models.RoleAdmin`, and its creator would be locked out of every admin-gated action with no admin left able to grant it back. The statement is idempotent — after the first startup there are no `'owner'` rows left.

Any group created by calling `GroupService.CreateGroup` directly instead of going through `POST /groups` gets no admin from the HTTP flow, since `POST /groups` is the only place `RoleAdmin` is assigned there. That used to be a harmless gap for the "Default" group in `cmd/seed/main.go`; now that admin gating is actually enforced, a group with no admin is a group where nobody can create a match or edit a score. The seed script therefore adds its **first** player (`thibaut`) with `AddPlayerToGroupWithRole(..., models.RoleAdmin)` and everyone else as a plain member. Any *other* group built the same way still needs a backfill by hand.

### Data model
`MatchPlayer` is the join table that carries both roster membership *and* the score: `(match_id, team_id, player_id, goals_scored)`. There's no separate "goals" or "events" table — a team's score is always derived by summing `goals_scored` over its players.

`Match` carries four **nullable** scheduling columns alongside `Date` — `ScheduledAt`, `RegistrationOpensAt`, `RegistrationsClosedAt` (all `timestamptz`, since a kick-off is an instant and not a calendar day) and `MaxPlayers` — and `MatchRegistration` is a second join table holding one row per sign-up, `(match_id, player_id)` under a composite `uniqueIndex` (which is what makes a double-clicked "Participate" harmless) plus a `CreatedAt` that *defines* the waiting list. Both are covered in "Scheduled matches and sign-ups" below. A match is scheduled iff `ScheduledAt` is set — use `Match.IsScheduled()` rather than scattering nil checks — and all-`NULL` is exactly the state every match predating the feature is in, which is why `AutoMigrate` needed no backfill for them, unlike `GroupMembership.IsFavorite` whose non-null `default:false` broke an invariant and had to be repaired in `connect.go`.

`Match.CreatedAt` (a plain, non-nullable `time.Time`, GORM's usual auto-populate-on-create convention — the same as `MatchRegistration.CreatedAt`/`MatchVote.CreatedAt`) was added later, originally purely for the MVP voting window (see below) to anchor on for a match with no kick-off at all — the voting window has since moved to a simpler `Date`-based rule that needs neither this nor `ScheduledAt`, so this field is currently unread by that feature (or any other), kept as plain metadata rather than removed. Unlike the four scheduling columns, this one **did** need a backfill: `matches` already had rows when the column was added, `AutoMigrate` gives it no default, and GORM errors scanning a `NULL` column into a non-pointer `time.Time` field on every later read of a row that predates it. `connect.go` backfills every `NULL` to `date::timestamptz` (the closest available stand-in for "when this was created" — not the real instant, but close enough for a row that's necessarily already years past any voting window either way), the same "repair the invariant a new non-null-shaped column broke" move as the `IsFavorite` backfill just above it, just for a genuine scan error instead of a business-logic one.

`Team` carries a `Name` (the display name an admin picks at group creation, e.g. "Les Rouges") and a `Position` (0 or 1, `json:"-"`): the order a match lists the group's two teams in, the first on the left. Teams used to have a `Colour` too; nothing displayed it any more once design v2 replaced v1, so the column was dropped (`database.ReplaceTeamColourWithPosition`, run by `applySchema` before `AutoMigrate`, since `AutoMigrate` never drops a column). Matches had been sorting their teams by colour, so that migration first fills `position` in the colour order, per group, and no match swapped sides. Every group has exactly two teams, created together with the group (see "Group bootstrapping" below) and renameable afterwards via `PATCH /groups/:id/teams/:teamId` (`TeamHandler.UpdateTeam` → `TeamService.UpdateTeam`, admin-only, scoped to `(team_id, group_id)` in one query so a team belonging to a different group reads as 404 rather than being silently updatable).

### The flatten/reconstruct pattern (matches.go)
`MatchService.GetMatchesDetails` / `GetMatchDetailsByID` do not use GORM associations or `Preload`. They run a raw SQL query with `LEFT JOIN`s across `matches → match_players → teams/players`, scan into flat `RowsMatchDetails` rows, then manually rebuild the nested `MatchWithDetails{ Teams: []TeamWithPlayers{ Players: []PlayerCustom } }` structure in Go (matching by ID in loops, appending as new IDs are encountered). When a match has no rows in `match_players` for a given team (or at all), there's a fallback path that queries all `teams` directly to still return empty team shells. Any change to the JSON shape returned to the frontend needs to touch both the SQL query and this reconstruction loop, not just the model struct — `TeamWithPlayers.Name` is a worked example: it required adding `teams.name as team_name` to both `SELECT`s, `TeamName` to `RowsMatchDetails`, and setting `Name` at all four `models.TeamWithPlayers{...}` construction sites (two "get or create this team while scanning rows", two "backfill a team with no roster yet" — one pair per function). The teams of each match are then ordered by `sortTeamsByPosition` (`Team.Position`, read from the group's teams the backfill already loads, then id), which is what puts the same team on the left every time.

The scheduling fields are the second worked example, and the instructive one is the field that *isn't* in the join. The four `matches.*` scheduling columns were added to both `SELECT`s, to `RowsMatchDetails`, and to the two `models.MatchWithDetails{...}` construction sites (one per function; row 0 is as good as any, since the `Match*` columns repeat identically on every row of a match — including the single all-NULL-team row of a match with no roster yet, which is the *normal* state of a scheduled match). But `RegistrationCount` deliberately does **not** come from there: `match_registrations` is a second one-to-many on `matches`, so joined alongside `match_players` it would multiply the rows (one per sign-up × one per assigned player) and silently corrupt every `Score` and goal total in this file, all of which are derived by summing those rows. It's fetched by a separate grouped count instead — `registrationCountsByGroup` for the list, `registrationCount` for the single match, both on the GORM query builder rather than raw SQL, since the group scope is a subquery and no joined columns are needed. `GetMatchesDetails` skips that second round-trip entirely unless at least one scanned row has a non-nil `scheduled_at`, which is what keeps it free for every group predating the feature — and this is also the function all four `StandingsService` calls go through, so an unconditional extra query would be charged to every standings request for nothing.

`Match.CreatedAt` is a third, smaller worked example of the same pattern (`matches.created_at as match_created_at` in both `SELECT`s, `MatchCreatedAt` on `RowsMatchDetails`, `CreatedAt` set at both `models.MatchWithDetails{...}` construction sites) — originally added so the frontend could compute the MVP voting window's own anchor for an unscheduled match without a second request; the voting window is Date-based now (see "MVP voting" below) and no longer needs it, but it's still exposed on the DTO as ordinary metadata. Unlike the scheduling fields it carries no `omitempty` on the DTO: every match has a `CreatedAt`, so there is no "doesn't apply" case to keep an old client from seeing.

`MatchService.UpdateMatch(matchID, groupID uuid.UUID, teams []models.TeamWithPlayers)` performs a diff: for each team in the incoming payload it loads existing `MatchPlayer` rows for that `(match_id, team_id)`, creates rows for players not yet present, updates `goals_scored` for players still present, and deletes rows for players removed from the payload. The whole diff runs inside `s.DB.Transaction(...)`.

Its first two parameters are the security-relevant part, and are deliberately **not** fields read off a DTO. It used to take a whole `models.MatchWithDetails` and trust that payload's own `ID`, which is what made `PUT /matches/:id` forgeable across groups (see the middleware note above): the handler now takes the match id from the URL and the group from `authorizedGroupIDFromContext` (published by `requireGroupAdminByMatchID`), and the body's `ID`/`GroupID` are ignored entirely — the response echoes them back overwritten with the authoritative values, so a client can never read its own body back as though the server had accepted it. The service then re-verifies both rather than trusting its caller, the same defence-in-depth `DeleteMatch` already applies: the match is loaded by `(id, group_id)` (a match from another group reads as `ErrMatchNotFound` — absent, not forbidden, exactly as in `GetMatchDetailsByID`), and every team id in the payload must belong to that same group (`ErrTeamNotInGroup` → 400, `assertTeamsInGroup`). That second check is not redundant: without it an admin could still attach one of their *own* group's teams to another group's match, which is the same corruption by a different route — and it mirrors `TeamService.UpdateTeam` scoping its own lookup to `(team_id, group_id)`.

`MatchService.DeleteMatch(matchID, groupID)` backs `DELETE /matches/:id` (admin-only, scoped to the match's group): it scopes its lookup to `WHERE id = ? AND group_id = ?` exactly like `GetMatchDetailsByID` — a match ID from another group reads as `ErrMatchNotFound` rather than being reachable — then, inside a transaction, deletes every `MatchPlayer` row for that match before deleting the match itself. That ordering is required, not just tidy: `MatchPlayer.MatchID` has a plain FK to `matches(id)` with **no `ON DELETE CASCADE`**, so deleting a match that still has roster rows fails with a database constraint error unless they're removed first. The route uses `requireGroupAdminByMatchID`, and `MatchHandler.DeleteMatch` acts on the group that middleware derived from the match and published (`authorizedGroupIDFromContext`); a `group_id` in the query string, if any, must equal it. `POST /matches` is the route still on `requireGroupAdmin`, and its handler likewise acts on the authorized group, answering 400 when the body names another one, so an admin of group A can't create a match in group B by putting A in the query and B in the body. The read handlers' `resolveGroupID` and the middleware's `resolveGroupIDForMembership` are thin wrappers over one shared `resolveScopedGroupID` (`internal/handlers/groupscope.go`), which owns the whole rule — `group_id` from the query string, then (only for the middleware, which passes `peekGroupIDFromBody`) the JSON body, then the caller's own first group, with the player looked up lazily at that last step so a request naming its group in the query string still needs none. The two used to be independent copies of those rules that merely happened to agree for every request, so a future edit to one alone could silently reopen exactly the cross-group bug this paragraph describes. All the wrappers add now is *how* a failure is reported — `resolveScopedGroupID` returns a `groupIDFailure{status, message}` as data, which the handler writes with `c.JSON` (it is the end of the chain) and the middleware with `c.AbortWithStatusJSON` (it is not). There's a test pinning the property directly: for the same request, the group the middleware authorizes and the group the handler acts on must be identical, and a malformed `group_id` must produce the same status and body from either side. On success it responds `{"deleted": true}`, the same convention as `LeaveGroup`'s `{"left": true}`/`RemoveMember`'s `{"removed": true}`. The same transaction also deletes the match's `MatchRegistration`, `MatchVote` and `MatchPrediction` rows — nothing *forces* any of them, since none declares an association on `Match` and there's no FK to violate, but leaving a deleted match's sign-up list, MVP votes or predictions behind would be dead rows nothing can ever read or clean up again.

### Scheduled matches and sign-ups
A match can be **scheduled**: created for a future kick-off, with a sign-up list members add themselves to and a waiting list past a maximum number of players. The whole feature is additive — a match created with none of the scheduling fields behaves exactly as it always did (an admin records a game already played and scores it right away) and serializes to byte-for-byte the same JSON, since every scheduling field on `MatchWithDetails` carries `omitempty` so a client that knows nothing about scheduling sees no new keys at all.

Four product decisions shape the implementation, each one removing machinery a reader might otherwise go looking for:
- **Two distinct timestamps.** `RegistrationOpensAt` is when the sign-up button goes live, `ScheduledAt` is kick-off. A single field couldn't express "opens Friday, played Sunday".
- **The admin closes sign-ups manually**, in order to *then* compose the teams — hence `RegistrationsClosedAt` as a nullable timestamp rather than a bool: `NULL` means open, a value records when they were closed, and clearing it re-opens them after a mis-click. Kick-off is a hard backstop regardless.
- **The waiting list is derived, never stored.** No status column, no promotion job: sign-ups are ordered by `CreatedAt`, the first `MaxPlayers` are confirmed and the rest are waiting. A withdrawal is then a plain row delete that mechanically promotes the next player with no race to lose, and lowering `MaxPlayers` rolls the tail of the list into the waiting list for free.
- **A sign-up is not a `MatchPlayer` row.** Beyond a `MatchPlayer` needing a `TeamID` and a goal count that don't exist yet when a player merely says they'll come, `ComputePointsStandings` treats any match whose two teams both have players as played — so recording sign-ups there would make next Sunday's match appear in the standings as a 0-0 draw.

**Creating one.** `CreateMatch(spec MatchSpec, groupID uuid.UUID)` takes a `MatchSpec` struct rather than a growing positional parameter list, the same call shape as `CreateGroup`'s `TeamSpec`. `spec.validate()` treats the three client-supplied scheduling fields as **all-or-nothing** — none (an ordinary match) or all three, else `ErrIncompleteSchedule`, since half a schedule has no defined behaviour at all — plus `ErrRegistrationOpensAfterKickoff` (a window opening at or after kick-off could never be used, given that kick-off closes sign-ups) and `ErrInvalidMaxPlayers` for a non-positive roster size (which would bench every single sign-up). All three map to 400 in `MatchHandler.CreateMatch`. A `ScheduledAt` in the past is deliberately *not* rejected: backfilling a match that already happened is legitimate, and the unscheduled flow has always accepted any date.

`MatchSpec.RegisterCreatorID` is the one extra, optional field, and it is not part of that all-or-nothing triple: `uuid.Nil` (the zero value every existing caller already sends) is a no-op, a non-nil id on a scheduled spec enrolls that player on the new match's sign-up list in the **same transaction** as the match itself, and a non-nil id on an unscheduled spec is `ErrRegisterCreatorOnUnscheduledMatch` → 400 — refused rather than silently ignored, because an unscheduled match has no list to join. The resulting `MatchRegistration` row is identical to one written by a later Participate (same table, same unique index, waiting list still derived from `CreatedAt` vs `MaxPlayers`). It deliberately does **not** go through `RegistrationWindowError`: the list is being born rather than joined, so a match whose window opens on Friday can still put its creator at #1 on Wednesday. Subsequent `Register`/`Unregister` calls stay gated on the window as before. The unscheduled / no-flag path stays a single `INSERT` rather than wrapping every create in a transaction — wrapping would change nothing a caller can observe.

`POST /matches` binds into a dedicated `createMatchRequest` struct instead of `models.Match` (the same choice the auth handlers already make). That's what makes `registrations_closed_at` unrepresentable at creation — "sign-ups closed before anyone could make one" is not an admin action that exists — rather than something a later filter has to remember to strip. `register_creator` is the opt-in bool that maps onto `MatchSpec.RegisterCreatorID`: true reads the player from the JWT (never from the body — there is no "register someone else" capability here either, the same rule `POST /matches/:id/registrations` already enforces) and omitted/false leaves the field at `uuid.Nil`. Its timestamps are plain `*time.Time`, so `encoding/json` parses them as RFC3339 and keeps **the offset the client sent**; that is load-bearing and must not be "normalized" to UTC, because a scheduled match's `Date` is *derived* from `ScheduledAt` via `models.DateOf` in the kick-off's own location, so a 21:00 Paris kick-off keeps the calendar day — and therefore the season — the client meant. `Date` stays the single write path for the day (seasons, ordering and the existing JSON contract are all built on it), which is why a caller can't supply both and have them drift apart.

**Routes**, all five `authRequired` and all in `main.go`:
- `POST /matches/:id/registrations` (any member) — signs the **caller** up; answers with their resulting `MatchRegistrationEntry`.
- `DELETE /matches/:id/registrations` (any member) — withdraws the caller's own sign-up.
- `GET /matches/:id/registrations` (any member) — the ordered list; seeing who's coming isn't privileged, only closing it is.
- `POST /matches/:id/registrations/close` → `{"closed": true}` and `POST /matches/:id/registrations/reopen` → `{"reopened": true}` (admin only, like every other write on a match).
- `PATCH /matches/:id/registrations/max-players` takes `{"max_players": 10}` and changes how many sign-ups count as confirmed (admin only). It answers with the **recomputed ordered list**, the same shape `GET` returns, for the same reason `Register` answers with the caller's entry rather than a bare success: the new confirmed/waiting split *is* the result of the call, and re-deriving it client-side from the cap is precisely what `ComputeRegistrationPositions` exists to prevent.

The player always comes from the JWT, never from the body or the path: there is no "register someone else" capability, and taking a player id from the request would silently create one. That's also why the `DELETE` has no `/me` suffix — a suffix would imply an alternative target that doesn't exist. `Register` answers with the caller's entry rather than a bare `{"registered": true}` because *reaching the cap is not an error*: the surplus sign-up succeeds and lands on the waiting list, so that response is the only place a client can learn "you are #17, you're on the bench". The position is read back from `ListRegistrations` rather than guessed from a count, since position and waiting status are properties of the whole ordered list.

**A third way of resolving the group** (`internal/handlers/matchscope.go`) exists for these routes, and it's the security-relevant part of the feature. `RequireGroupMembershipByMatchPathParam` / `RequireGroupAdminByMatchPathParam` derive the group from the *match* named in the path (`MatchService.GetGroupIDByMatchID`) and authorize against that one. Neither pre-existing pair fits: `RequireGroupMembership`/`RequireGroupAdmin` resolve the group from a query param, the JSON body, or — failing both — the caller's own first group, which used here would be a genuine hole, since the path names a match and a member of group A could act on group B's match just by supplying their own group id (or none at all); and `...ByPathParam` reads a group id straight from a path that doesn't carry one. They also differ from the four older middlewares in one deliberate way: they **publish** the group they authorized into the Gin context (`authorized_group_id`, read back with `authorizedGroupIDFromContext`, the way `AuthMiddleware` publishes `player_id`), and the two admin handlers read it back instead of resolving a group themselves. That saves a duplicate lookup, but the real reason is structural — it makes "an admin of group A acting on a match in group B" impossible to express, which is exactly the bug `MatchHandler.DeleteMatch` still has to avoid by hand.

This pair is no longer used only by the sign-up and vote routes: **`PUT /matches/:id` was migrated onto `RequireGroupAdminByMatchPathParam` too**, because it had precisely the hole the paragraph above describes — it resolved its group from the request body while the match id came from that same body, so an admin of group A could pass `GroupID` = A and `ID` = a match in group B and rewrite it (see `MatchService.UpdateMatch`). `POST /matches` deliberately stays on `requireGroupAdmin`: it creates the match, so there is no match in the path to derive a group from.

Status codes are chosen to keep match ids unenumerable. A caller who isn't a member gets **404** "match not found", identical to a genuinely unknown id and emitted from one shared `abortMatchNotFound` so the two wordings can't drift apart either — a 403 would confirm the match exists, and anyone could then enumerate other groups' match ids by watching the status flip. A member who merely isn't an admin gets **403**, because they can already read the match through `GET /matches/:id/details`, so there's nothing left to hide. Beyond authorization, `respondMatchRegistrationError` maps `ErrMatchNotFound` → 404, `ErrMatchNotScheduled` → **400** (a match with no schedule has no sign-up list at all: malformed request, not a state to retry) and the four state conflicts — `ErrRegistrationsNotOpenYet`, `ErrRegistrationsClosed`, `ErrAlreadyRegistered`, `ErrNotRegistered` — → **409**.

`MatchRegistrationService` keeps the policy in two package-level pure functions, the same split as `ComputePointsStandings` versus its data loading, so the whole thing is unit-testable without a database:
- `RegistrationWindowError(match, now)` is the entire "is this list open" rule, and **both** `Register` and `Unregister` call it — withdrawing is gated on the same window as signing up, because once the admin has closed the list the roster is being turned into teams, and once the match has kicked off the list is history (a player who wants out after that talks to an admin). `ErrRegistrationsClosed` covers both ways sign-ups stop, an explicit close *and* kick-off having passed: the refusal and the remedy are identical from the caller's side, so splitting them would leak scheduling detail without changing anything a client could do. It's `!now.Before(*ScheduledAt)` rather than `After`, so kick-off itself is closed. `RegistrationOpensAt` is nil-guarded rather than dereferenced — `CreateMatch` guarantees it, but a row hand-crafted in SQL might not, and "no stated opening time" is best read as open since creation.
- `ComputeRegistrationPositions(entries, maxPlayers)` numbers an already-ordered list 1-based and flags the tail beyond `maxPlayers` as waiting (a nil `maxPlayers` means no cap, so nobody waits). The ordering itself is `ListRegistrations`' job and is **total**: `created_at ASC, id ASC`. The tie-break is not decoration — two sign-ups landing in the same microsecond would otherwise be ordered arbitrarily by the database, and right at the confirmed/waiting boundary that could swap the last confirmed player and the first reserve between two reads of unchanged data.

`SetMaxPlayers` is the admin action the derived waiting list makes almost free, and the one the feature was extended for: 12 players signed up for a 16-a-side match, so the admin drops the cap to 10 and the last two roll onto the bench in sign-up order — no row rewritten, nobody re-registered, and raising it back promotes exactly the same two. It reuses `ErrInvalidMaxPlayers` (`matches.go`, `MatchSpec.validate`'s own sentinel) for a non-positive cap rather than declaring one of its own — benching every single sign-up is as meaningless set after the fact as it is at creation — and setting the cap a match already has is a **no-op success**, same reasoning as Close/Reopen. It is deliberately **not** gated on `RegistrationWindowError`, unlike `Register`/`Unregister`: adjusting the split is typically what an admin does right *after* closing sign-ups, in order to compose the teams, so refusing it on a closed list would block the main use case. The handler binds `max_players` as a `*int` rather than a plain `int` with `binding:"required"`: the one value this endpoint must reject (0) is also Go's zero value, so `required` would conflate "omitted" with "explicitly zero" and answer the wrong error for the single input worth being precise about.

`Register` checks for an existing sign-up rather than leaving it to the composite unique index, so the caller gets a clean `ErrAlreadyRegistered` instead of a driver-level constraint error — the index is still the real guarantee under a concurrently double-clicked button. `CloseRegistrations`/`ReopenRegistrations` scope their lookup to `(match_id, group_id)` exactly as `DeleteMatch` does, and are both **no-op successes** when the match is already in the target state: same reasoning as `UpdateMemberRole` setting a role a member already holds — a retried request must not fail for nothing, and the *first* close's timestamp is the one worth keeping. Re-opening writes `NULL` through a `map[string]any`, since GORM skips zero values passed to `Updates` as a struct. It's allowed even after kick-off, where it simply has no effect (the backstop still refuses every sign-up) — refusing it there would add a rule that protects nothing. `ListRegistrations` treats an unscheduled match as an empty list rather than an error, unlike `Register`, so a caller doesn't have to know about scheduling just to render a match.

The service deliberately does **not** check that the player belongs to the match's group: that's authorization, enforced one layer up by the route, exactly as `MatchService` relies on `requireGroupAdmin` instead of re-checking roles itself.

### MVP voting (internally MOTM)
The award is shown to players as **MVP** (short) or **MVP of the Match** (long), never with a plural "s". Code, routes, JSON fields, preference keys and the database keep the `motm` names (`MotmAwards`, `/standings/motm`, `tab=motm`, `motm_announced`, `match_votes`, `motm_notified_at`). A player who actually took part in a match can vote for who they thought was best in it once its roster is composed — an ordinary already-recorded match, or a scheduled one after "Fill teams from sign-ups"/manual composition. It deliberately reuses as much of the sign-up feature's shape as it can (the match-scoped middleware, the derive-don't-store philosophy, the tie-inclusive-award pattern already established by `ComputeRegistrationPositions`), while diverging from it in the two places the product is actually different: voter eligibility, and what a repeated action means.

`models.MatchVote` (`(match_id, voter_id, voted_for_id)`) is the join table, with a composite `uniqueIndex` on `(match_id, voter_id)` — **not** "at most one sign-up" the way `MatchRegistration`'s identical-looking index is, but "exactly one *current* vote per voter per match". That difference in meaning is the whole feature:
- **Voting is an upsert, not a one-shot action.** `MatchVoteService.Vote(matchID, voterID, votedForID)` replaces an existing vote from the same voter rather than rejecting a second call with something like `ErrAlreadyRegistered` — a player changing their mind about who deserves MOTM, before or after the final whistle, is the ordinary case here, not a mistake to refuse. `POST /matches/:id/votes` therefore always answers 200 with the resulting tally, never a 409 for "you already voted".
- **Voter and candidate are held to the identical roster-membership standard.** This reverses an earlier, deliberate product decision documented in a previous version of this section — "voter eligibility is broader than 'played in the match': any group member can judge, including a sub who never got on or a member who only watched" — based on new explicit product feedback: only someone who actually played in *this specific match* may vote on who was its best player. Both sides are now checked by the same `playerOnRoster` helper (a `MatchPlayer` row on either team): a voter who wasn't on the roster is `ErrVoterNotOnRoster` → 400, and voting for a real group member who simply never played in this match is still `ErrVotedForPlayerNotOnRoster` → 400, unchanged. The route itself still only requires `RequireGroupMembershipByMatchPathParam` (the exact same middleware the sign-up routes use, with no admin-only route anywhere in this feature, unlike sign-ups' Close/Reopen) — the narrower rule lives in `MatchVoteService.Vote`, not in a stricter route guard, since group membership and match-roster membership are different questions. Self-votes are also rejected outright (`ErrCannotVoteForSelf` → 400) — there is no legitimate self-nomination for "best player on the pitch". All three are 400s rather than 409s, unlike the sign-up window's state conflicts: whether the voter is themselves, whether the voter is on the roster, and whether the candidate is on the roster, are all true or false regardless of timing, so there is nothing to retry into validity the way a closed sign-up window eventually reopens.
- **There is still no admin close/reopen** — nobody manually freezes voting the way sign-ups are closed. What voting *does* have, added after real product feedback, is a fixed window (below); once that has elapsed there is nothing left to reopen, unlike sign-ups.
- **The award is derived, never stored**, mirroring the waiting list's own choice: there is no "winner" or "award" column anywhere. `ComputeMotmWinners(tally []models.MatchVoteTally) []uuid.UUID` is the entire rule, kept as a pure function of an already-computed tally (unit-tested without a database, the same split as `ComputeRegistrationPositions`): find the max vote count, return every candidate at that count. **Ties are inclusive by product decision** — a three-way tie makes three Men of the Match for that game, not one picked arbitrarily. An empty tally (nobody voted, or every vote was later withdrawn) returns no winners at all, not a default.

**The voting window.** Casting, changing, or removing a vote is only allowed until the vote closes — reading the tally never is (see `GET` below). `MotmVotingDeadline(date, scheduledAt)` (`internal/services/matchVotes.go`) is the deadline and `VotingWindowError(match models.Match, now time.Time) error` the check built on it (closed once `!now.Before(deadline)`), mirroring `RegistrationWindowError`'s own split between a pure window-check function and its thin callers (`Vote`/`Unvote`), so it's unit-tested without a database exactly the same way. `IsMotmVoteClosed` (standings) and `MotmAnnounceAt` (the push) read the same deadline. Two rules, by product decision:
- **A scheduled match closes 24 hours after kick-off** (`MotmVotingWindow`): a Thursday 19:45 kick-off closes on Friday at 19:45. `Date` plays no part.
- **A match without a kick-off** (an admin recording a game already played) keeps the older Date-based rule: open through the calendar day after `Date`, closing at the stroke of `Date+2` — there is no kick-off to count from.

History: the very first rule was 24 hours after `ScheduledAt`, or after `CreatedAt` for a match without a kick-off. It was replaced by the Date-only rule for every match, because the status badge built on the same idea looked inconsistent from one match to the next. The kick-off rule came back later for scheduled matches only, on explicit product request; `CreatedAt` is still not used, so a match without a kick-off keeps the Date rule rather than anchoring on when it was created.

Past the deadline, `Vote`/`Unvote` both return the new `ErrVotingClosed` → **409**, the same status-code family as `ErrRegistrationsClosed` (a state conflict — the identical request would have succeeded a moment earlier — not a malformed one). `ListVotes`/`GET /matches/:id/votes` is **not** gated on this at all: the tally past the deadline is the finalized result, still worth serving, just no longer worth letting anyone change. `Unvote` keeps its pre-existing "no such match is still a no-op, never a 404" behaviour (see its own comment and `TestVote_Integration_UnknownMatchNotFound`) for a match `findMatch` can't even load — there is no window to enforce against a match that doesn't exist, and the route this backs is unreachable for an unrecognised id anyway (`RequireGroupMembershipByMatchPathParam` 404s first). The roster-must-be-composed rule from before is untouched and now simply ANDs with the window: `playerOnRoster` already requires the candidate to have a `MatchPlayer` row, which requires the roster to be at least partly built, regardless of timing.

**Routes**, all three `authRequired` + `RequireGroupMembershipByMatchPathParam` (the same match-scoped middleware from `matchscope.go` the sign-up routes use, and for the same reason — the group has to come from the match named in the path, never from a query param or the caller's own first group, or a member of group A could vote on group B's match):
- `POST /matches/:id/votes` takes `{"voted_for_id": "..."}` and casts or replaces the **caller's** vote — the voter always comes from the JWT, never the body, the same "no acting on someone else's behalf" rule as `MatchRegistrationHandler.Register`. It answers with the same summary `GET` returns, so a client sees the updated tally without a second request. 409s with `ErrVotingClosed` past the 24h window.
- `DELETE /matches/:id/votes` withdraws the caller's own vote. Like `ReopenRegistrations`, it's a **no-op success** when the caller had never voted — never a 404 — since removing a vote that was never cast is still exactly nothing to do. Also 409s with `ErrVotingClosed` past the window, since changing your mind about withdrawing is still an action on the vote, not a read.
- `GET /matches/:id/votes` returns `models.MatchVoteSummary { Tally []MatchVoteTally, MyVoteFor *uuid.UUID }` — every candidate with at least one vote, ordered by vote count desc then name asc, plus which player (if any) the caller has voted for. `MyVoteFor` is a pointer with `omitempty` for the same reason `MatchWithDetails.RegistrationCount` isn't a plain value: "the caller has not voted" has to stay distinguishable from a real player id, and `uuid.Nil` is a value a genuine vote could never hold but would be an ambiguous way to say so. Seeing the tally isn't privileged — only casting a vote is scoped to the caller's own choice — so this is open to any member, same as `ListRegistrations`, and it is never gated on the voting window either.

Status codes follow the sign-up routes' own unenumerability rule: a non-member gets 404 "match not found" (identical to a genuinely unknown id, via the same shared `abortMatchNotFound`), since a 403 would confirm the match exists and let match ids be enumerated by watching the status flip.

`MatchVoteService.tallyForMatch`/`TallyVotesForMatches` are GORM query-builder aggregations (`Joins` + `Group` + `Count`), **not** raw SQL — this is a single join with a `GROUP BY`, exactly the case the query builder is for, unlike the multi-table flatten/reconstruct `matches.go` needs raw SQL for (see "The flatten/reconstruct pattern" above). `TallyVotesForMatches` exists as its own batched query, keyed by match id, specifically for `StandingsService.GetMotmStandings` below — one round-trip for a whole group's matches rather than one query per match, the same reasoning `registrationCountsByGroup` already established for sign-up counts.

**The season leaderboard**, `GET /standings/motm?season=...`, follows `GetPointsStandings`/`GetScorers`'s exact shape: `StandingsService.GetMotmStandings(groupID, season)` loads the group's matches, filters by season in Go, then runs the pure `ComputeMotmStandings(matches, votesByMatch)` — which counts, per player, how many matches' `ComputeMotmWinners` included them, tie-inclusive (a three-way tie increments three rows, not one), then sorts by award count desc, name asc as the tie-break, mirroring `ComputePointsStandings`/`ComputeScorers`'s own convention. `IsMember` is set the same post-processing way as `PointsStandingRow`/`ScorerRow`, via the same `currentMemberIDs` helper — a player who has since left the group keeps every award their match history earned them, just tagged `IsMember: false`. Votes are **not** part of `MatchWithDetails` and never joined alongside `match_players` — the same reason `RegistrationCount` isn't (see "The flatten/reconstruct pattern"): `match_votes` is a second one-to-many on `matches`, so joining it in would multiply every scanned row and corrupt every goal total the file derives by summing them. It's fetched separately instead, once per `GetMotmStandings` call, via `TallyVotesForMatches` over every match id in the already-season-filtered result.

### Match predictions ("Pronostic")
Any group member can predict a scheduled match's outcome — team A wins, draw, team B wins — at odds derived from each side's Elo rating, and a season leaderboard ranks players by their net return. It's a free game between friends: no balance, no wallet, no stake to choose. Every prediction implicitly risks one token, a hit pays `odds - 1` and a miss costs `1`. It shares no table, component or route with MVP voting. Code: `internal/services/matchPredictions.go` (window, upsert, listing), `internal/services/matchOdds.go` (`ComputeMatchOdds`, `EloRatingsBeforeMatch`), `ComputePredictionStandings` in `standings.go`, and the frontend's `PredictionsV2.vue` plus `src/services/matchPrediction.js`.

**Only scheduled matches, only once fully composed — deliberately.** `PredictionWindowError(match, rosterComposed, now)` is the whole rule, a pure function like `RegistrationWindowError`/`VotingWindowError`. An unscheduled match, or one where either team is still empty, is `ErrPredictionsNotAvailable` → 400. From kick-off on (`!now.Before(*ScheduledAt)`, so kick-off itself is closed) it's `ErrPredictionsClosed` → 409. "Fully composed" means **both** teams have a player (`rosterFullyComposed`), which is stricter than the frontend's `teamsAreComposed` ("either team"): a winner can't be picked between a team and nobody. Unscheduled matches are excluded on purpose, not by oversight: by this codebase's convention an unscheduled match is how an admin records a game that has *already been played*, so its outcome is known at creation time. If predicting on a match created without the sign-up flow is ever wanted, the right move is to let `MatchSpec.validate()` accept a `ScheduledAt` alone, not to force a kick-off time onto the "record a played match" flow.

**Predicting is an upsert**, like an MVP vote: `models.MatchPrediction` is `(match_id, player_id, predicted_team_id)` with a composite `uniqueIndex` on `(match_id, player_id)`, and a second `Predict` call replaces the first. `PredictedTeamID` is a `*uuid.UUID`, and `nil` means a draw. A team id that isn't one of this match's two teams is `ErrPredictedTeamNotInMatch` → 400. Unlike voting, **anyone in the group may predict**, whether or not they are on the roster.

**The odds are derived, never stored.** `EloRatingsBeforeMatch(matches, matchID)` replays the group's history strictly *before* that match through the same `ComputeEloStandings` `cmd/elo` uses (a truncated slice, not a second implementation), so a match's odds reflect only what was known before it. They therefore don't change once the match is played, even though they're recomputed on every read. `ComputeMatchOdds(ratingA, ratingB)` compares the two teams' average ratings (a player new to the group counts as `EloStartingRating`). The draw probability is modelled first, at 0.40 when the teams are level, shrinking with the rating gap (`PredictionDrawSlopePerEloPoint`) down to a 0.20 floor. Above 1/3, a draw between level sides is the likeliest outcome and therefore the lowest odds, which matches real play: the first production group drew 4 of its first 8 matches. It started at 0.30/0.12, which made the draw always pay more than either win. The remaining probability is then split between the teams in Elo's own expected-score ratio. Each multiplier is `1/p`, with no house margin, clamped to `[1.1, 10]`. All of these are named constants in `matchOdds.go`. Only the draw values have been checked against real results, on 8 matches; worth revisiting once there are a few dozen. This is also the first place the Elo rating has any user-visible effect: the ratings themselves are still only shown through the CLI (see "Elo rating" below), but here they move the odds.

**Routes** (`main.go`):
- `POST /matches/:id/predictions` takes `{"predicted_team_id": "<uuid>" | null}` and casts or replaces the **caller's** prediction. The player always comes from the JWT.
- `GET /matches/:id/predictions` returns `models.MatchPredictionSummary { Entries, Count, Revealed, Odds, MyPrediction }`. **Other members' picks stay private until kick-off:** before it, `Entries` holds only the caller's own prediction and `Revealed` is false, so nobody can follow the crowd while the choice is still open. From kick-off on (when nobody can change their pick any more) `Revealed` is true and `Entries` lists everyone's. `Count` is always the total, which gives no one's pick away. This is enforced in `ListPredictions`, not just hidden in the UI, since any member can call the route directly. `Odds` is omitted until the roster is fully composed. `MyPrediction` is omitted when the caller hasn't predicted, so a present `MyPrediction` with a null `PredictedTeamID` is a draw, never "no prediction". This read is **never** gated on the window.
- `GET /standings/predictions?season=...` returns `[]models.PredictionStandingRow { PlayerID, Name, Predictions, Correct, Points, IsMember, History }`, sorted by points desc, then name asc. `History` is every settled prediction behind the row, oldest first (`models.PredictionHistoryEntry`: the match's date, team ids/names and final score, the pick, its odds, whether it was right and the points it earned). It is built in the same `ComputePredictionStandings` pass as the totals, so the two can't disagree, and covers the same season-filtered, recorded matches.

Both match routes use `RequireGroupMembershipByMatchPathParam`, for the same unenumerability reason as sign-ups and votes. The leaderboard uses `requireGroupMember`, like every other standings route.

**A match is settled when an admin saves its score, not on a calendar rule.** `Match.ResultRecordedAt` (nullable `timestamptz`) is set by `MatchService.UpdateMatch` the first time it runs on a scheduled match at or after kick-off; later corrections keep that first timestamp, since every standing is derived from the score anyway. `GetPredictionStandings` counts only matches carrying it (`FilterResultRecorded`); the other standings count a scheduled match from the same moment (`FilterCountedMatches`, see "Standings" below), and an unscheduled one from midnight after its day. The reason: until the score is in, a composed match reads 0-0, and settling on that would hand every "Draw" prediction a win. Conversely, once the score is saved there is nothing to wait for, so points land straight away. A roster composed *before* kick-off doesn't set it (that's not a result). It did need a backfill, though not for the standings (matches predating the column carry no predictions): the Pronostic page reads `NULL` after kick-off as *Awaiting result*, so every scheduled match played and scored before the release showed that badge forever. Since the points, scorers, profile and Elo standings now also count a scheduled match from `ResultRecordedAt`, the same backfill is what keeps those older matches in them. `database.BackfillResultRecordedAt` (run by `applySchema`) sets the column to the kick-off on every scheduled match with a composed roster that kicked off before `resultRecordedAtCutoff`, the moment the feature reached production. It is bounded by that fixed instant rather than "kick-off has passed" because after it a `NULL` is meaningful: filling it on every startup would settle a match the admin hasn't scored yet at 0-0. It is exposed on `MatchWithDetails` as `ResultRecordedAt` through the usual flatten/reconstruct steps (both `SELECT`s, `RowsMatchDetails`, both construction sites).

**The leaderboard replays Elo over the group's *whole* history, even when it is season-filtered.** `GetPredictionStandings` loads every match, settles only the season-filtered, recorded ones (`FilterMatchesBySeason` then `FilterResultRecorded`), but passes the unfiltered list to `ComputePredictionStandings` as the Elo input. Season-filtering that input would restart every rating at 1500 each September and silently change the odds a past prediction was settled at. A regression test pins this. A settled match also has to pass `ComputePointsStandings`' "both teams have players" check, and the result is read off `Team.Score`, own goals included. `IsMember` is set afterwards via `currentMemberIDs`, like the other three tables. Predictions are fetched by `TallyPredictionsForMatches` in one batched query, never joined into the `match_players` flatten (same reason as `RegistrationCount` and votes).

**Frontend.** `/predictions` is a top-level page (`PredictionsV2.vue`, the target icon in the tab bar), scoped to the active group and season like home. Two sub-tabs: **Matches**, one card per scheduled match with both teams set (`isScheduledMatch && rosterFullyComposed`), each with its three picks (team A, Draw, team B, with odds), so a member bets straight from the list; and **Leaderboard** (`?tab=leaderboard`). The picks stay buttons once predictions close, styled as locked (`aria-disabled`) rather than `disabled`. The line-ups live on the match page, not here.
- **Display states.** `matchPrediction.js`'s `predictionState`/`predictionsAreOpen` mirror `PredictionWindowError`. `predictionDisplayState` goes one step further: *Predictions open*, then *Awaiting result* (kick-off passed, no `ResultRecordedAt`), then *Settled* (with the final score). `settlePrediction` (odds − 1 on a hit, −1 on a miss) applies the same arithmetic as `ComputePredictionStandings`, so a card's points always add up to the leaderboard.
- **Behaviour.** `nowMs` is sampled once, as everywhere else. A refused bet (kick-off passed while the page was open, a network failure) shows the backend's message in the shared toast (see "Action toasts" below) and re-reads that match's summary.

### Seasons
A season runs September 1st → August 31st and has **no table**: `models.SeasonOf(Date) string` (`internal/models/date.go`) derives its label (`"2025-2026"`) from a match date alone — a date in September or later belongs to the season starting that year, an earlier one to the season that started the previous year. `GET /standings/seasons` just maps `SeasonOf` over the group's matches and dedupes/sorts in Go, so no new query or migration is involved.

`ComputeSeasons` counts **every** match, including a scheduled one nobody has played yet — so scheduling a match into a future season makes that season appear in `GET /standings/seasons` before a ball has been kicked. That's a decision, not an oversight, and there's a test pinning it: `GET /matches/details` is filtered by whichever season the frontend has selected, so dropping a future season from this list would make the upcoming match unreachable in the UI, which is strictly worse than one extra dropdown entry.

The frontend's default selection is deliberately **not** "the last season in the list" for exactly this reason — that was the original approach, and real testing surfaced its cost immediately: scheduling one match far enough out silently hid every other match behind a near-empty future season, since it's now the new last entry. `MatchesAndStandings.vue`'s `loadSeasons()` instead defaults to `seasonOf(new Date())` (`src/services/datetime.js`, mirroring `models.SeasonOf` exactly) — the season *today* actually falls in, independent of what matches happen to exist. A future scheduled match changes the *list* `GET /standings/seasons` returns; it must not change what "today" defaults to. The one fallback case — today's own season has no matches logged yet, so it isn't in the returned list — still falls back to the last season that does, the same "no filtering" degradation as before.

`GET /matches/details` takes the same optional `?season=` query param as the standings endpoints (`MatchHandler.GetMatchesDetails` reads `c.Query("season")` and passes it to `MatchService.GetMatchesDetails(groupID, season)`, which applies `FilterMatchesBySeason` to its result before returning). The filter is applied in Go rather than as a SQL `WHERE`, for the same reason the endpoint above needs no query: a season is a derived label, not a stored column. Empty means "no filtering", and that is what **every** call site in `standings.go` passes explicitly (`GetPointsStandings`, `GetScorers`, `GetSeasons`, `GetPlayerProfile`) — they load a group's whole history and run their own `FilterMatchesBySeason` pass (or, for `GetSeasons`, need every season there is), so pushing the season down would double-filter or collapse the seasons list to the one asked for.

### Standings (matches.go → standings.go)
`StandingsService` (`internal/services/standings.go`) wraps a `MatchService` and exposes `GetPointsStandings(groupID, season)`/`GetScorers(groupID, season)`/`GetSeasons(groupID)`, backing `GET /standings/points`, `GET /standings/scorers` and `GET /standings/seasons` — plus `GetMotmStandings(groupID, season)` backing `GET /standings/motm`, which follows the identical shape but needs one extra data source (a match's votes); see "MVP voting" above for why that source is a separate query rather than another join. The actual aggregation lives in package-level pure functions, `ComputePointsStandings`/`ComputeScorers`/`ComputeSeasons`, which take an already-loaded `[]models.MatchWithDetails` and know nothing about how that slice was produced. That split is what made both scoping axes cheap to add: the service loads a group's matches via `MatchService.GetMatchesDetails(groupID)` (the SQL-level scope) then narrows the slice in Go with `FilterMatchesBySeason` before handing it to the aggregators, which never changed. An empty `season` means "don't filter", so callers that don't pass one keep the all-time behaviour. Points standings only count matches where both teams have at least one player (an empty team means "not played yet", not a 0-0 draw — this is also the reason sign-ups live in their own table instead of as `MatchPlayer` rows); a match's result (win/draw/loss) is derived by comparing `Team.Score` between the two sides and applied to every player on each side.

`FilterCountedMatches(matches, now)` (alongside `IsMatchCounted`, same file) is a second, later filter applied right next to `FilterMatchesBySeason` in `GetPointsStandings`/`GetScorers`/`GetPlayerProfile` (and `GetEloStandings`) — real feedback: an admin can compose a scheduled match's roster ahead of its own kick-off (via "Fill teams from sign-ups"), which already satisfies `ComputePointsStandings`'/`ComputeScorers`' own "both teams have players" check, so a match could count before it had actually been played. A match counts the moment its result is recorded (`ResultRecordedAt`, set by the first save at or after kick-off), so the standings move as soon as the score is saved rather than at midnight. A match created without a schedule never gets a `ResultRecordedAt`, so for it alone `IsMatchCounted` falls back to `IsMatchCompleted`: "Completed" from midnight the day *after* it was played (the frontend's own Date-only `matchStatus` rule). A scheduled match whose score was never recorded does not count, whatever its date. MVP awards use `FilterMotmCountedMatches` instead (`GetMotmStandings`, and the profile's `MotmAwards`): the same counted rule *and* the vote closed (`IsMotmVoteClosed`, the `VotingWindowError` deadline, midnight two days after the match day), so a leader is never awarded while the vote can still change. `FilterCompletedMatches` (the plain midnight-after filter) is no longer used by the standings. Deliberately **not** applied to `ComputeSeasons`/`GetSeasons`: that list already, and separately, includes an unplayed scheduled match on purpose (see "Seasons" below), and these filters must not disturb it.

`models.PointsStandingRow`/`models.ScorerRow` each carry an `IsMember bool` (json `"IsMember"`, matching these two structs' existing PascalCase convention). `GetPointsStandings`/`GetScorers` set it as a **post-processing step** after calling `ComputePointsStandings`/`ComputeScorers` — those two pure functions are untouched and still know nothing about group membership, only about already-loaded match data. The service loads the group's current member IDs via the private `currentMemberIDs(groupID)` helper (itself a thin wrapper over `GroupMembershipService.GetPlayersByGroupID`, built into a `map[uuid.UUID]bool`) and sets `row.IsMember` per row by `PlayerID`. A player removed from the group keeps every row their match history earns them — standings are computed from match history, not current membership — just tagged `IsMember: false`, which is what `RankingsV2.vue` uses to label the row "(left the group)" rather than hiding or altering it. `StandingsService.GetPlayerProfile` (below) deliberately does **not** call `currentMemberIDs`: every group it walks is, by construction, one the caller currently belongs to, so the field would be trivially `true` everywhere and isn't worth the extra query — its rows are left at the zero value (`false`), which the profile page doesn't read anyway.

**Agoranking** (`internal/services/agoranking.go`, `GET /standings/agoranking`, the fourth Rankings tab) is a **hidden feature** (`agoranking`, `models.FeatureAgoranking`, see "Hidden features"): without the `player_features` row the route answers 403 (`PlayerService.HasFeature`, checked before the group), and `RankingsV2.vue` neither shows the tab nor calls the route (`?tab=agoranking` falls back to Points). The visual tests turn it on for every Rankings baseline. It ranks points per match, weighted by matches played, with no table of its own: `GetAgoranking` loads, season-filters and `FilterCountedMatches` exactly like `GetPointsStandings`, and the pure `ComputeAgoranking` reuses `ComputePointsStandings`' rows (win 3, draw 1, loss 0, same "both sides have players" rule). Matches = the group's matches that count; `N = ceil(Matches / 3)`, both the number of "average" matches every player starts with and the minimum to be ranked; the group average = total points ÷ total participations; `Rating = (points + N × average) ÷ (matches + N)`. The response is one object, `{Matches, N, GroupAverage, Ranked, Unranked}`, each row carrying `Played/Won/Drawn/Lost/Points`, the **unrounded** `Rating` and `IsMember`. `Ranked` (matches ≥ N) is ordered by rating (ties within 1e-9 count as equal), then more matches, then name; `Unranked` by matches, then points, then name (names without case). The frontend (`RankingsV2.vue`, helpers in `services/agoranking.js`) shows the rating with two decimals, folds "How it's calculated" and "Not ranked yet · n" closed by default, and loads the endpoint with its own `.catch` so a failure only breaks that tab. The explanation deliberately has no number in it (no threshold, no average): both change through the season.

### Elo rating (CLI-only)
Each group also has an implicit Elo rating pool over its players — "implicit" because, unlike every other number in this doc, it is not exposed through any HTTP route or the frontend at all. `internal/services/elo.go`'s `ComputeEloStandings` and `StandingsService.GetEloStandings` are wired only into `cmd/elo/main.go`, a small **read-only** CLI the repo owner runs locally to inspect the numbers privately before deciding whether, or how, to ever surface this to players. That is a deliberate product decision, not a partial implementation: `main.go` gains no new route, and nothing under `frontend/` changes for this feature. The ratings themselves are still not exposed anywhere, but they now **indirectly** reach players through the odds on the Pronostic page (see "Match predictions" above): `EloRatingsBeforeMatch` reuses `ComputeEloStandings` to price each match. A change to the Elo constants therefore changes those odds too, including the ones past predictions are settled against.

**Scored per group, never across groups** — the same reasoning `GetPointsStandings`/`GetScorers`/`GetMotmStandings` already build on: a calciotto group never plays another group, real matches are always one group's own players against each other, so a rating pool is scoped the identical way, via the identical call (`MatchService.GetMatchesDetails(groupID, "")`). There is deliberately no `GetPlayerProfile`-style `Overall`/cross-group aggregation here — a player's Elo in one group says nothing about their level in an unrelated group's own pool (different opponents, different history), so combining them the way points/goals/MOTM awards are combined across a player's groups would produce a meaningless number.

**Continuous across the group's whole history, never reset per season** — the one point where this deliberately *breaks* the pattern every other standings table in this codebase follows. `GetPointsStandings`/`GetScorers`/`GetMotmStandings` all take a `season` parameter (and `GetEloStandings` conspicuously does not, anywhere in its signature) because points/goals/MOTM awards are all accumulators that only ever make sense measured over a fixed period — "top scorer of 2025-2026" is a well-formed question, "top scorer ever" isn't especially interesting since it just rewards playing more matches. A rating is different: it's an estimate of current skill, and skill does not reset to a common baseline every September 1st the way an accumulator implicitly does by being filtered per season. Restarting everyone at `EloStartingRating` each season would throw away exactly the information a rating exists to carry forward.

**Derived fresh on every call, never persisted** — no new column on `Player` or anywhere else, no caching layer, nothing written to the database at all; `ComputeEloStandings` replays every one of a group's completed matches from scratch each time it's asked. This is the same "derive, never store" philosophy the waiting list, the MVP award and the match-status badge already follow elsewhere in this codebase, applied to a case where it pays off unusually well: a group's entire history is at most a few hundred matches with on the order of sixteen players each, cheap to replay in Go on every call, and in exchange editing or deleting a past match (`MatchService.UpdateMatch`/`DeleteMatch`, both pre-existing) needs zero special-case invalidation logic for this feature — there is no cached rating anywhere that could go stale, because there is no cached rating at all. The alternative (a stored, incrementally-updated rating) would need a migration path for every future edit to old scores, which this sidesteps entirely.

**Filtering reuses two existing rules verbatim, no new ones.** "Is this match played" is exactly `ComputePointsStandings`'s own check (`len(match.Teams) == 2` and both teams non-empty) — mirrored, not reimplemented, inside `ComputeEloStandings` itself, the same defensive posture `ComputePointsStandings` already takes rather than trusting a caller's pre-filter. "Does this match count" reuses `FilterCountedMatches(matches, now)` exactly as `GetPointsStandings`/`GetScorers` already do, for the identical reason: an admin can compose a scheduled match's roster (and therefore satisfy the "played" check above) before its own kick-off, and a rating update must not fire before the result is in. `FilterMatchesBySeason` is never called here at all — there is no season parameter to apply it with.

**Chronological replay is not incidental — `MatchService.GetMatchesDetails` returns matches `ORDER BY match_date DESC`, the opposite of what a replay needs**, so both `StandingsService.GetEloStandings` and `ComputeEloStandings` itself independently sort ascending (by `Date`, then `CreatedAt`, then `ID` as a fully deterministic final tie-break — the same three-level ordering `MatchRegistrationEntry`'s own `created_at ASC, id ASC` convention already established one level down) via the shared private `sortMatchesChronologically` helper. `ComputeEloStandings` sorting its own input unconditionally — rather than documenting "expects pre-sorted input" as a precondition a caller could silently violate — is what makes an out-of-order input slice a correct, directly unit-testable case rather than undefined behaviour: `elo_test.go` feeds matches in reverse order and asserts the same result as the correctly-ordered input, precisely because a win-then-draw and a draw-then-win over the same two matches produce different final ratings — Elo's update is nonlinear, so the two orderings do not commute.

**The exact math** is a standard chess Elo update, tuned for this domain. A player enters a group's history at `EloStartingRating` (1500) the first time they're encountered while replaying — no separate initialization pass. A team's expected score is the logistic function, divisor `EloDivisor` (400), of the gap between the two teams' **average** pre-match rating (`sum(ratings)/len(players)` per side — team sizes need not match); the actual score is 1/0/0.5 for a win/loss/draw, read off `Team.Score` exactly the way `ComputePointsStandings` already derives win/draw/loss. Both teams' expected and actual scores, and every player's resulting delta, are computed from **pre-match** ratings before any of them are applied, so team B's update can never see team A's already-applied delta for the same match or vice versa. Each player's own K-factor — `EloKProvisional` (60) below `EloProvisionalGameThreshold` (10) rated games in this group, `EloKSteady` (40) at or above it — is based on **that player's own** prior rated-games count, not the match's position in the group's history, so a veteran and a debutant meeting in the same match are each updated at their own pace; the counter only advances once every delta for the match has been computed, so it affects a player's *next* match, never the current one.

The K-factor split is intentionally more aggressive than a typical chess federation's (FIDE's own provisional/steady K-factors are considerably lower). A competitive chess player accumulates rated games far faster over a season than a calciotto player realistically will — a weekly game caps out around 40-50 matches a year, and plenty of players log far fewer — so each individual result has to carry more signal for the rating to say anything meaningful within a season or two, rather than converging so slowly it's still mostly noise a year in.

**Output ranking** is rating descending, name ascending as the tie-break — the identical convention `ComputePointsStandings`/`ComputeScorers`/`ComputeMotmStandings` already use.

Code lives in `internal/services/elo.go` (`ComputeEloStandings`, the constants, `StandingsService.GetEloStandings`) and `cmd/elo/main.go` (the CLI itself); `models.EloStandingRow` is the DTO, declared in `customModels.go` alongside `PointsStandingRow`/`ScorerRow`/`MotmStandingRow` even though, unlike them, it is never serialized by any handler today. Run it the same way any other `cmd/` script is run outside Docker (see "Gotchas" below for the `DB_HOST=localhost` etc. env vars needed): `go run ./cmd/elo -group "Default"` (by exact, case-insensitive name) or `go run ./cmd/elo -group <uuid>` (by id) for one group's table, or `go run ./cmd/elo -all` for every group in the database. It never mutates anything, which makes it the only read-only tool under `cmd/` — `seed`, `richseed`, `perfsetup` and `addmember` all write.

### Player profile (cross-group)
`GET /players/me/stats` is the one standings-shaped endpoint that isn't scoped to a single group. `StandingsService.GetPlayerProfile(playerID, season)` walks the caller's groups (`GroupMembershipService.GetGroupsByPlayerID`, injected into `StandingsService` alongside `MatchService` and wired in `main.go`), loads and season-filters each group's matches exactly like the group-scoped endpoints, then runs `ComputePointsStandings` once per group (`PerGroup`) and once over the concatenation of every group's matches (`Overall`) — the aggregators themselves are untouched. A group the player belongs to but has never played in still gets a zeroed `PerGroup` entry, and a player with no matches anywhere gets a zero `Overall` row rather than an error; `models.PlayerGroupStanding` embeds `PointsStandingRow` so the JSON stays flat. Two additive fields ride on the same response: `Seasons` (the sorted union of `ComputeSeasons` over every group's unfiltered matches, unchanged by `?season=`), and `PredictionPoints` on `Overall` and each `PerGroup` row. A group's points are `ComputePredictionStandings` over that group's own history (`FilterResultRecorded` of the season filter, Elo replayed on the unfiltered matches), and `Overall.PredictionPoints` is the sum of those per-group totals rather than a settlement of the groups mixed together.

`MotmAwards` rides alongside at both scopes — `models.PlayerGroupStanding`/`models.PlayerOverallStanding` each embed `PointsStandingRow` and add their own `MotmAwards int` rather than growing `PointsStandingRow` itself, since that type is also `GET /standings/points`' own row shape and has no business carrying an MVP count. Computing it follows the exact same "load once, compute at two scopes" shape the rest of this method already has: for each group, the already-loaded (season-filtered) matches are turned into match ids, `MatchVoteService.TallyVotesForMatches` loads their votes in one round-trip (the same call `GetMotmStandings` makes, just per group here), and `ComputeMotmStandings` finds this one player's award count via the new `findMotmAwards` helper (mirroring `findPointsRow`, defaulting to 0 when the player has no awards rather than treating absence as an error). Every group's `votesByMatch` map is merged into one combined map as the loop goes — match ids are globally unique, so two groups' entries can never collide under the same key — which is what lets `Overall.MotmAwards` be computed once, at the end, over the concatenation of every group's matches, the same way `Overall`'s points/goals already are.

The player comes from the JWT, never from the URL — there is deliberately no `/players/:id/stats`. Group membership is itself privileged information, so returning another player's cross-group profile would leak which groups they belong to, including groups the caller isn't in, bypassing `RequireGroupMembership`. That's also why the route is wired with `authRequired` only and no `requireGroupMember`: there is no single `group_id` to authorize against, and the handler only ever reports on the token holder's own groups. Viewing someone else's profile would need a visibility model of its own and doesn't exist.

### Input validation
`PlayerService.CreatePlayer` trims the name and rejects empty input (`ErrEmptyPlayerName`, a sentinel in `internal/services/players.go`). It has no duplicate-name check of its own, and `Player.Name` carries no DB-level uniqueness either (see the auth section above) — `PlayerService` stays entirely group-agnostic. It is not reachable through any HTTP route today (see "Group bootstrapping" above — the admin-created "ghost player" flow it used to back, `POST /players`, was removed entirely); it's still called directly by `cmd/seed` and by test fixtures across the codebase as a quick way to create a player with no credentials, purely for setup. Match date validation happens for free via the `Date` type's `UnmarshalJSON`: a malformed date fails JSON binding in the handler and surfaces as a 400 through the existing `ShouldBindJSON` error path, with no extra service-side check needed.

**Self-service rename** (`PATCH /players/me`, `authRequired` only — same reasoning as `GET /players/me/stats`: it only ever acts on the JWT's own player id, so there's no single `group_id` to authorize against) is the one place `Player.Name` uniqueness *is* enforced, and deliberately **globally** rather than per-group — a real divergence from every other name-touching path in this codebase, driven by an explicit product call rather than a technical one. `PlayerHandler.UpdateMyName` reads the caller's id via `playerIDFromContext`, trims the incoming name, and calls `PlayerService.UpdateName(playerID, newName)`, which: rejects an empty/whitespace-only name with the existing `ErrEmptyPlayerName` sentinel (shared with `CreatePlayer`); else checks `LOWER(name) = LOWER(?) AND id != ?` against every other player row and rejects a collision with the new `ErrPlayerNameAlreadyUsed` sentinel (`internal/services/players.go`) — both map to 400 via `errors.Is` in the handler; else updates the row. The `id != ?` exclusion is what makes renaming to your own current name (or the same name in a different case) a no-op success instead of a false collision against yourself. This is intentionally inconsistent with `CreatePlayer`/`SignupNewPlayer`'s total permissiveness on name collisions (see above): creation stays cheap and collision-tolerant because a display name legitimately isn't a unique identifier at that point, but a player *actively choosing* to rename themselves into a name someone else already holds is a different, narrower action product wants blocked outright, everywhere in the system, not just within one group — there is no per-group angle here since a rename isn't scoped to any group at all.

### Frontend

The screens themselves (every page is a design v2 one) are described in "Design v2" below; this section covers the plumbing they share.

- **Routes** (`src/router/index.js`, `createWebHistory`): `/` (`MatchesAndStandings.vue`, the home shell, see below), `/rankings` (`RankingsV2`), `/matches/new` (`NewMatchV2`), `/matches/:id` (`MatchView`, every member), `/matches/:id/edit` (`EditMatchV2`, admins), `/predictions` (`PredictionsV2`), `/profile` and its sub-pages `/profile/account`, `/profile/notifications`, `/profile/groups/:id` and `/profile/groups/:id/settings` (all `ProfileV2`), and the public pages `/login`, `/signup`, `/forgot-password` and `/reset-password`. Those four are the ones `beforeEach` lets through without a token (`publicRoutes`), and `App.vue` treats them as unauthenticated: a page reachable without a token must not load `/groups/me` nor show the tab bar. `/standings` and `/groups` are bare redirects (to `/` and `/profile`) kept for old bookmarks. There is deliberately no catch-all route, so an unmatched URL renders an empty `<main>`.
- **`/matches/:id/edit` is admin-only through a real `beforeEnter` guard.** `canEditMatch(matchId)` loads the caller's groups (`loadMyGroups()`, the cached `GET /groups/me`), finds the one owning the match with `findGroupForMatch` and checks its role; anything else, including a network error, redirects to `/` (fail closed). It is a frontend-only gate: `GET /matches/:id/details` stays open to every member, since the match page needs it, and every write is admin-gated on the backend anyway. `findGroupForMatch` tries `getMatchDetailsByID(matchId, group.id)` for each of the caller's groups in turn, a 404 meaning "not this one": called without a `group_id`, the backend resolves the caller's *first* group and 404s every match of their other groups.
- `src/services/api.js` is the single Axios client (`API_BASE_URL` from `resolveApiBaseUrl` in `src/config/apiBaseUrl.js`: the `VUE_APP_API_BASE_URL_BY_HOST` entry for the current hostname, else the `VUE_APP_API_BASE_URL` env var, default `http://127.0.0.1:8080` — the `VUE_APP_` prefix is mandatory, see the deployment section) — every backend call goes through here. Its request `timeout` is similarly overridable via `VUE_APP_API_TIMEOUT_MS` (`apiTimeoutMs`, falling back to today's hardcoded `10000` when unset or invalid) — added after a real load-test run showed every request aborting client-side (`ECONNABORTED`, no `.response`, surfacing as the generic "...failed. Please try again." fallback) right around 10s under concurrent load, even though the backend's own logs showed a clean 200 for the same requests a few seconds later. Below that ceiling, a slow-but-successful backend response and a genuinely broken one are indistinguishable to the caller — raising this is what lets a deliberate load test see the backend's *real* response time instead of measuring this client-side cutoff. See "Perf load testing" below. The calls on one match named in the path (sign-ups, votes, predictions, positions) take **no** `groupId`, and deliberately so: the backend derives the group from the match in the path, and passing one would be the very hole that design closes.
  - `api.js` threads `group_id` as a query param through `getMatchesDetails`/`getMatchDetailsByID`/`getPointsStandings`/`getScorers`/`getSeasons` via a shared `query({...})` builder that drops empty values. `getMatchesDetails(groupId, season)` also carries the optional `season`, the same way `getPointsStandings`/`getScorers` do. `createMatch(matchData, groupId)` puts the group in the **body**, under the snake_case key `group_id` — `CreateMatch` binds into a dedicated request struct whose tag is `json:"group_id"`, and Go's case-insensitive fallback does not see past the underscore, so a `GroupID` key binds to nothing and the match silently lands in the player's first group instead. The optional third `scheduling` argument is what carries `scheduled_at`/`registration_opens_at`/`max_players` and, when "Sign me up" is ticked, `register_creator: true`.
- **Active group** — `src/services/activeGroup.js` holds the group the home page, rankings and predictions are scoped to (the top bar's group select). It's a per-device preference in `localStorage` (`calciotto-active-group`), not server state: the backend has no notion of an "active" group, `resolveGroupID`/`resolveGroupIDForMembership` just take whatever `group_id` a request carries.
  - `resolveActiveGroup()` is the whole contract: it loads `GET /groups/me`, and if the stored id isn't in that list (the player left the group, another account used this browser, or this is a fresh device/session with nothing stored yet — e.g. right after logging in) it falls back to the player's **favorite group** (`group.is_favorite`, set server-side — see "Group bootstrapping" above) and rewrites the stored value, rather than sending a `group_id` `RequireGroupMembership` would reject. `groups[0]` is kept only as a further defensive fallback if no group is marked favorite (shouldn't happen given the backend invariant, but costs nothing to guard). `resolveActiveGroupId()` is the thin wrapper the views call in `created()`; it swallows errors and returns `''`, which just means "send no `group_id`" — i.e. degrade to the old first-group behaviour instead of taking the view down.
  - The `GET /groups/me` promise is cached at module scope (failures aren't), so every consumer on a page shares one request. That's safe precisely because the active group only ever changes through a **full page reload** — with one exception the cache has to be told about explicitly: `clearMyGroupsCache()` (exported alongside `loadMyGroups`, which also takes `{ force: true }` for the same purpose), called from `App.vue`'s `logout()` next to `clearActiveGroupId()`. Logging out is the one transition that changes *who* the caller is without leaving the page, so without it the next account to log in on that tab would be handed the previous one's groups and roles straight out of the in-memory promise — including an `admin` role it doesn't have. There is no reactive store (no Vuex/Pinia) and the views read the group once, in `created()`, so a reload is what actually re-scopes the app.
- **`MatchesAndStandings.vue`** (route `/`) is the home shell: it resolves the active group, the caller's role on it and the season (today's season by default, `seasonOf(new Date())` in `datetime.js`, mirroring `models.SeasonOf`; the last season with matches when today's has none yet, so a match scheduled into next season never hides every other one), publishes them to the top bar's selects (`v2Context`, provided by `App.vue`), and only then mounts `HomeV2` so it never asks for `/matches/details` without a `group_id`. A `?match=<code>` link (a share, a push notification) is turned into `/matches/:id` right away; `MatchView` finds the match's own group itself (`findMatchInMyGroups`, `src/services/v2Match.js`).
- `#app` carries an explicit `color: var(--text-primary)`: `.dark-mode` toggles on `#app`, a *descendant* of `body`, so `body`'s own `color` resolves against the light value and plain inheritance hands that down to anything that sets no colour of its own (see the comment in `App.vue`).
- **Share links are self-hosted "tinylinks"**, not the full `/matches/:id` URL. A raw UUID reads badly next to "Join Agoran" in a chat, and a public shortener (TinyURL, is.gd, ...) was ruled out for the browser CORS and uptime requirements: most don't set the CORS header a browser needs to read their response, and either way it's an external dependency's uptime for something this simple. `src/services/shortLink.js`'s `encodeMatchId`/`decodeMatchId` instead re-encode the match id's own 128 bits as base62 (`92bbe7a1-fa67-49dc-9058-85837504d0d4` → something like `4kX9pQz...`, no hyphens) — losslessly and reversibly, with **no lookup table and no new backend route or storage at all**: the "short link" *is* the id, just spelled in a smaller alphabet, so there's nothing to keep in sync or garbage-collect. `router/index.js`'s `/m/:code` is a bare `redirect: to => ...` entry (no component of its own): it calls `decodeMatchId(to.params.code)` once, purely to validate the code, then redirects to `/?match=<code>` — the **raw code**, not the decoded id; a malformed code (hand-edited, truncated in transit) falls back to `/` rather than throwing mid-navigation.

  Every code is left-padded with `'0'` to a **fixed width** (`CODE_LENGTH`, the length of encoding `2^128 - 1` — computed once from `BASE62_ALPHABET`'s own length rather than hardcoded) — this is load-bearing, not cosmetic. Base62, like any positional numeral system, strips leading zero bits the same way `parseInt` would, so a UUID with several leading zero bytes would otherwise encode to a noticeably *shorter* code than a typical one. Without a fixed width, `decodeMatchId` has no way to tell a genuinely short code from a longer one truncated in transit (a copy-paste cut short, say) — every character of a truncated code is still valid base62, so it doesn't fail to parse, it just silently produces a different, wrong-but-plausible UUID (an actual bug this codebase shipped and then fixed once a code review caught it — the fix is the fixed width plus a length check, not a "try to detect corruption" heuristic bolted on after the fact). `decodeMatchId` rejects any code whose length isn't exactly `CODE_LENGTH` before decoding at all, and separately rejects a same-length code whose value still exceeds `2^128 - 1` (possible since `62^CODE_LENGTH` overshoots `2^128`) rather than letting the fixed-width hex slicing silently drop its high bits. Decoding itself re-pads the reconstructed hex to the UUID's fixed 32 digits before re-inserting the hyphens, same reasoning one level down (a decoded value with leading zero bytes needs its hex grouping restored).
- **Two pure service modules** hold the date and sign-up logic that is easy to get wrong, kept out of the components because testing them through a mounted component would mean one mount per case:
  - `src/services/datetime.js` — the whole date path, both directions. Outbound (`toLocalRFC3339`, `dateTimeLocalToRFC3339`, `formatUTCOffset`): a local `YYYY-MM-DD` day plus an `HH:MM` time into RFC3339 **carrying the browser's own UTC offset**, because the backend derives the match's day (and season) from `scheduled_at` in the offset it was sent in. Nothing here goes through `toISOString()`, which always emits `Z` and would file a 00:30 Paris kick-off under the previous day; `<input type="datetime-local">` has the mirror-image problem (its value carries no offset at all), so it routes through here too. The offset is read from a `Date` built at that exact local instant rather than from `new Date()`, so a match scheduled across a DST boundary is stamped with the offset in force *then*. Inbound (`formatDateTimeForDisplay`, `formatDateTimeShort`): rendered in the **browser's** zone, no `timeZone` option — a kick-off is a single instant and a player elsewhere wants to know when it happens for them — returning `''` rather than "Invalid Date" for unparseable input. Calendar days (`Match.Date`'s `YYYY-MM-DD`) are the third case and the opposite one, handled by `parseCalendarDay` plus `formatCalendarDay`/`formatCalendarDayLong`/`formatCalendarDayShort`: `new Date('2026-09-06')` is specified to parse a date-*only* string as **UTC** midnight (a date-*time* string with no offset parses as local — the inconsistency is in the language), so formatting it in the browser's zone rendered the *previous* day for anyone west of Greenwich, which is what the components used to do by hand. The parse is explicitly local because a calendar day is not an instant: `Match.Date` is the day the group played, identical for every viewer, where `ScheduledAt` is one instant deliberately shown in each viewer's own zone. An out-of-range day (`2026-02-31`) is rejected rather than rolled over into March, and unusable input **echoes the raw string** instead of returning `''` — a kick-off line can be dropped from a card harmlessly, but a match's date is the card's identity, so a blank would just look broken.
  - `src/services/matchRegistration.js` — `deriveRegistrationState(match, nowMs)` collapses the four scheduling fields into one of five states (`unscheduled` / `not-open-yet` / `open` / `closed-by-admin` / `closed-at-kickoff`), mirroring `RegistrationWindowError` on the Go side. The backend stays the authority and every action is re-checked there, but a UI that only found out by getting a 409 would show a Participate button that always fails and, worse, a Withdraw button that silently stopped working (closing the list refuses both — hence the single `registrationsAreOpen` predicate both buttons hang off). Two deliberate divergences from the Go ordering: an explicit close wins over "hasn't opened yet" here, because this decides what the *user is told* and "sign-ups open Friday" would be a promise the closed flag already broke; and `nowMs` is passed in rather than read inside, so a view samples the clock exactly once. The two "closed" states are separate because only one is reversible. `registrationStateLabel(state)` is the state → short-label mapping ("Sign-ups open"/"Sign-ups not open yet"/"Sign-ups closed", the two closed states sharing one label). `teamsAreComposed(match)` (true once either team has ≥1 player) is what turns a match from "about places" into "about teams" on home and the match page. `fillTeamsFromRegistrations` is v1's mechanical team split, no longer called by the app (the edit page uses `splitByPositions`, see "Design v2") but still unit-tested.
- API payload field casing is PascalCase on the match payloads (`ID`, `Name`, `Score`, `Players`, `GoalsScored`) — this comes directly from the Go JSON struct tags in `customModels.go`, not a frontend convention; some older DTOs (`Team`, `GroupWithRole`, `PlayerWithRole`) are lowercase.

### Seeding data
`app/cmd/seed/main.go` is the real seeding tool (replaces an older set of ad hoc `*_test.go` files that abused `go test` to insert rows with no isolation or cleanup — those are gone). It reuses the normal `internal/services` layer, so seeded data goes through the same code path as the API. It creates 12 players, 2 teams (named "Black"/"White" — passed to `groupService.CreateGroup` as `services.DefaultTeamSpecs`), and N **unscheduled** matches on the last N Sundays — it passes `services.MatchSpec{Date: date}` and nothing else, so seeded history looks exactly like a match an admin recorded after the fact, with no sign-up list — each match splitting the players randomly between the two teams with a weighted-random goal count per player. Run via `go run ./cmd/seed` (locally, with `DB_HOST=localhost` etc. exported) or `docker compose exec backend go run ./cmd/seed` (inside the network, where the `db` hostname resolves).

`app/cmd/richseed/main.go` is a separate, one-off complement to `cmd/seed` for manual testing: it does **not** replace `cmd/seed`'s minimal, idempotent contract above, it enriches whatever `cmd/seed` already produced. It gives every credential-less ("ghost") player left in the database a real email/password, creates three more groups alongside "Default" (with the seeded "thibaut" joining each as a plain member rather than an admin), randomly spreads the rest of the player pool across all four groups, and — in every group — generates a rich, varied spread of matches across several past and current seasons: plain already-played matches, a recently-played scheduled match with a composed roster and MVP votes, and one scheduled match in each sign-up state the app supports (not yet open, open with a waiting list, closed but not yet composed, and closed with the roster already built ahead of kick-off). Unlike `cmd/seed`, group/membership creation is safe to re-run (existing groups and memberships are reused/skipped), but **match generation is not idempotent** — re-running it adds another full spread on top of whatever is already there. `-recent-only` regenerates just the one recently-played composed match (+ votes) per group, for recovering that one piece without duplicating everything else (the scenario that motivated it: a kick-off dated too far in the past for the MVP voting window to still be open when the votes are cast). Run the same way as `cmd/seed`, after it: `go run ./cmd/richseed`.

`app/cmd/demoseed/main.go` is the one to reach for when you want to *look at* the app with every feature populated, and it is deliberately different from both tools above: it **TRUNCATEs every application table** and rebuilds a complete dataset from scratch, with **every date computed from the moment it runs**. It does not need `cmd/seed` first, and re-running it replaces the data rather than stacking on top. That is the point: re-run it next week and yesterday's match is still yesterday's, the composed match is still three days out, the open sign-up list still opened yesterday. A dataset seeded once with absolute dates drifts as the calendar moves (a "voting still open" match quietly becomes a closed one).
- **Content:** 16 players (`<name>@mail.com` / `user1234`) across three groups. `thibaut` is admin of "Default" and a plain member of "Les Copains du Mardi" (admin `matthias`) and "Foot du Vendredi" (admin `vincent`), so one login sees both the admin and the member side.
- **Per group:** four plain unscheduled matches in the previous season (season selector and Elo history behind the odds), then six weekly scheduled matches already played (`-36` to `-8` days at the group's usual time, plus one that kicked off 20 hours ago so its 24-hour MVP vote is still open whenever the script runs: sign-up list, closed, composed, result with the odd own goal and `ResultRecordedAt` set, MVP votes, settled predictions), then a match that kicked off two hours ago with predictions but no score saved yet (*Awaiting result*), then one upcoming match in each remaining state: composed with predictions open (`+3`), sign-ups closed but no teams (`+5`), sign-ups open with a waiting list (`+7`), sign-ups not open yet (`+14`, opening at `+4`).
- **Kick-offs are in `Europe/Paris`**, at a fixed time per group (`time/tzdata` is embedded, so this doesn't depend on the container's zone). A match's `Date` and season therefore follow the Paris calendar day.
- **`thibaut` is left with nothing to do on the matches still open to actions:** no prediction on the `+3` match, not signed up on the `+7` one, no vote on yesterday's match. Logging in as him shows every action available.
- **Real services where a window is still open, direct inserts where it has closed.** Sign-ups on upcoming matches, predictions on the `+3` match and votes on yesterday's match go through `Register`/`Predict`/`Vote`, the same code path as the API. For matches already played, those services would rightly refuse (the window is over), so registrations, votes and predictions are written straight into their tables, timestamped as if made before kick-off.
- **Safety and reproducibility:** it refuses to run when `DATABASE_URL` is set, which is how production is reached (see `pkg/database/connect.go`). Randomness (goals, who signs up, picks) is logged as `random seed: N` and replayable with `-rand-seed N`; two runs with the same seed on the same day produce identical data.

Run it inside the network (`docker compose exec backend go run ./cmd/demoseed`) or on the host with `DB_HOST=localhost` etc. Note that the `seed` compose service still runs on every `up`; after `demoseed` it just sees players and skips.

`app/cmd/addmember/main.go` is another, much smaller one-off, and unlike the two above it is meant to be run against **production**: it adds a single existing player to a single group directly through the service layer, for the case of a player who ended up in **no group at all** (an account created before invite codes were mandatory, or one whose only membership was removed). No HTTP route can do this — `POST /groups/:id/players` needs an admin of the target group, and `POST /groups`/`POST /groups/join` are disabled (see "Group bootstrapping" above) — so bypassing the routes is the whole point, the same reasoning `cmd/perfsetup` gives for creating its throwaway group. It takes `-player-id` and `-group-id` (both UUIDs, read out of the `players`/`groups` tables) plus an optional `-role` defaulting to `member`, and deliberately has **no `-is-favorite` flag**: `AddPlayerToGroupWithRole` already grants the favorite automatically on a player's very first membership ever, which is exactly this tool's case. It verifies that precondition itself and refuses if the player unexpectedly already belongs to a group, rather than silently leaving them with two favorites or none. Run it with `DATABASE_URL` set (unlike `cmd/perfsetup`, which refuses it and only runs against a local database): `go run ./cmd/addmember -player-id <uuid> -group-id <uuid>`. Like `cmd/elo`, and unlike `cmd/seed`/`cmd/richseed`, it touches nothing but the one membership row it creates.

### Perf load testing
The performance test exercises the signup and participation flows on a loopback frontend and API backed by a disposable `calciotto_perf` database.

1. **`app/cmd/perfsetup/main.go`** creates a group, an administrator, and a match with open registrations in the local test database. It requires loopback `DB_HOST` and rejects `DATABASE_URL` and `DATABASE_URL_UNPOOLED`. The admin password comes from `PERF_ADMIN_PASSWORD` or `-admin-password`.
2. **`frontend/loadtest/run.js`** drives virtual users through signup, match participation, viewing the group roster, and logout. It accepts a loopback frontend and blocks remote browser requests. The report includes timings and errors for each step:
   - **A bare `page.waitForURL`/element wait cannot tell "rejected" apart from "just slow."** A rejected request (rate limit, a validation error, a client-side abort) never navigates, so a naive wait only ever reports `Timeout Xms exceeded` regardless of *why* — indistinguishable from a hung network call. `waitForOutcome` polls for either the expected success condition or a visible error element (`.error-message` for signup, the shared toast's `.toast-message.error` for Participate) and reports whichever resolves first, and a screenshot is saved to `loadtest/reports/failures/` on every failure. This is what caught the real finding below: a screenshot taken at a "failed" signup's timeout showed the app already fully redirected and rendered past it — the request had succeeded, just after the wait gave up.
   - The report includes the HTTP status or network error for the signup and participation writes. These diagnostics omit response bodies to keep session data out of the report.

   Every step's timing is recorded per user (`stepTimer`) and written, alongside a pass/fail summary, to `loadtest/reports/report-<timestamp>.{json,txt}` (gitignored, like the Playwright visual-test artifacts) — the console output alone is lost once a terminal scrolls past it. `SIGNUP_TIMEOUT_MS`/`PARTICIPATE_TIMEOUT_MS`/`STEP_TIMEOUT_MS` (defaults 60000/60000/120000) exist because a real run showed these need real headroom under load — bcrypt hashing and DB contention under N concurrent signups can legitimately take much longer than a single request would, and a load test wants to *measure* that latency, not misreport it as a hung request.
3. Stop the disposable database after the run. **`devops/perf-cleanup.sql`** provides a preview and an optional cleanup transaction for a retained loopback `calciotto_perf` database.

`frontend/loadtest/README.md` documents the local database, fixture setup, app startup, and report. Set temporary signup limits on the local Go process.

## Installable app (PWA)

The frontend is an installable web app: added to a phone's home screen, it opens full screen with no browser address bar, on Android and iOS alike. It is also the groundwork for push notifications, which need a service worker and, on iOS, an installed app.

- **`public/manifest.webmanifest`** (`display: standalone`, white theme and background) plus the tags in `public/index.html`: `<link rel="manifest">`, an `apple-touch-icon` and the `apple-mobile-web-app-*` metas, since iOS takes its icon and home-screen title from those rather than from the manifest. `theme-color` colours the phone's status bar; `App.vue` keeps it in step with the in-app light/dark toggle (`syncThemeColorMeta` in `theme.js`), because that toggle is the app's own setting, not the system's. The iOS status bar style is `default` rather than `black-translucent`: the page then starts below the status bar instead of underneath it, so nothing sticky has to account for it.
- **`viewport-fit=cover`** is what makes `env(safe-area-inset-*)` report real values on a notched iPhone. The bottom tab bar and the mobile toast already padded with them, but without this they were always 0, and the installed app's tab bar would have sat under the home indicator.
- **Icons** — every icon the app ships comes from one source, `frontend/branding/icon-source.png` (a full-bleed 1024 px square on design v2's navy `#141a33`, kept out of `public/` so the original isn't deployed; it is the orange v2 mark, `branding/v2/variante-a-sombre.png`, placed at 614 px on that navy — and `icon-source-light.png` is `variante-b-claire.png` the same way on `#eef0f7`): `public/icons/` (192 and 512 px, a 512 px maskable one for Android's crop, the 180 px `apple-touch-icon`, opaque since iOS shows transparency as black, and the 32 px tab favicon) plus `public/favicon.ico`, written as that same 32 px PNG behind an `.ico` header. They are generated, not drawn: `sh scripts/generate-icons.sh branding/icon-source.png --light branding/icon-source-light.png --zoom 1.5 --maskable-zoom 1.22 --background '#141a33'` renders them with the Chromium in the visual tests' Playwright image (no image library added for a once-per-logo task). A round or transparent logo would instead take `--inset 0.8` (and a `--background` other than the logo's own navy), so the maskable crop and iOS's rounded corners don't cut into it. `--zoom` crops the source's plain navy margins from its centre so the ball fills more of a small icon; the maskable icon zooms less (`--maskable-zoom`) because Android crops it to a circle of 80% of its width, and the ball must stay inside it. On this source the ball is about 60% of the square and centred, so 1.5 leaves it at about 90% of the any-purpose icons and 1.22 leaves it at about 73% of the maskable one — inside that circle, with the navy still filling the whole square. Changing the logo means replacing the source and re-running that one command (re-checking the zoom against the new image). `--light` points at `frontend/branding/icon-source-light.png`, the light-mode mark on a light background: the same run writes `public/icons/logo-light.png` from it, at the same zoom as the other non-maskable icons. `App.vue` shows that file in light mode and `icon-192.png` in dark mode, in place of the old "Calciotto" text, on desktop only: on a phone the top bar only exists on the public pages, and the logo is hidden there. Manifest, apple-touch and favicon stay the dark mark.
- **`public/sw.js` caches nothing and has no `fetch` handler**, deliberately: offline use isn't a goal, and a worker that caches the app shell is the classic cause of an app that never picks up a new deploy. It only takes control straight away on install. `main.js` registers it in production builds only (on the dev server it would outlive restarts and get in the way of hot reload), and `playwright.config.js` sets `serviceWorkers: 'block'` so the visual tests never run one.
- **Installing differs per platform**, which `src/services/pwaInstall.js` turns into one of four states for the "Install Agoran" row in the profile's Settings (`ProfileV2.vue`): `installed` (already running standalone, or Chrome reported `appinstalled`), `prompt` (Chrome fired `beforeinstallprompt`; the row replays it, which opens Chrome's own dialog — the event works once, so the row hides afterwards until Chrome offers again), `ios` (no such event exists there and a page cannot trigger an install, so it explains Share → Add to Home Screen), and `unavailable` (anything else; no row). The tracker is created in `main.js` **before** the app mounts: Chrome fires its event shortly after load, usually long before anyone opens the Profile page, and an event nobody was listening for is lost. It also calls `preventDefault()` on it, so Chrome doesn't show its own install banner on top of ours.
- **Hidden features** — a feature can be gated per player: `models.PlayerFeature` is a `player_features` table of `(player_id, feature)` rows, and a feature is switched on **by hand, in the database**, with no route or UI to do it:

  ```sql
  INSERT INTO player_features (player_id, feature) VALUES ('<player uuid>', 'passkeys');
  -- and to switch it off again:
  DELETE FROM player_features WHERE player_id = '<player uuid>' AND feature = 'passkeys';
  ```

  The key is the composite `(player_id, feature)` rather than `BaseModel`'s id, because that id is only generated by a GORM hook and a hand-written `INSERT` would otherwise have to supply one; the foreign key to `players` makes a mistyped player id fail instead of enabling the feature for nobody (an integration test pins that). `GET /players/me/features` (`authRequired` only, the caller's own features, never anyone else's) returns `{"features": [...]}`, sorted and never null.

  **Launched features.** `design-v2`, `pwa-install` and `push-notifications` started as hidden features and are now on for **every** player: they are listed in `models.LaunchedFeatures`, and `PlayerService.GetFeatures` returns them for everyone, merged with the player's own rows (a row for a launched feature is harmless and not listed twice). Nothing was inserted in the database to launch them. `ProfileV2.vue` still reads the list for the notifications and install rows; the frontend no longer reads `design-v2` anywhere (see "Design v2" below). The backend no longer checks either of the last two anywhere (subscribing, preferences and sends are open to every player; the `design-v2` filters on `result_recorded` and `motm_announced` are gone). `passkeys` and `agoranking` are the features still hidden. To launch another, add it to `LaunchedFeatures` and drop whatever server-side check it had. `ProfileV2.vue` shows the install row only when the list holds `pwa-install` (`PWA_INSTALL_FEATURE` in `pwaInstall.js`, matching the backend's `models.FeaturePWAInstall`); a failed call just keeps it hidden. `AuthService.DeleteAccount` deletes the account's rows with the rest. Only the *row* is hidden: the manifest and service worker are static files served to everyone, so any player can still install through the browser's own menu. The visual fixtures stub the route with no feature by default; tests that need one pass `{ features: [...] }`.
- **On iOS, the installed app has its own storage**, separate from Safari's, so the first launch asks for a login again. On Android it shares Chrome's and stays logged in.

## Push notifications

Seven push notifications about a match, all about **scheduled** matches except `motm_announced` (which follows the MVP vote every match has), open to every player (`push-notifications` is a launched feature, see "Hidden features" above):

| Type | When | Who |
|---|---|---|
| `registration_open` | the sign-up list has opened (time-driven) | every group member not already signed up |
| `team_assigned` | an admin saves a roster that places or moves the player, before kick-off | that player |
| `predictions_open` | 10 minutes (`PredictionsOpenDelay`) after the first `team_assigned` of the match, once both teams have at least one player, before kick-off (time-driven; sooner when kick-off is less than 10 minutes away) | every group member, once per match |
| `kickoff_reminder` | kick-off is at most `KickoffReminderLead` (30 min) away (time-driven) | the roster once composed, otherwise the confirmed sign-ups |
| `result_recorded` | the admin's first save after kick-off, the one that sets `ResultRecordedAt` | the roster, the only ones allowed to vote for MVP |
| `predictions_settled` | 3 minutes (`PredictionsSettledDelay`) after that first score save (`ResultRecordedAt`), at most `PredictionsSettledWindow` (24 h) after it (time-driven) | only players who placed a prediction for that match, each with the points that prediction earned, once per match |
| `motm_announced` | the MVP vote has closed (`VotingWindowError`), announced at `MotmAnnounceAt`: for a scheduled match, right at the close (kick-off + 24h); for a match without a kick-off, whose vote closes at 00:00 UTC on D+2, at 09:00 Europe/Rome that day, summer or winter time (time-driven) | the winners (`ComputeMotmWinners`, ties included), whether or not they voted, with the winner message; every other player who voted, with the winners' names; once per match. Shown to players as **MVP** |

- **Backend** (`internal/services/notifications.go`): `NotificationService` holds the subscriptions (`models.PushSubscription`, one row per device, `Endpoint` unique so the same browser subscribing again — even as another account — replaces its row) and every trigger. The feature is checked when subscribing (`POST /players/me/push-subscription` answers 403 without it) **and again on every send**, through a join on `player_features`, so deleting the row stops notifications at once, even to a device already subscribed. `member_joined` is the one type sent to a group's admins only, after a signup through the group's invite code (`AuthService.Notifier` → `NotificationService.MemberJoined`), linking to the group's member list; the preferences lists only show it to an admin of at least one group. A player can also turn any type off individually (`models.NotificationPreference`); `send` skips that player for that type only. A push service answering 404/410 (app uninstalled, permission revoked) deletes that subscription, as does an endpoint outside the allowed push hosts (`isAllowedPushEndpoint`: FCM, Mozilla, Apple, and Windows for Edge, both `web.push.windows.com` and the regional `*.notify.windows.com` hosts), which `Subscribe` also refuses with a 400. Every attempt is logged with the `[push]` prefix (sent, failed, skipped because turned off, or subscription deleted), with the type, player id, subscription id and the push service's HTTP status, never the endpoint or keys. Sending is through `WebPushSender` (`github.com/SherClockHolmes/webpush-go`, VAPID, 24 h TTL); with no VAPID keys `Sender` is nil and nothing is delivered, though triggers still run — the same degraded-but-running choice as Brevo.
- **Per-notification preferences.** `notification_preferences` is one row per `(player_id, type)` the player has set (`Enabled` true or false). No row means on, so every existing player — and any type added later — keeps receiving it with no backfill. `GET /players/me/notification-preferences` returns one boolean per type (`{"preferences": {...}}`); `PUT` on the same path accepts any subset and answers the full map. An unknown type is 400 and writes nothing. Both routes are 403 without the `push-notifications` feature, like subscribe. `send` drops a player for a type they turned off after the feature check, and the match is still claimed, so turning it back on does not replay a notification that already went out. `DeleteAccount` deletes the rows with the subscriptions. The Notifications page groups them as Match (`registration_open` "Sign-ups open", `team_assigned` "Your team", `result_recorded` "Final score"), Predictions (`predictions_open` "Predictions open", `predictions_settled` "Predictions settled") and Reminder (`kickoff_reminder` "Kick-off in 30 minutes"), and only shows that list while notifications are on for this device. `motm_announced` is listed as "MVP announced" right under "Final score" (the label is `MOTM_ANNOUNCED_LABEL` in `src/services/notificationLabels.js`).
- **The event-driven ones** come from `MatchService.UpdateMatch`, which, when a `Notifier` is set (only `main.go` sets one, so tests and `cmd/` tools are unaffected), loads the roster before the save and hands a `RosterSavedEvent` (before/after player→team maps, and whether this save recorded the result) to `NotificationService.RosterSaved` after commit. That runs through `Dispatch`, a goroutine in production so an admin's save never waits on push services; tests swap it for an inline call. A save before kick-off sends `team_assigned` for whoever was placed or moved. The first save that sends it records `Match.TeamAssignedNotifiedAt` (claimed with `UPDATE ... WHERE ... IS NULL`, so a later move still notifies the moved player but never changes it). That timestamp is what times `predictions_open`, which the save no longer sends: sent in the same instant as the teams notification, a phone could show only the last of the two. The first save after kick-off (`ResultRecorded`, the one that sets `ResultRecordedAt`) sends `result_recorded` to the roster. It no longer sends `predictions_settled`, for the same reason as `predictions_open`: sent in the same instant, a phone could show only the last of the two. `ResultRecordedAt` (set once, never moved by a correction) is the clock the tick sends it from. A later correction of the score changes the leaderboard, which is derived from the score, but never sends `result_recorded` again. The points are not a second formula: that function settles this one match (odds − 1 on a hit, −1 on a miss, a predicted draw being a nil team id), and each recipient is told their own line. "Who played" for this notification means who took part in the predictions, not who was on the roster: guessing the result does not require having played, which is the same rule `MatchPredictionService` already applies.
- **The five time-driven ones (`registration_open`, `predictions_open`, `kickoff_reminder`, `predictions_settled`, `motm_announced`) need a clock the backend doesn't have**: the free Koyeb instance sleeps when idle, so a timer inside it would not fire. cron-job.org calls `POST https://api.agoran.app/internal/notifications/tick` every minute with header `Authorization: Bearer <NOTIFICATIONS_TICK_SECRET>`, compared in constant time; without that secret the route isn't registered at all. The GitHub secret value must match the one configured in cron-job.org, since `deploy.yml` copies it to Koyeb on each deploy. `Tick` is idempotent: each match records when each of the five went out (`Match.RegistrationOpenNotifiedAt`/`PredictionsOpenNotifiedAt`/`KickoffReminderNotifiedAt`/`PredictionsSettledNotifiedAt`/`MotmNotifiedAt`, `json:"-"`), claimed with an `UPDATE ... WHERE ... IS NULL` so two overlapping ticks can't both send, and a late tick still sends what is due. Each type is its own step (`tickRegistrationOpen`, `tickPredictionsOpen`, `tickPredictionsSettled`, `tickKickoffReminders`, `tickMotm`): a step whose query fails is logged (`[push] tick: <type> failed`) and the others still run, so one broken query can't silence every notification. The tick still answers 500 when any step failed, with the error per step and, under `sent`, what went out anyway. `/health` deliberately doesn't touch the database, so it can't see a failing tick: cron-job.org's failure email (job settings, notify on failure) is what reports one. `predictions_open` is due `PredictionsOpenDelay` (10 min) after `TeamAssignedNotifiedAt`, or straight away when kick-off comes before that; it goes out at the first tick from then on that finds both teams with a player (`rosterFullyComposed`) and kick-off still ahead, to every current member, and `PredictionsOpenNotifiedAt` is set to that tick's time. The reads happen before the claim, so a failure to load the roster or the members leaves the match unclaimed and the next tick retries. Once set, nothing sends it again: not a moved player, an edited goal, or a roster emptied and recomposed. A list that opened more than `RegistrationOpenWindow` (6 h) before any tick saw it is left alone — which is also why every list already open when the feature shipped needed no backfill. `predictions_settled` is due `PredictionsSettledDelay` (3 min) after `ResultRecordedAt`, so with the tick every minute it arrives 3 to about 4 minutes after the score save (plus the instance's wake-up when it was asleep). It goes out at the first tick from then on, computed from the match as it stands at that tick (a score corrected within the 3 minutes is settled on its final value), and `PredictionsSettledNotifiedAt` is set to that tick's time; the tick's response counts it in `predictions_settled`. A match nobody predicted is marked done at that tick and sends nothing. A roster no longer fully composed has nothing `ComputePredictionStandings` can settle: the match stays unclaimed and the first tick after it is composed again sends it. A result recorded more than `PredictionsSettledWindow` (24 h) before any tick sent it is never announced. When the column was added, every result already recorded had been settled by the save itself: `database.AddPredictionsSettledNotifiedAt` adds the column and, in the same transaction, sets it to each such match's `result_recorded_at` (`BackfillPredictionsSettledNotifiedAt`), so the first tick after that deploy announces nothing old. It runs only on the start that adds the column (before `AutoMigrate`, which would add it without the backfill); on any later start a NULL on a recorded result is a notification still waiting for its tick. `motm_announced` (`notifications_motm.go`) goes out at the first tick at or after `MotmAnnounceAt` (the close itself for a scheduled match; 09:00 in Rome on the closing day for one without a kick-off, computed with the zone database embedded through `time/tzdata`, since the alpine image has none), so within about a minute of that time. The tally (`tallyForMatch`, the one `ListVotes` shows) is read at that tick; winners get `winner: true`, other voters the `winners` names (tally order, so alphabetical on a tie), and anyone without the `design-v2` feature is dropped from both, and `Match.MotmNotifiedAt` is set to that tick's time. That filter reads the `design-v2` row in `player_features` (`playerHasFeature`). It only makes sense while v2 is a hidden feature: when v2 becomes the design for everyone, remove the filter in `notifyMotm` (and the v2-only listing of the preference) rather than counting on every player having the row, otherwise anyone without it is silently never told. A match nobody voted on is marked done and sends nothing. A vote whose announcement time passed more than `MotmAnnounceWindow` (24 h) before any tick sent it is never announced. When the column was added, `database.AddMotmNotifiedAt` added it before `AutoMigrate` and, in the same transaction, set it to that announcement time on every match whose announcement time had already passed (`BackfillMotmNotifiedAt`), so the deploy announced no past vote; a vote still open, or closed that morning before 09:00 in Rome, is announced normally. It runs only on the start that adds the column.
- **The payload is data, not text** (`PushMessage`: type, deep link, tag, group, kick-off instant, team, score, and — on `predictions_settled` only — the points that recipient earned). `frontend/public/sw.js`'s `buildNotification` writes the wording, so a kick-off time is shown in the device's own zone, like everywhere else in the app; it is exported for `tests/unit/public/sw.spec.js`. `predictions_open` reads "Predictions are open" / "{Group}: match on {kick-off}. Make your pick." `predictions_settled` reads "Predictions settled" / "Bianco won! You earned 2.33 points." — the name of the team that scored more, from the payload's score, without repeating the score `result_recorded` already showed; "It's a draw! You earned 1.50 points." when the goals are level; the points sentence alone when the score is missing. A loss uses the absolute value and no minus: "You lost 1 point." when that amount is exactly 1, "You lost 1.50 points." otherwise. A whole number drops the decimals ("2 points"); anything else keeps two. Zero is "You earned 0 points." `motm_announced` reads "You're the MVP!" / "See the game." for a winner, and "MVP: Luca" / "See the game." for a voter (the same "MVP:" on a tie, "MVP: Luca & Marco", "MVP: Luca, Marco & Sara" for three or more; no plural); the code keeps the `motm` names; every word of it is in `MOTM_TEXT` in `sw.js` (`name` is a copy of the short `MVP` constant), and the deep link opens the match. The deep link is `/?match=<code>`, so the Go side has its own copy of the base62 short-link encoder (`services/shortlink.go`), pinned against vectors from `shortLink.js`. Tapping a notification focuses an open Agoran window and sends it there, or opens one. The tag is per match and type, so a second team change replaces the first notification instead of stacking.
- **Frontend**: `src/services/pushNotifications.js` turns the browser's situation into one state for the Notifications page (`/profile/notifications`, `ProfileV2.vue`) — `needs-install` (not running as the installed app — see the next bullet), `unsupported` (no Push API or no registered worker, which includes the dev server and the visual tests), `denied` (only the user can undo it, in the settings), `off`, `on`. Turning on must run from the click (browsers only show the permission prompt for a user gesture); it fetches the VAPID public key from `GET /push/public-key` (`''` when unconfigured, so the frontend has no build-time key to keep in sync), subscribes, and posts the subscription. Turning off tells the backend first, then drops the browser subscription. When the page loads in the `on` state it re-sends the subscription, since the backend may have dropped it, and it loads `GET /players/me/notification-preferences`. Turning one type off `PUT`s that key alone (`{"preferences": {"kickoff_reminder": false}}`); turning the device off hides the list without forgetting the choices. `App.vue`'s `logout()` turns push off on this device before clearing the token, so the next account on it doesn't get the previous one's notifications.
- **Only from the installed app, on every platform.** Notifications can only be turned **on** when the page runs as the installed app (`isStandalone`); in any browser tab the card says to install first. An iPhone has no choice (Safari tabs have no push), and making Android and desktop match keeps one behaviour everywhere, with notifications arriving as the app. A tab can still read `on`: on Android and desktop the installed app and the browser share one subscription, so a tab reports it and lets the player turn it off.
- **A device stops receiving when the session ends, not only on logout.** `disablePushOnLogout` tells the backend when it can and drops the browser subscription in every case (`forgetPushOnThisBrowser`), so logging out offline can't leave the device subscribed. `api.js`'s 401 interceptor does the same browser-only drop when a session that existed ends without a logout (expired, revoked by a password change elsewhere): with no token the backend can't be told, but the push service then answers its next send with "gone" and `NotificationService.send` deletes the row. A 401 with no session (a wrong password at login) touches nothing.
- **Uninstalling on Android.** The subscription belongs to Chrome, not to the installed app, so uninstalling the app doesn't stop notifications, and no event tells a site it was uninstalled. `stopPushIfAppUninstalled` (run once per load from `App.vue`) asks Chrome whether the app is still installed (`navigator.getInstalledRelatedApps`, with the manifest listing itself under `related_applications`) and, in a tab, turns notifications off when it no longer is. It only trusts an empty answer once the check has been seen to work on this device: opened as the installed app, it must answer "installed", which is recorded in `localStorage` (`calciotto-installed-app-detection`). Without that proof — another browser, an unsupported version, a manifest URL Chrome doesn't resolve — it does nothing, since turning notifications off on a guess is worse than leaving them on. It only runs when the site is opened, so a player who uninstalls and never comes back keeps receiving through Chrome; nothing on the web can catch that.
- **Setup**: generate the keys locally with `npx --yes web-push generate-vapid-keys` and paste them straight into GitHub — the public one as the `production` variable `VAPID_PUBLIC_KEY`, the private one as the secret `VAPID_PRIVATE_KEY` — plus `VAPID_SUBJECT`, then the repository-level `NOTIFICATIONS_TICK_SECRET` (see "Configuration inventory" above). `VAPID_SUBJECT` must be the bare contact email (for example `bref.tibo@gmail.com`) or an `https://` URL, with no `mailto:` prefix. `github.com/SherClockHolmes/webpush-go` v1.4.0 prepends `mailto:` itself to any subject that does not already start with `https:`, so `mailto:bref.tibo@gmail.com` is signed as `mailto:mailto:bref.tibo@gmail.com`. Chrome and FCM accept that doubled prefix; Apple's push service rejects it with `403 {"reason":"BadJwtToken"}`. That secret's value must match the bearer token configured in cron-job.org, because `deploy.yml` copies it to Koyeb on each deploy. `deploy.yml` syncs the optional secrets to Koyeb like `BREVO_API_KEY`, with a warning when they are missing. The repository variable `BACKEND_URL` was only used by the removed tick workflow and may now be unused.

## Design v2

The app's **only design**. `design-v2` (`models.FeatureDesignV2`) started as a hidden feature, was launched (it is still in `models.LaunchedFeatures`, so `GET /players/me/features` keeps listing it), and has since **replaced v1 entirely**: the frontend no longer reads the flag at all, every route points straight at its v2 page, and the v1 screens are gone (`MatchesPanel.vue`, `MatchDetails.vue`, `Profile.vue`, `Predictions.vue`/`PredictionsPanel.vue`, `Login.vue`, the standings tables, the v1 group modals, `InstallAppCard.vue`/`NotificationsCard.vue`, the `*Gate.vue` switches, `services/designV2.js`, `services/loginV2.js`, and their unit and visual tests).

`GET /players/me/features` returns the caller's flags and guide completion status. Passkey access requires `passkeys`.

- **Nothing waits for the features request.** `App.vue` paints the requested page straight away. It used to hold every session's first load on a "Loading Calciotto…" screen for up to 2 s (`STARTUP_WAIT_MS`) to decide between v1 and v2, and fell back to v1 when the request failed; both are gone with the choice itself. `src/services/featureStatus.js` still caches the response in memory by session ID (one request per session, shared by every caller, including after access token renewal); the shell reads it in the background for the guide only (`syncGuide`), and `ProfileV2.vue` for its notifications, install and passkey rows. `logout()` resets the cache and discards any in-flight response.
- **The class.** `App.vue` puts `design-v2` on `#app` — the same element that already carries `.dark-mode` — on every route, the public auth pages included; no request decides it, and the v1 top bar (logo and theme toggle) is gone. `main.js` mounts only after `router.isReady()`; a missing route name (the router's start location) is treated as not authenticated in `isAuthenticatedRouteName`.
- **Player guide.** An explicit `guide_completed: false` opens `PlayerGuide.vue` in place of the page when the background features answer lands (on a slow network the page shows briefly first; this happens once per account). `PUT /players/me/guide` records completion once per account in `players.guide_completed_at`. The required guide can't be closed or skipped; only once the player has reached the end and saving has failed does it offer Continue anyway, which lets them in for this session only: the server still says the guide is incomplete, so the next session asks again. Profile settings offer a replay. The five screenshots in `frontend/public/guide/{light,dark}/` use fictional fixture data. The guide follows the app theme, which defaults to the system theme until a player saves a preference.
- **Public pages.** Login, signup, forgot-password and reset-password never call `GET /players/me/features`. `/login` is `v2/LoginV2.vue`, in the v2 shell (logo-only top bar, no tab bar, no theme toggle: the theme is the saved one or the device's). A leftover `calciotto-login-v2` localStorage key from the rollout is ignored. LoginV2 makes the usual calls (`login`, `signInWithPasskey`, `setToken`, push `/`) and offers the passkey under the same condition (`supportsPasskeys() && shouldOfferPasskeyLogin()`); its failures, a wrong password included, go to the shared toast as sentences (`authErrorMessage`, e.g. "Invalid email or password."), 12px from the bottom on a phone since there is no tab bar. `/signup`, `/forgot-password` and `/reset-password` are `v2/SignupV2.vue`, `v2/ForgotPasswordV2.vue` and `v2/ResetPasswordV2.vue`, on the same layout: the four share `v2/authPageV2.css` (`<main class="page is-auth auth-v2">`, a 360px column on web), and the three new ones add `.has-toast-room` (96px of bottom padding on a phone, so a two-line toast never hides the last link). They make the same calls as the v1 pages did, with no API change. **Sign up**: the invite code comes first (Space Mono capitals), prefilled from `?invite=CODE` with the hint "Filled in from your invite link." while the field still holds the link's code ("Ask your group admin for it." otherwise); an empty code is refused before any request ("Invite code is required."), and every failure goes to the toast; success stores the token and pushes `/`. **Forgot password**: the backend's generic answer becomes a grey `.auth-notice` (`role="status"`) above the form and the button becomes "Send again"; failures go to the toast. **Reset password**: one field; a link with no `token`, or the backend's "invalid or expired reset token", shows "This link has expired. Request a new one." in the toast; success pushes `/login?reset=success`. `src/services/v2Auth.js` turns the backend's lower-case messages into sentences (`asSentence`, `authErrorMessage`, `resetErrorMessage`).
- **Isolation.** Every v2 token lives in `src/assets/design-v2.css`, scoped to `.design-v2` and `.design-v2.dark-mode`; the layout rules that read them live in `src/assets/design-v2-ui.css`, every selector under `.design-v2`. `main.js` imports both. The global variables (`--primary-color`, `--bg-primary`, and the rest) are not touched, (no v1 page is left that reads them).
- **Where the screens live.** The v2 pages are in `src/components/v2/`: `HomeV2.vue`, `MatchView.vue`, `EditMatchV2.vue`, `RankingsV2.vue`, `PredictionsV2.vue`, `ProfileV2.vue`, and the auth pages `LoginV2.vue`, `SignupV2.vue`, `ForgotPasswordV2.vue`, `ResetPasswordV2.vue`. `ProfileV2.vue` uses two v2-only blocks: `InvitationV2.vue` (the invite-code card in group settings, with Renew confirmation) and `PasskeysV2.vue` (the Account page's Passkeys section, `passkeys` feature only). Both sit in `CollapsibleCardV2.vue`, a card closed by default under a header button (chip icon, title, mono summary, chevron). Both report an open confirmation through a `confirming` event so the shell's `is-confirming` class shows the sheet. The router points `/matches/:id/edit` at `EditMatchV2.vue`, `/rankings` at `RankingsV2.vue`, `/predictions` at `PredictionsV2.vue`, `/login`, `/signup`, `/forgot-password` and `/reset-password` at their v2 pages and every `/profile...` route at `ProfileV2.vue`, with no guard about the design. `/` is still `MatchesAndStandings.vue`, now a thin shell that resolves the group and season, publishes them to the top bar's selects (`v2Context`) and mounts `HomeV2.vue`; it no longer loads the three standings tables (the old v2 home fetched points, scorers and MOTM on every visit and showed none of them). The v2 shell (top bar, tab bar) is in `App.vue`. The font faces are plain `@font-face` rules at the top of `design-v2.css`, pointing at `public/fonts/v2/*.woff2`, and `index.html` preloads DM Sans and Big Shoulders Display, so text no longer repaints in a new face once a features answer lands.
- **Group details.** In the v2 group page, members can see its optional description and custom website link. Admins edit both in Group settings. The app saves them through `PUT /groups/:id/details` and reads them from `GET /groups/me`.
- **Fonts.** Headings use **Big Shoulders Display** (700 and 800). Labels use **Space Mono**, uppercase. Body text uses **DM Sans** (400/500/600).
- **Colour.** Tokens match the validated mockups. Accent `#e8743b` and on-accent `#141a33` are the same in both themes. Dark: navy `#141a33`, surface `#1c2440`, text `#eef0f7`, muted `#8b93ad`, rule `rgba(238,240,247,0.12)`, outline `#9aa3bc`, danger `#ff8a80`, success `#7dcea0`, wait `#e8c37a`. Light is the inversion (off-white `#eef0f7`, white surface, navy text, muted `#5c6578`, danger `#a8362c`, success `#2f6b4f`, wait `#8a5a12`). `.dark-mode` on the same element selects the dark palette. The orange accent is reserved for the primary action and for the signed-in player. Top bar and tab bar are 64px.
- **Logo.** Only what the app shows is deployed: `frontend/public/icons/v2/` holds the two header symbols, downscaled to 120 px (three times their 40 px display size, for high-density screens; the 512 px originals were 240 KB each and loaded on every v2 page). The two source variants stay in `frontend/branding/v2/`, out of `public/`. The installed app has moved to the new mark: every app icon, the favicon and v1's navbar logo (`icon-192.png`/`logo-light.png`) are generated from them through `branding/icon-source*.png` (see "Icons" above), for every player, flag or not. The v2 top bar shows `header-symbole-sombre.png` in dark mode and `header-symbole-clair.png`, the inverted mark, in light mode: the logo only, never with text, and never on an orange background.
- **Profile stats.** `GET /players/me/stats` also returns `Seasons` and `PredictionPoints` (see "Player profile" above), and `Email`, the signed-in player's own address, which the v2 Account page shows read-only.
- **Email exposure.** `Player.Email` is `json:"-"` and is never serialized. The member list (`GET /groups/:id/players`, `models.PlayerWithRole`) says whether a player has an account with `has_account`, never with the address; that is what both profile pages use to style a player with no account and to hide the promote button. The only response that carries an email is the caller's own, in `/players/me/stats` `Email`. `playeremail_integration_test.go` and `groupmembers_email_integration_test.go` pin both sides.
- **Preferred positions.** `fillTeamsFromRegistrations` (the old v1 split, still in `matchRegistration.js`) knows nothing about them. A player picks any of `GK`, `DEF`, `MID`, `FWD` (or none) on the Account page, stored in `players.preferred_positions` (`text[] NOT NULL DEFAULT '{}'`, `models.PreferredPositions`, a small `Scanner`/`Valuer` writing the array literal `{DEF,MID}`; AutoMigrate adds the column on start-up without touching any row, every existing player simply having none). `PlayerService.UpdatePreferredPositions` → `NormalizePreferredPositions` rejects anything else with `ErrInvalidPosition` (400, the reason naming the value), forgives case and spaces, deduplicates and stores canonical order GK, DEF, MID, FWD. `Player.PreferredPositions` is `json:"-"` like `Email`: the player reads and replaces their own through `GET`/`PUT /players/me/positions` (`{"PreferredPositions": [...]}`; a body without the key is a 400, not a silent wipe; a route of its own because `PATCH /players/me` is the rename, which requires a name, while the Account page saves positions alone at every tap). **Every member of a group sees the others' positions**, through `GET /matches/:id/positions` behind `RequireGroupMembershipByMatchPathParam` (non-member 404), which lists the match's group members with at least one position as `[{PlayerID, PreferredPositions}]`; the sign-up list and the match details never carry them (`positions_integration_test.go`). They were admin-only at first, then opened to every member. In the UI (`src/services/v2Positions.js`): Account → a "Positions" section under Identity, four equal 44 px toggles (`aria-pressed`, in a `role="group"`), optimistic save at each tap sent one after the other, toast "Positions saved." or rollback plus the server's reason; `MatchView.vue` → for every member, a grey mono tag after the name in both line-ups ("DEF · MID", nothing for no position, the name giving way with …); `EditMatchV2.vue` → the tag at the right of each row and, under each team's count, "GK 1 · DEF 2 · MID 2 · FWD 1" (a multi-position player counts in each of their positions). **The v2 automatic split** is `splitByPositions(registrations, rosters, positionsById, rng)`, pure, with `rng` injectable: additive like v1 (confirmed only, placed players never move), sizes at most one apart (the odd player's side drawn at random), the pool shuffled; then for GK, DEF, MID, FWD in turn each team with nobody able to play it gets one (a single-position player first, else the one with the fewest positions: the multi-position joker); then the other players with a position by main position (first in canonical order), each to the team where the per-position counts end up closest; then the players with no position to the team with more room; last, newcomers on opposite teams are swapped while that evens the counts. No Elo. Without positions (none set, or the request failed) it is a plain random split. The visual tests seed `Math.random` in `gotoApp` so the split screenshots are stable.
- **Done, and not done.** Done: everything signed in, plus login, signup, forgot-password and reset-password. Kick-off times use the viewer's own zone, the same rule as `formatDateTimeShort` in `datetime.js` (no `timeZone` option). The score on the edit page is derived from goals plus the other side's own goals. Some visual specs still pass `{ features: ['design-v2'] }` to `gotoApp`; it no longer changes anything.
- **Since the launch, every player starts with the required guide**: an account whose `guide_completed_at` is `NULL` (every player who was on v1) sees `PlayerGuide.vue` on their next sign-in, once.
- **Tests.** `tests/unit/services/featureStatus.spec.js` covers session caching. `tests/unit/components/App.spec.js` covers the v2 class, public routes, failure and logout. `tests/visual/guide.spec.js` covers completion, save retries, replay and both themes. The screens have visual baselines under `tests/visual/__screenshots__/v2-*/` (see "Visual regression tests" above).
- **Loading a match from a bare id.** `MatchView.vue` and `EditMatchV2.vue` load through `findMatchInMyGroups` (`src/services/v2Match.js`), which runs `findGroupForMatch` over the caller's groups, the active one first. `GET /matches/:id/details` without a `group_id` resolves against the caller's *first* group, so calling it bare 404s every match of a player's other groups, the same trap `canEditMatch` already avoids.
- **Creating a match** is a page of its own, `NewMatchV2.vue` on `/matches/new` (v2 only: the route's guard sends a player without the flag home, and the page sends a non-admin of the active group home). It only creates **scheduled** matches: day and kick-off time, when sign-ups open (now by default), places (16 by default) and "Sign me up" (`register_creator`); recording an already played match isn't offered in v2. `src/services/v2NewMatch.js`'s `buildNewMatch` mirrors the backend's schedule rules (plus a kick-off in the future) and names the field a reason belongs to, which the page shows under that field; the backend's own refusal shows above the button. A created match opens on its page. The way in is the home page's floating **+** button (`.fab`, labelled "New match"), bottom right, above the tab bar on a phone and in the corner on a desktop. It is shown to an admin of the active group whatever the page shows, so the next match can be created while one is already scheduled; the page gets extra bottom padding (`.has-fab`) so the button never covers the last row once scrolled to the end. ## Internationalisation (i18n)

Part 1 of 7 of the translation plan (English stays, French, Italian, German and Spanish come). This part is the plumbing only: nothing on screen changes, no text goes through it yet. The plan, in order: infrastructure (this), extraction of the English texts into `en.json`, the fr/it/de/es bundles, the player's saved language (`players.locale`, NULL = follow the phone) with the Account selector, push and email texts, API error codes, then the visual pass in German at 360 px.

- **`vue-i18n`, composition API, `legacy: false`** (`src/i18n.js`). `fallbackLocale` is `en`, so a key missing from a language shows its English text rather than the key. `vite.config.mjs` sets the `__VUE_I18N_*` flags (no legacy layer in the bundle, no flag warnings). The build keeps `script-src 'self'`: vue-i18n compiles messages without `eval`/`new Function`.
- **Bundles** are `src/locales/<code>.json`, picked up by file name (`src/locales/index.js`, `import.meta.glob`). `LOCALES` there lists the five languages in the selector's order (English, Français, Italiano, Deutsch, Español) with their own name and the BCP 47 tag used for Intl (`en` → `en-US`, so English keeps the output of the `'en-US'` calls elsewhere). **A language is supported when its bundle exists and is not empty**: today only `en`, which is why a French phone still gets English and `<html lang="en">`. Adding `fr.json` is enough to switch French on.
- **The active language** is owned by `src/services/locale.js`, never set from components on the i18n instance directly. `detectLocale()` takes the first language of `navigator.languages` that the app speaks (regional tags count: `fr-CA` → `fr`; an unsupported first choice such as `pt-BR` gives way to the next one), else `en`. Public pages stay on the browser's language and never choose one.
  - `source` is `'phone'` (nothing chosen: follows the browser, including a later `languagechange` event) or `'explicit'` (`setLocale(code)`; an unsupported code is refused, returns `false`). `followPhone()` goes back to the phone, which is the first line of the future selector (`players.locale` NULL). A chosen language equal to the phone's is still `explicit`.
  - Every change goes through one `apply()` that sets the i18n locale and `<html lang>`, so the attribute (screen readers, hyphenation, browser translation offer) cannot drift from what is shown. `index.html` keeps `lang="en"` as the pre-script default.
  - **Not persisted, and not in `localStorage`** (not for the language: the saved choice will be the server-side `players.locale`). An explicit choice therefore lasts until reload for now. The hooks for the saving are ready: `initLocale({ saved })` (called in `main.js`, with nothing yet) restores a saved choice as `explicit` **without announcing it**, and `onLocaleChange(listener)` is called with `{ locale, source }` on every later change, which is where the PATCH will go (source `'phone'` = send NULL). If a local fallback is wanted for signed-out pages once the selector exists, that is a decision to take then, not a default.
  - `localeState` is a read-only reactive `{ locale, source }` for components.
- **`src/services/intl.js`** is the Intl helper: `formatDate(value, options)` (Date, timestamp or RFC3339; `''` for empty or unparseable), `formatNumber`, `pluralCategory(n)`, `plural(n, { one, other })`, all in the active language, built per call so a language change needs no invalidation. No option is added by default: 24 h clocks come from the language itself (French, Italian, German, Spanish; English stays 12 h). Plurals in messages (`"{n} pt | {n} pts"`, `$t(key, { n }, { plural: n })`) use the same `Intl.PluralRules` rule (`src/services/pluralRules.js`), so French says "0 pt" where English says "0 pts"; vue-i18n's own default would call 0 plural.
- **Not rewired yet**: `datetime.js` and `v2Home.js` still format with the literal `'en-US'`. They move to the helper together with their texts in the extraction PR (English output is identical by construction: same tag). `en.json` holds only a few keys so far (`language.label`, `award.mvp`, `award.mvpOfTheMatch`, `unit.points`); a test pins the award keys to `MVP` / `MVP_OF_THE_MATCH` of `v2Home.js` until those constants are replaced by the bundle.
- **Fixed terms**: « Agoranking » and « MVP » are never translated, and « MVP » takes no plural « s » (a tie is still « MVP »; « 3 MVP »). The long form is translated around it (« MVP du match », « MVP des Spiels », « MVP della partita », « MVP del partido »).
- Tests: `tests/unit/services/{locale,intl,i18n}.spec.js`. The locale service keeps module state, so they reset modules between cases and make a language "available" by giving it a message (`i18n.global.setLocaleMessage`).

## Action toasts

Every message reporting the outcome of an action goes through **one component, `AppToast.vue`**: bottom right (above the mobile tab bar), a real close button (`.toast-close`), gone on its own after `TOAST_DURATION_MS` (five seconds), a new message replacing the current one and restarting the timer. A view holds it by ref (`<AppToast ref="toast" />`) and calls `this.$refs.toast.show(message, type)` / `dismiss()`, with `type` one of `success`/`error`/`info`/`warning`. Every v2 page that reports an action holds one (`HomeV2`, `MatchView`, `EditMatchV2`, `PredictionsV2`, `ProfileV2`, `InvitationV2`, `PasskeysV2`, the four auth pages), and so does `ShareButton.vue` (see "Design v2" for what each reports). Owning the timer in one place is the point: before it, each view's own copy had drifted (different durations, and one dismiss looking up a selector that matched nothing).

The styles stay in `global-styles.css` (`.toast-container`, `.toast-bottom`, `.toast-message.<type>`, `.toast-close`). Bootstrap ships its own `.toast-container` with `width: max-content`, which beat the mobile left/right stretch and left every toast at its 300px content width on a phone, so the mobile rule sets `width: auto`.

**Form validation errors stay inline**, next to the field they're about: the profile's rename, account-deletion password and group-details fields (`ProfileV2`, `GroupDetailsForm`), and the new-match form's per-field reasons (`NewMatchV2`). A toast in a corner would separate the message from what needs fixing. The auth pages (`LoginV2`, `SignupV2`, `ForgotPasswordV2`, `ResetPasswordV2`) are the exception: their failures go to the shared toast (see "Design v2").

## Gotchas

- `AutoMigrate` runs on every backend startup (`InitDB` in `connect.go`), so schema changes to the GORM models in `internal/models/database.go` take effect automatically on next run/restart — no separate migration files exist.
- **The app's pool uses pgx's simple protocol** (`appDialector` in `pkg/database/connect.go`, `PreferSimpleProtocol: true`): no statement is prepared on the server. With pgx's default (prepare and cache every query), Neon's pooler shares a prepared statement between every client sending the same query text, so after a migration adds a column a `SELECT *` prepared before it fails on every run with `cached plan must not change result type` (SQLSTATE 0A000) for as long as the pooler keeps the server connection that prepared it. That took the notifications tick down for about 15 minutes after #76 added `matches.motm_notified_at` (every tick a 500 from 10:47 to 11:02 Rome time), until it cleared on its own. `TestAppPool_SelectStarSurvivesAnAddedColumn` reproduces it against a plain Postgres. Don't switch the app pool back to prepared statements.
- **Schema application is serialized by a Postgres advisory lock**, not merely made less likely to race: `InitDB` calls `applySchema` through `withSchemaMigrationLock`, which takes `pg_advisory_lock(schemaMigrationLockKey)` (an arbitrary fixed key, `726750310`; nothing else in this codebase takes an advisory lock). Two situations hit this for real — several backend replicas each calling `InitDB` on startup in production, and `go test ./...` in CI, where every package is its own binary running concurrently and `testutil.OpenDB`'s `sync.Once` only dedupes *within* one binary. Without it two processes can both see a table as absent and issue concurrent `CREATE TABLE`s, which Postgres does **not** fully serialize on its own: one loses a race on the implicit row type registered in `pg_type` and fails with `duplicate key value violates unique constraint "pg_type_typname_nsp_index"` (SQLSTATE 23505) — not an app bug, just two DDL statements arriving at once. The mechanics are load-bearing: a session-level advisory lock belongs to the *connection* that took it, so the helper pins one physical `*sql.Conn` out of the pool and hands `fn` a `*gorm.DB` built on that same connection (`postgres.Config{Conn: conn}`) rather than the pool-backed `db` — which could otherwise route `AutoMigrate`'s own statements onto a different connection than the one holding the lock. Release is `defer`red and only logs a warning on failure, since closing the connection drops a session-level lock anyway.
- Outside Docker (e.g. running `go run .` or `go run ./cmd/seed` directly on the host), `DB_HOST` defaults to `db` which won't resolve — override it to `localhost` and match the port Postgres is published on (`POSTGRES_PORT`/`DB_PORT` in `devops/env/develop.env`, 5432 by default).
- Forgetting `--env-file env/develop.env` on `docker compose up` silently breaks the `db` service: `${POSTGRES_PORT}`/`${POSTGRES_PASSWORD}` and the bare `DB_NAME`/`DB_USER`/`DB_PASSWORD` refs resolve to empty, and the `pg_isready` healthcheck then fails with `role "root" does not exist` (it falls back to the container's default OS user). Adding `environment:`/`env_file:` on the `db` service itself does not fix this — those only populate the container's runtime env *after* Compose has already resolved the `${...}` placeholders in the YAML from the flag/shell env.
